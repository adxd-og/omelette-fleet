# 0.3.3 Implementation Plan — master (package map and interfaces)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This file is the map; each package has its own plan file next to it (`2026-09-08-0.3.3-P<n>-*.md`).

**Goal:** No paid answer is lost: units send progress, spool every result, answer cancellation by policy, and `doctor` names the client's two timeout walls; plus the handoff block after compaction, `doctor` under any prefix, and `capped` for every unit.

**Architecture:** The MCP transport (`core/jsonrpc.mjs`) grows a per-request context (id, progress token, abort signal) and an in-flight table; the runtime (`core/unit.mjs`) uses it for progress, cancellation and a result id, and writes every result to a new spool module (`core/results.mjs`) before answering. The CLI (`bin/omelette-fleet.mjs`) gains `results` and two doctor checks; the guard hook gains a `SessionStart` branch; two adapters learn `capped`.

**Tech Stack:** Node >= 20, zero runtime dependencies, `node --test` with fake vendor binaries under `test/`.

**Spec:** `docs/superpowers/specs/2026-09-08-0.3.3-design.md`

## Interfaces (fixed here; package plans conform to these names)

### P1 produces

`core/jsonrpc.mjs`
- `createHandler({ serverInfo, tools, callTool, instructions, notify = () => {} })` — `callTool(name, args, call)` now receives a third argument:
  ```js
  call = {
    id,                       // the JSON-RPC id, number or string, as received
    progressToken,            // params._meta.progressToken, or null
    signal,                   // AbortSignal; aborted by notifications/cancelled for this id
    notify(method, params),   // sends a JSON-RPC notification { jsonrpc, method, params } — no id
  }
  ```
  - `tools/call` registers `{ id, controller }` in an in-flight map before dispatch; removes it after. Ids compare by type and value (`1` and `"1"` are different requests).
  - `notifications/cancelled { requestId }` → `controller.abort()` for a live id; unknown / finished ids are ignored; returns `null`.
  - When `call.signal.aborted` is true by the time `callTool` settles, `handle` returns **`null`** (no response is sent), whatever the mode.
  - The handler object exposes `handle.inflight()` → number and `handle.drain()` → Promise resolved when in-flight reaches 0 (immediately if already 0).
- `serve({ … })`: passes `notify` = `send`; on stdin `end` it stops reading, awaits `handle.drain()`, then `process.exit(0)`.
- Spike 1a: under `OMELETTE_DEBUG_META=1` the handler logs `tools/call _meta=<json>` via `log` — kept behind the flag, documented as a debugging aid.

`core/config.mjs`
- `KEY_SCHEMA.cancel = { type: 'enum', values: ['finish', 'kill'], default: 'finish' }` (per unit or `defaults`, like every key).

`core/spawn.mjs`
- `runProcess({ …, signal })`: when `signal` aborts, `SIGKILL` the process group exactly like the hard-kill path; the result carries `cancelled: true` (and `killed: true`). Absent signal = today's behaviour.

`core/unit.mjs`
- `TOOL_KINDS` gains `'local'`: a tool with `run(args, ctx)` answered in-process, never spawned, never tracked by the status feed, never spooled. `catalog` stays as it is.
- `createUnitRuntime(unit, { env })` → `{ log, status, callTool, cfgFor, tools }` unchanged in shape; `callTool(name, args = {}, call = {})` accepts the P1 `call` (every field optional; tests may omit it).
- Result id: `makeResultId(seq)` exported → `${YYYYMMDDTHHMMSSZ}-${process.pid}-${seq}`; the runtime holds its own counter; `status.start(tool, promptText, model, effort, resultId)` takes it as a 5th argument.
- Progress: when `call.progressToken != null`, every 30 s (`PROGRESS_EVERY_MS`, exported, overridable via `createUnitRuntime(unit, { env, progressEveryMs })` for tests) → `call.notify('notifications/progress', { progressToken, progress: <elapsed s>, message: '<unit> <tool> running · <elapsed>s' })`. Cleared in `finish()`.
- Cancellation: `mode = cfg.values.cancel`; `ctx.spawn` and `ctx.retry` receive `signal` only when `mode === 'kill'` (`finish` lets the child run). `ctx.signal` is exposed to adapters (gather loops skip remaining spawns when aborted).
- `finish(text, isError, extra)` gains the outcome: status `'ok' | 'error' | 'cancelled'`; `extra.detached = true` when the request was aborted and the run was left to finish; `extra.resultId` always. `finish` returns the same `{ text, isError? }` as today; the handler decides whether to send it.
- **P2 hook point:** `finish()` calls `onResult(record)` (a runtime-internal function, no-op in P1) with
  ```js
  record = { resultId, tool, model, effort, startedAt, endedAt, durationMs,
             status, partial, detached, cwd, promptPreview, text }
  ```
  (`cwd` = the call's `args.cwd` if any, else `''`; `promptPreview` = the status feed's 200-char preview).

`core/status.mjs`
- `start(tool, promptText, model, effort, resultId)`; `active` entries, the `start` log line, `end` log line and `lastEvent` carry `resultId`. `end(token, status, error, extra)` accepts status `'cancelled'`; `extra.detached` passes through like `partial`. Schema stays 1; `docs/STATUS-FEED.md` lists the new fields.

- Runtime: `onResult` = `store.write(record)` when `cfg.values.results`; the store is created per call from `cfg` (config live-reload semantics as elsewhere). The write happens inside `finish()` before it returns.
- Tool `<unit>_result` (kind `local`, appended by `createUnitRuntime` when the adapter did not declare one) with `inputSchema { id?: string }`; output shapes per spec 2b.
- CLI: `omelette-fleet results [unit] [id] [--path]`; unit names validated against `UNIT_ORDER`; exit 1 with a one-line message for an unknown unit / id.
