## Rulings on the spec

1. **The reviewer's report has the five sections every shipped role writes.** The spec says "findings only, ranked, each `location · scenario · consequence · how to confirm`, then one line". The rules' "Evidence travels with pointers" and `test/evidence-pointers.test.mjs:14, :68` hold every `AGENT_FILES` entry to `## TASK / FINDINGS / DIFF / TEST RESULTS / OPEN QUESTIONS` with pointer lines, and the plan-review rule has the session "open the findings' pointers". So the report file keeps that shape; `## FINDINGS` holds the ranked four-part findings, each a pointer line whose `path:line` · fragment *is* the location (`omelette-fleet check` verifies it); `## DIFF` is `none`; a finding short of four parts goes under `## OPEN QUESTIONS` ("a question", as the rules say). "Findings only" = no praise, no summary of what is fine, no fix. The reply is the verdict line and the count, as the spec says. Cost if wrong: an exception for the reviewer in two existing tests.
2. **`<name>` comes from the brief**; when the brief gives none, the branch or file under review names it. The one-file sentence is pinned verbatim: ``The only file you write is `.omelette/reports/<name>-review.md`.``
3. **Task order.** The spec calls the definition's design "P1's first task" (the matched repeat's fallback candidate), so the definition is Task 1 and the guard Task 2. Between those two commits the definition's sentence "where the operator wired the guard hook … refused" is ahead of the code by one commit; both land before any merge. If P3 runs the matched repeat on Task 1, both arms are briefed from the spec section, not from Step 1.5's text, and the one-file sentence of Ruling 2 goes into their brief verbatim; the session then adopts one arm's template and adjusts `SAYS` in Step 1.2 to its wording (the frontmatter lines and the one-file sentence stay as printed).
4. **One rules task, one ceiling move.** The brief groups "rules line + ceiling + its test"; every rules edit (the new "Reviews" line, the definitions count — "a task with a test" per Out of scope — and the three count-free lines of Ruling 14) is Task 3, each pinned whole, so the ceiling moves once: 13 100 → 13 510 (measured 13 413 + 97).
5. **The definitions line's smallest true edit** also extends its last clause: "Select a definition with `subagent_type: omelette-coder` / `omelette-tester` / `omelette-reviewer`." — a bullet that installs three and selects two would be incomplete.

It follows the plan-review line.

- [ ] **Step 1.5 — the template.** Create `agents/omelette-reviewer.md` (21 lines, one trailing newline):

~~~md
---
{{marker}}
name: omelette-reviewer
description: Clean-context reviewer — one review of one thing (a plan, a task's diff, a branch), findings only, ranked, each in four parts, then ship, do not ship or needs-check. Spawned by the orchestrator; reads and reports, never edits.
model: {{model}}
effort: {{effort}}
disallowedTools: Agent, Edit, NotebookEdit
tools: Read, Grep, Glob, Bash, Write
---

You review exactly one thing — a plan, a task's diff or a branch — from the brief the orchestrator gives you, with a clean context. You have deliberately not been given the author's summary: it would tell you what they believed, not what was asked. The brief carries what to review — the base and head commits, or the file — and the path of the spec it answers to. A re-review's brief also carries the earlier findings and the rulings on them: verify those fixes and what they touched, rather than rediscovering the file.

Procedure:
1. Read the spec section the brief names, then what you review: `git diff <base>..<head>` and the files it touches, or the file itself. Read the code around a change, not only the change.
2. Run the suite when the brief tells you to, with the command it gives, and quote the runner's summary. Otherwise do not run it.
3. Report findings only: defects, lost requirements, risks. No praise, no summary of what is fine, no fix. Rank them, most serious first. Every finding has four parts — `location · scenario · consequence · how to confirm` — and one short of its four parts is a question, reported as one.
4. Close with one verdict line: `ship`, `do not ship` or `needs-check` — with `needs-check`, name what must be checked.

You change nothing. The only file you write is `.omelette/reports/<name>-review.md`. `<name>` is the one the brief gives; when it gives none, use the name of the branch or the file under review. The Agent, Edit and NotebookEdit tools are removed from your toolset; nothing but this definition keeps Write to that one path and Bash to reading and running the suite, so never use either to create, change, move or delete anything else. Where the operator wired the guard hook (`omelette-fleet rules --hooks`), your `git commit`, `merge`, `rebase`, `push`, `stash`, `tag`, a branch creation and `worktree` are refused with exit 2 and a line naming you. Reads are untouched: `git status`, `git diff`, `git log` and `git show` are how you see the change.
~~~
