# 0.3.5 · P1 — The `[1m]` ceiling, and a settings file named by whichever reader tripped over it

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development (or superpowers:executing-plans). Steps use `- [ ]`. **The coder never commits.** Each task ends with a report to the orchestrating session, which reviews it and commits it on `feat/0.3.5`.

**Goal:** A session running a 1M model is measured against 1 000 000 tokens rather than 200 000. The guard and `doctor` both read the `[1m]` suffix off the model id — `ANTHROPIC_MODEL` first, then the `model` key of the user's own settings pair — as the fourth step of the ceiling chain, below `autoCompactWindow` and above Claude Code's default; they read it in the same order with the same acceptance, so the `handoff` line and the nudge cannot disagree. And `doctor`'s settings reads gain the list `readClientEnv` already had: any of its three readers that trips over a settings file names it, once, in one wording that no longer claims the loss was limited to `env` values.

**Architecture:** Two halves that must stay identical. In the self-contained hook script, `contextCeiling` gets one more source between `autoCompactWindow` and the 200 000 default: `modelWindow(env)`, built on a new `userSetting(env, key, accept)` helper that factors out the user-scope settings pair the `autoCompactWindow` scan already walks (same directory rule, same two files, same order, same bounded symlink-following read). In the CLI, `readClientSetting` grows the `unreadable: string[]` `readClientEnv` returns, `resolveContextWindow` makes the same two-step model lookup and carries every list up, `handoffReport` passes it to `cmdDoctor`, and `cmdDoctor` merges it with the two lists it already has. The one thing that is shared between the two halves is the grammar of the suffix, and it is shared the way `parseContextWindow` already is: `core/rules.mjs` exports `parseModelWindow` for the CLI, the guard carries a copy because it imports nothing, and both are pinned against the same table.

**Tech Stack:** Node ≥ 20, zero runtime dependencies, `node:` builtins only, plain ESM. `node --test` (`npm test`); the guard is exercised as a child process with a JSON event on stdin (`test/hooks-handoff.test.mjs`), the CLI as a child process with its own `HOME` and `OMELETTE_HOME` (`test/cli.test.mjs`, `test/doctor-timeouts.test.mjs`).

**Spec:** `docs/superpowers/specs/2026-09-09-0.3.5-design.md` — **§1 and §5, plus their lines in Docs and Testing, are this package.** Package map and fixed interfaces: `docs/superpowers/plans/2026-09-09-0.3.5-master.md` ("Shared interfaces" is binding — P2 and P3 are planned against those names in parallel).

**Facts this package rests on** (established in the spec and in the code as it stands — do not re-derive, do not contradict):

- The defect: an operator running a 1M model with `autoCompactWindow` unset had a 1M context measured against the 200 000 default, and the guard read the session as 144 % full. A default that is wrong for every 1M session is the thing being fixed.
- Claude Code writes the model it is running into the user's settings, suffix and all; `ANTHROPIC_MODEL` is the variable that names a model in a process's environment. A hook sees the environment and the settings files, never the client's argv — so `claude --model …[1m]` alone is invisible to it, and that is documented rather than guessed at.
- `readClientEnv` already returns `{ value, source, unreadable }` and already separates ENOENT (silence) from every other read failure (named). `readClientSetting` is its sibling for a file's own top-level keys and does not.
- `hookWiringAt` swallows *every* read failure as "absent" and names only a file that reads and does not parse into an object; `readClientEnv` stops at the first hit, so it names only the files ahead of the value. Neither is changed by this package.
- The rendered guard carries its `handoff` block as a JSON literal substituted by `renderHookFile`; `doctor` reads the block back out of the installed script. Unchanged here.

- **The guard still never fails a hook.** Everything added here exits 0 and prints nothing when it has nothing to say; the only non-zero exit in the script stays the `PreToolUse` refusal's exit 2. - **Project-scope settings are not read for either key.** The user scope's pair only (`$CLAUDE_CONFIG_DIR` or `~/.claude`), on both sides.

## Spec ambiguities resolved here (binding for the coder)

1. **What "the env `ANTHROPIC_MODEL`" means for `doctor`.** §1 names the environment as the first source. Resolved: the **process environment only**, on both sides — `env[MODEL_ENV]`, never `readClientEnv`. That is what the guard can see, and it is exactly how both sides already treat `CLAUDE_CODE_AUTO_COMPACT_WINDOW`. A model pinned through a settings `env` block reaches the hook's environment on its own if the client exports it; doctor does not go looking for one the guard would not see.
2. **Where the suffix has to sit.** "ends in `[1m]`" is read as: the value is a **string**, it is **trimmed**, and `/\[1m\]$/i` matches. `claude-opus-5[1m] (default)`, `claude-opus-5[1m]x` and `[1m]-opus` are therefore not windows — the suffix ends the id or it says nothing. A non-string `model` (number, boolean, array, object, null) is skipped on both sides: the guard tests `typeof raw === 'string'`, and `readClientSetting` already refuses anything but a string or a number before calling `accept`, and a number can never end in `[1m]`.
3. **`[1m]` alone as a value.** `"model": "[1m]"` is accepted as a 1M window. It is nonsense to write, it is harmless to honour, and the alternative is a second rule ("the suffix must follow at least one character") that neither half would test the same way. Documented in the test rather than in prose.
4. **Which files carry `model`.** The **user scope's pair only** — `settings.local.json` then `settings.json` under `$CLAUDE_CONFIG_DIR` when it is set to something, else `~/.claude` — the same files, in the same order, as `autoCompactWindow`. A project's `.claude/settings.json` is never read for either key, on either side, and both halves have a test that says so.
5. **Fall-through, not first-file-wins.** A file whose `model` is not a `[1m]` id does not end the scan: the next file is read. This is the rule `readClientSetting` already applies through `accept` and the guard already applies through its loop, and it is what makes `settings.local.json: "model": "claude-opus-5"` + `settings.json: "model": "claude-opus-5[1m]"` a 1M window on both sides.
6. **Two scans, not one.** `autoCompactWindow` is resolved across **both** files before `model` is looked at anywhere, because the spec fixes the precedence by source and not by file: a `model[1m]` in `settings.local.json` loses to an `autoCompactWindow` in `settings.json`. Both halves therefore walk the pair twice, which is also what `doctor`'s per-key `readClientSetting` does today.
7. **The shape `handoffReport` returns.** The master says it "passes `unreadable` up" without fixing a shape. Resolved: `{ line, unreadable } | null` — `null` keeps its meaning (no guard of ours carries a rendered block, so nothing was read and there is no line), and `handoff.enabled=false` returns a line with an empty list, because that branch resolves no ceiling and opens no file.
8. **What `unreadable` means for `readClientSetting`.** The same rule `readClientEnv` uses, clause for clause: ENOENT is silence; any other read failure, or a parse that is not a plain object, is named and the scan continues. The list holds only the files **this** scan opened — the ones ahead of the value in the client's own order — which is why `cmdDoctor` merges rather than replaces.
9. **Where the merged list is printed.** Unchanged: after the `mcp timeout` block, one line per distinct path, in `mergeUnreadable`'s first-seen order with `walls.unreadable` first. The handoff list is merged **after** the walls', so an operator whose broken file is seen by both readers sees it in the client's own precedence order, exactly as today.
10. **The wording change is for every source.** §5 says "for all sources", so the line no longer says `env values in it`. Three existing tests pin the old text and are updated in the same task as the code; `CHANGELOG.md`'s 0.3.4 entry quotes the old wording and is **not** rewritten — it is a record of what that release printed.

 * thing. `unreadable` holds the files THIS scan opened — the ones ahead of the
 * value in the client's own order — and doctor merges the list with the ones

 * @param {{global?:boolean, cwd?:string, env?:object, accept?:Function}} o
 *   `accept` turns the raw string into the value worth having, or null when
 *   this file's is not one.
 * @returns {{value: any, source: string|null, unreadable: string[]}}

function readClientSetting(name, { global = true, cwd = process.cwd(), env = process.env, accept = (v) => v } = {}) {

    // file this user cannot open — means the contents are there and lost.

    if (value === null || value === undefined) continue; // not a value: the next file may hold one

  }
