## Why

Two facts from `docs/MEASUREMENTS.md`: sixteen planners cost 4.6 M tokens, ~285 k each, and most of that was reading `core/` again; and the rendered rules file is 14 k characters of prose loaded at every session start. A long context costs on every turn and reads worse — the model finds less in more — so *cheaper* and *better* pull the same way here: hand each agent what it needs, pointed at, and nothing it must rediscover.

What stays as it is, because the numbers said so: the plan format keeps full code (writing the plan is under 10 % of a planner's cost; a plan with code is reviewable before anything is built), the coder/tester report already goes to a file with a short reply, and the plan already goes to a file the coder follows.

## P0 — measure first

Two throwaway measurements in the scratchpad; only their rows are committed.

- **Where a sub-agent's context goes.** A script reads one planner's and one coder's transcript from 1.1.0 and splits their input by source: `Read` results, `Bash` output, `Grep`/`Glob` output, the brief and the conversation itself — characters per source, and the ten files read most often with how many times each was read. Output: one table in MEASUREMENTS, "Where a planner's context goes". This decides whether P2's map is aimed at the right thing; if reading is not the bulk, the spec is amended before P2.
- **Who crosses 200 k, and doing what.** From the same transcripts (every sub-agent of 0.3.3 → 1.1.0 whose count is available): how many crossed 200 k tokens, at which turn, and what the turns past it were — new reading, re-reading, or writing. Output: one row. It decides whether the shipped definitions drop the `[1m]` window (a `model:` value, config not code) in 1.2.0: if the tail past 200 k is mostly re-reading, they do; if it is work, they keep it and the row says why.
- **N0 spike.** A one-file function-hooks mod compares `$.session.usage().context.percent` with the guard's transcript-based estimate at three points of a session. Output: one row, the largest gap seen. Nothing enters the package; if the API is not available on this install, the row says so.

## P1 — the rules file as a map

`rules/omelette-fleet.md` (the template; the rendered copy is what every session loads) is cut to the rules and nothing that explains a mechanism.

- **Ceiling: 8 000 characters rendered** (from 14 214), pinned by a test. Every rule that binds the session stays; every sentence that describes *how a hook works* moves out.
- **What moves, and where.** The three hook-mechanics bullets of "Ledger and handoff" (PreCompact/SessionStart print, PostCompact summary, the threshold reminder and Stop gate) become one bullet — *what the hooks do for the ledger, and that the discipline is still the file* — and their full text becomes a section `## The handoff hooks` in `docs/CONFIG.md` (the keys `handoff.*` are documented there already). The small-change exception and lane keep their rules in two bullets; the worked reasoning goes to ORCHESTRATION "The operating model".
- **Shape.** Same sections, one line per rule where a rule fits a line; the routing table stays a table. No `| Question | Where |` map: this file is read by a model, not browsed, and a map of links would be tokens that point elsewhere.
- **Unchanged.** The two bullets pinned by `test/evidence-pointers.test.mjs`; the short-contract mechanism in `core/rules.mjs` (the contract still says "the rules already say everything").

## P2 — briefing from the map

Rules text and ORCHESTRATION; no code, no new agent definition. Three rules:

- **A planner starts from the map.** The brief for a planner carries the scout map's path and the package's section of the spec, and says: read the map first, open only what the map does not cover, and record in the plan's header which map lines it relied on. The operator's own `planner` definition (not shipped) gets the same sentence.
- **A coder gets its task, not the release.** The brief carries the task's section of the plan and the pointers it needs, not the whole spec; the spec's path is there for the cases the plan did not settle.
- **The session reviews a plan by its header, task list and Self-Review.** The full plan file goes to a unit (`codex_code_review` or `grok_code_review`, spec path and plan path, four-part findings); the session opens the pointers of the findings, not the file. The ledger records the findings and rulings as for any review.

ORCHESTRATION "Evidence with pointers" gains the three as a short list under a new heading `### What each agent is handed`.

## P3 — this release is the experiment

1.2.0 has two build packages (P1, P2) and is planned from a scout map — the first release that is. That gives the "after" row MEASUREMENTS owes, and one comparison on top:

- **P1 is planned by a fresh `planner` briefed with the map** (the P2 rule, applied one release early).
- **P2 is planned by a `fork` of the session taken right after a compaction**, when the session's context holds the spec, the map and little else. The fork inherits that context at cache price and writes the same kind of plan.
- Both are measured with `scripts/agent-usage.mjs` (tokens, tool uses, minutes) and read with the same review. Two rows in MEASUREMENTS "Planning cost": *after, fresh planner with map* and *after, fork*. Whichever is cheaper at equal review yield becomes the sentence in the rules; the other stays a measured alternative.

If the fork's plan is materially worse on review, that is the result, and the rule says "fresh planner with map".

## P4 — a task lead between the session and the coder

The session's context is the most expensive place to keep anything: whatever lands there is re-read from cache on every later turn until the next compaction. Today every task's diff, coder report and tester output land there, 10–30 k tokens a task. P4 moves the task-level loop out.

- **The role.** A *task lead* — the operator's private definition for now (`~/.claude/agents/omelette-lead.md`; the session's model and effort, `tools` restricted to `Agent(omelette-coder, omelette-tester)` plus read and shell) — receives one task: the task's section of the plan, the spec path, the map path, the rules, and the ledger's rulings so far. It spawns the coder, then the tester (clean context, spec plus `git diff`), arbitrates test-vs-spec, continues the same coder for up to three rounds, and returns **one** report in the five-section shape: status, findings as pointer lines, every ruling it made and why, what it did not do. It never commits (the definition says so, and the guard learns its role name).
- **The session** briefs leads, runs `check` on each report, opens three of its pointers itself, copies the lead's rulings into the ledger as `candidate` and marks them `verified` or overrules, commits the task. The coder's and tester's short replies no longer reach the session at all.
- **What the rules keep.** "Arbitration belongs to the orchestrator" becomes: the lead arbitrates inside the task and reports the ruling; the session confirms or overrules in the ledger. The clean-context tester, the ≤ 3 rounds, the escalation to the operator, and "nothing a delegate says lands unverified" are unchanged — the lead's report is a delegate's report.
- **Experiment.** Every task of P1 and P2 goes through a lead. Measured: the session's context growth per task — the bytes of tool results and agent replies that entered the session between a task's brief and its commit, from the session transcript — against the same figure for 1.1.0's tasks (same transcript file). And the lead's own cost per task from `scripts/agent-usage.mjs`. Both become one row in MEASUREMENTS.
- **Ship or not.** If the session's growth per task falls by half or more at equal review yield, `omelette-lead` ships as a third definition, with its rules text, in 1.3.0. If not, the row says so and the private definition stays an option.

P2's "a coder gets its task, not the release" still holds with a lead in the middle: the lead hands the coder the task section, not the plan.

## Out of scope

- The plan format (full code stays). The report shape (unchanged since 1.1.0).
- The compaction threshold (`handoff.threshold`); lowering it is a later experiment once N0 says how good the guard's estimate is.
- `/omelette-test` under auto permission mode, the Windows harness, `check`'s memory peak: still the post-1.1 backlog.
- A shipped `planner` definition: the operator's stays private for now. A shipped `omelette-lead` waits for P4's row (1.3.0 at the earliest).
- Security auditing — a security agent, attack-class briefs for the pre-release Codex audit, a comparison of audit harnesses on this repository. Its own spec, after the research the operator asked for on 2026-09-22; nothing of it in 1.2.0.
