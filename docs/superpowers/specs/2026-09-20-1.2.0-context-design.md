## Why

Two facts from `docs/MEASUREMENTS.md`: sixteen planners cost 4.6 M tokens, ~285 k each, and most of that was reading `core/` again; and the rendered rules file is 14 k characters of prose loaded at every session start. A long context costs on every turn and reads worse — the model finds less in more — so *cheaper* and *better* pull the same way here: hand each agent what it needs, pointed at, and nothing it must rediscover.

What stays as it is, because the numbers said so: the plan format keeps full code (writing the plan is under 10 % of a planner's cost; a plan with code is reviewable before anything is built), the coder/tester report already goes to a file with a short reply, and the plan already goes to a file the coder follows.

## P0 — measure first

Throwaway measurements in the scratchpad; only their rows are committed.

**The source.** Claude Code keeps every sub-agent's own transcript (`<project>/<session>/subagents/agent-<id>.jsonl`, 76 on this machine for the 1.1.0 session) and every assistant message in it carries `usage`: `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`. Their sum is the context that request ran with; summed over requests with the documented multipliers (reads 0.1×, five-minute writes 1.25×) it is what the agent cost. This is the **measurement contract** for the release: per-request usage from transcripts, never a notification aggregate. (MEASUREMENTS "Sub-agents by role" stays as taken; its "how" paragraph gains the pointer to the better source.)

- **Where a sub-agent's context goes.** Two planners' and two coders' transcripts from 1.1.0: what each turn introduced, by source — `Read` results, `Bash` output that reads a file (`cat`, `sed -n`, `head`, `git show`) counted as reading, other `Bash`, `Grep`/`Glob`, the brief, the model's own output — and the ten files read most, with the count and the overlap between reads. Stated limit: this is the logged text each turn *added*; the resident context per request is the `usage` sum, reported beside it. Output: one table, "Where a planner's context goes". If new reading is not the largest source, P2 is amended before it is built.
- **Who crosses 200 k, and doing what.** From every sub-agent transcript of the 1.1.0 session: the first request whose `usage` sum passed 200 k, and for the turns after it, the same by-source split. Output: one row. It *informs* the `[1m]` question; it does not decide it — a tail of re-reading may be recovery after a compaction. The shipped definitions keep `[1m]` in 1.2.0; a matched pair (one task under `[1m]`, the same task under 200 k, same brief and review) is a 1.3.0 experiment if the row makes it worth running.
- **N0 spike.** A one-file function-hooks mod logs, at each of three live points of a session (early, near `handoff.threshold`, right after a compaction), `$.session.usage().context.percent` together with the guard's estimate, the guard's numerator and the window it resolved — same request, both values. Output: one row, the largest gap and where. Nothing enters the package; if the API is not available on this install, the row says so.

## P1 — the rules file as a map

`rules/omelette-fleet.md` (the template; the rendered copy is what every session loads) is cut to the rules and nothing that explains a mechanism.

- **Ceiling: 8 000 characters rendered** (from 14 214), pinned by a test. Every rule that binds the session stays; every sentence that describes *how a hook works* moves out. The cut is made sentence by sentence, and the hook bullets hold obligations dressed as explanation that must keep a line of their own: *after a compaction, re-read the ledger before doing anything else*; *the handoff block is still yours to write*; *handoffs at every natural pause, the hook is the net under it*; *a ledger kept in another repository gets neither the stamp nor the print*; *a manual `/compact` below the threshold gets no reminder*. The test pins those five by substring.
- **What moves, and where.** The three hook-mechanics bullets of "Ledger and handoff" (PreCompact/SessionStart print, PostCompact summary, the threshold reminder and Stop gate) become one bullet — *what the hooks do for the ledger, and that the discipline is still the file* — and their full text becomes a section `## The handoff hooks` in `docs/CONFIG.md` (the keys `handoff.*` are documented there already). The small-change exception and lane keep their rules in two bullets; the worked reasoning goes to ORCHESTRATION "The operating model".
- **Shape.** Same sections, one line per rule where a rule fits a line; the routing table stays a table. No `| Question | Where |` map: this file is read by a model, not browsed, and a map of links would be tokens that point elsewhere.
- **Unchanged.** The two bullets pinned by `test/evidence-pointers.test.mjs`; the short-contract mechanism in `core/rules.mjs` (the contract still says "the rules already say everything").

## P2 — briefing from the map

Rules text and ORCHESTRATION; no code, no new agent definition. Three rules:

- **A planner starts from the map.** The brief for a planner carries the scout map's path and the package's section of the spec, and says: read the map first; open three of its pointers yourself before relying on it, and if one is false treat the whole map as unverified (the 1.1.0 rule for every map consumer — unchanged); then open only what the map does not cover; record in the plan's header which map lines it relied on and which it re-took. The operator's own `planner` definition (not shipped) gets the same sentence.
- **A coder gets its task, not the release.** The brief carries the task's section of the plan and the pointers it needs, not the whole spec; the spec's path is there for the cases the plan did not settle.
- **The session reviews a plan by its header, task list and Self-Review.** The full plan file goes to a unit (`codex_code_review` or `grok_code_review`, spec path and plan path, four-part findings); the session opens the pointers of the findings, not the file. The ledger records the findings and rulings as for any review.

ORCHESTRATION "Evidence with pointers" gains the three as a short list under a new heading `### What each agent is handed`.

## P3 — this release is the experiment

1.2.0 has two build packages (P1, P2) and is planned from a scout map — the first release that is. That gives the "after" row MEASUREMENTS owes, and one comparison on top, on **one frozen package** so the two methods plan the same thing:

- **P1 is planned twice, independently**: by a fresh `planner` briefed with the map (the P2 rule, applied one release early), and by a `fork` of the session. Same spec section, same map, same model and effort, same tools.
- **The fork is defined**, so it can be repeated: it is taken from a session whose context since its last compaction is exactly the SessionStart handoff print, one read of the spec and one read of the map — nothing else — and the ledger records the Claude Code version and the fork's first-request `usage` (how much came from cache).
- **Both plans go to the same unit review, blinded**: the reviewer gets the two files under neutral names and the spec, and a fixed rubric — spec coverage, task atomicity, interface consistency, placeholders — with four-part findings. The session builds P1 from the plan that reviewed better; P2 is planned by that method alone.
- Cost per plan from each planner's transcript (the P0 contract). Two rows in "Planning cost": *after, fresh planner with map* and *after, fork*, each with its review result. The rules gain the sentence only if one method is both cheaper and not worse on the rubric; otherwise both stay measured alternatives and the rule stays "fresh planner with map".

## P4 — a task lead between the session and the coder

Whatever lands in the session's context is read again, from cache, on every later *session request* until the next compaction — not while the session waits, but on each of the hundreds of requests a release takes. Today every task's diff, coder report and tester output land there, 10–30 k tokens a task. P4 moves the task-level loop out. Whether that is cheaper *in total* — the lead reads the same material once at full price and adds its own turns — is the question the experiment answers, not a premise.

- **The role.** A *task lead* — the operator's private definition for now (`~/.claude/agents/omelette-lead.md`; the session's model and effort, `tools` restricted to `Agent(omelette-coder, omelette-tester)` plus read and shell) — receives one task: the task's section of the plan, the spec path, the map path, the rules, and the ledger's rulings so far. It spawns the coder, then the tester (clean context, spec plus `git diff`), continues the same coder for up to three rounds, and returns **one** report. It never commits (the definition says so, and the guard learns its role name).
- **What the lead may rule on, and what it may not.** The lead arbitrates *implementation* disputes — a failing test whose answer is in the spec or the task section — and records each ruling with the spec line it rests on. A dispute the spec does not answer, one that needs another task's constraint, or one that would change what the release does is not the lead's: it stops, no corrective edit is made, and the report carries the question under `## OPEN QUESTIONS`. "Arbitration belongs to the orchestrator" thus keeps its meaning at the release level; the session confirms or overrules every lead ruling in the ledger.
- **The report** is the five-section shape with two things it may not compress: `## TEST RESULTS` carries the tester's raw runner summary verbatim, every failure in full, and `## DIFF` carries `git diff --stat` plus the paths of the coder's and tester's own report files. The session's acceptance is unchanged from any delegate's: `check` on the report, three pointers opened by hand, the coder's and tester's reports available on disk — and the session runs the full suite itself before it commits, as it does today. A lead's summary that omits a failure is caught there, not trusted past it.
- **The session** briefs leads, accepts as above, copies the lead's rulings into the ledger as `candidate` and marks them `verified` or overrules, commits the task. The coder's and tester's short replies no longer reach the session at all. The clean-context tester, the ≤ 3 rounds, the escalation to the operator, and "nothing a delegate says lands unverified" are unchanged.
- **Experiment, matched.** P1 is built through leads; the tasks of P2 are built directly by the session, as in 1.1.0. Per task, from the P0 contract: the session's `usage` sum per request over the task's span (its resident context), the total across every agent that touched the task (session, lead, coder, tester — input, cache writes and reads at the documented multipliers), wall-clock time, and defects the release reviews later found in that task. One table in MEASUREMENTS.
- **Ship or not.** `omelette-lead` ships as a third definition, with its rules text, in 1.3.0 only if the lead's tasks are not more expensive in total, the session's resident context per request grew less, and the reviews found no more defects in them. Otherwise the table says so and the private definition stays an option.

P2's "a coder gets its task, not the release" still holds with a lead in the middle: the lead hands the coder the task section, not the plan.

## Out of scope

- The plan format (full code stays). The report shape (unchanged since 1.1.0).
- The compaction threshold (`handoff.threshold`); lowering it is a later experiment once N0 says how good the guard's estimate is.
- `/omelette-test` under auto permission mode, the Windows harness, `check`'s memory peak: still the post-1.1 backlog.
- A shipped `planner` definition: the operator's stays private for now. A shipped `omelette-lead` waits for P4's row (1.3.0 at the earliest).
- Security auditing — a security agent, attack-class briefs for the pre-release Codex audit, a comparison of audit harnesses on this repository. Its own spec, after the research the operator asked for on 2026-09-22; nothing of it in 1.2.0.
