## Why

Read 2026-11-03 across the 1.7.3 ledger, the 2026-10-20 audit, backlog §2c and §3:

- **The guard refuses the wrong thing and lets the right thing through.** A coder's `cat > core/ledger.mjs <<'EOF'` was refused because the file's body holds the word `commit` (ledger 1.7.3: coders were told to use Write). The same guard lets `"git" commit`, `git "commit"` and `g'it' commit` through (audit finding 6, low, reproduced by Codex). A reviewer may write anywhere: its "only the report" rule is its definition's text and the session's `git status` afterwards.
- **A curated file can be overwritten by a summary.** The ledger, the register and the backlog are appended to by rule, and nothing refuses a Write that replaces one with a shorter version, which is what a session does after a compaction when it "tidies up" (claude-code-sdlc shipped a shrink guard for exactly this; the memory talk's rule is a content-hash precondition in the harness, not the model).
- **A coder's DIFF section is its own account.** Nothing compares the files a coder or tester says it touched with the files its loop actually wrote; the transcript knows (`agent_transcript_path` on `SubagentStop`).
- **The handoff is free prose and dies with the hook's reach.** "Where the work stands · open findings · agents in flight · next action" is a convention; what was tried and failed is lost between compactions (backlog p13); the stamp says only `trigger: manual`; after a `/clear` the print arrives as hook output, which a mod cannot deliver as a context block and a headless session may never see.
- **Reviews rediscover and over-fix.** A re-review after a multi-commit fix round reads `HEAD~1`, not the dispatch's base; a reviewer that declines to judge something says nothing; every finding, pre-existing or nit, becomes a fix round (codex-plugin-cc's adversarial brief, superpowers' reviewer rules, the article's 59 % repeat-finding figure in backlog §3).

## The model

- **A guarded role** is one of the four shipped names, matched whole: `omelette-coder`, `omelette-coder-medium`, `omelette-tester`, `omelette-reviewer`. Unchanged.
- **A curated file** is one the operating model asks to be appended to, never rewritten: `.omelette/ledger-*.md`, `.omelette/backlog.md`, `.omelette/decisions.md` and the file its `register:` line names (`docs/DECISIONS.md` here). The list lives in the guard script (`CURATED`), the register redirect read as `core/ledger.mjs` reads it.
- **A delivery** is the path by which the guard's answer reaches the engine: the **settings hook** (`PreToolUse` → `hooks/omelette-guard.mjs`, exit 2 + stderr, as today) or the **mod** (`tool.call` in `mods/omelette-fleet`, which runs the same rendered script and answers `{ deny }`). One script, two deliveries; the script's test table is the contract for both.
- **The script the mod runs is the rendered one** — `<project>/.claude/hooks/omelette-guard.mjs`, else `~/.claude/hooks/omelette-guard.mjs` — never the template in the package (its first line is `{{marker}}`). No rendered copy: the mod guards nothing and says so once in the pane and the debug log (`guard v2 needs omelette-fleet rules --hooks`).

## Guard v2: the script

All in `hooks/omelette-guard.mjs`, each a row group in `test/hooks.test.mjs`, each named in SECURITY "The guard hook":

1. **A heredoc body is not a command.** `tokenize` recognises `<<WORD`, `<<-WORD`, `<<'WORD'`, `<<"WORD"` and skips the lines up to the terminator (`WORD` alone on a line, leading tabs allowed after `<<-`) as text: no tokens, no git words. One exception, because the shell expands it: inside an **unquoted** heredoc, `$(…)` and backquotes are substitutions and are handed back as spans exactly as they are outside one. A heredoc with no terminator runs to the command's end. `<<<` (a here-string) stays a redirection target as today. Rows: a `cat > file <<'EOF'` whose body holds `git commit` passes; `<<EOF` with `$(git commit)` in the body is refused; `<<'EOF'` with the same is text; two heredocs on one line (`cmd <<A <<B`); a terminator with trailing spaces does not terminate.
2. **Quotes do not hide the git word or the subcommand** (audit 6). `isGitWord` and `subcommandAt` compare `unquote(text)`, so `"git" commit`, `git "commit"`, `g'it' commit` and `git co"mm"it` are the commit they are. The rule for action flags stays as it is (`rebaseWrites`: a quoted recovery flag is data) — it protects the other direction and is documented in the script.
3. **A truncating Bash write to a curated file is refused** — for every `agent_type`, the main thread included. A redirection `>`, `>|`, `<>` or `&>` whose target resolves to a curated file; `tee` without `-a`/`--append` to one; `sed -i`, `perl -i`, `sort -o`, `mv`/`cp` **onto** one; `truncate`, `: >`, `rm` of one. Appends (`>>`, `tee -a`), reads and `git mv` pass. Target paths are compared after `unquote` and `path.resolve` against the cwd, symlinks not followed (the file's own name is what the rule protects). The refusal names the file and the rule: `<file> is appended to, never rewritten; to replace it on purpose, move it first`. Why Bash here: Claude Code's own Edit, and its Write on a file the session has Read, refuse a file that changed since that read (P3, 2026-11-03, 2.1.316: `File has been modified since read … Read it again`), so the harness holds the content precondition there; Bash was the open path, and a Write to a file never Read is the other (rule 4).
4. **A Write to a curated file is an append or it is refused** — every `agent_type`. P3 showed that Write on a file the session never Read overwrites it without a check, and after a `/clear` a session knows the ledger from the hook's print, not from a Read: the "rewrite with a summary" failure runs through exactly that gap. So `PreToolUse` on `Write` whose `file_path` is curated: allowed when the file does not exist, or when `content` starts with the file's current bytes (an append, whatever the tool); refused otherwise with `<file> is appended to, never rewritten: Edit for an in-place change (the harness checks it has not moved since your read), append otherwise; to replace it on purpose, move it first`. No size heuristic (the 40 % shrink guard of backlog p9 is superseded by this exact rule, my call). `Edit` is not covered: the harness already refuses a stale one.
5. **The reviewer's write fence.** `PreToolUse` on `Write`, `Edit`, `NotebookEdit` with `agent_type: omelette-reviewer`: refused unless `file_path` resolves (symlinks followed, `realpath`) under `<cwd>/.omelette/reports/` and ends in `-review.md`. Refusal: `omelette-reviewer writes nothing but .omelette/reports/<name>-review.md`. The settings snippet's `PreToolUse` matcher widens from `Bash` to `Bash|Write|Edit|NotebookEdit`; `doctor` reads the matcher as it does today and names a snippet still on `Bash` alone (`guard: Write/Edit not wired — re-merge the PreToolUse group`).
6. **The touched record** (p7). `SubagentStop` for a guarded role: the script streams `agent_transcript_path` (JSONL, 16 MB cap, 2 s, fail-soft), collects every `Write`/`Edit`/`NotebookEdit` `file_path` and every Bash command the guard's own tokenizer reads as a write to a path (the rules of 3), and writes `.omelette/reports/touched-<agent_type>-<agent_id first 8>.md`: `# touched — <agent_type> <agent_id>`, `transcript: <path>`, one line per path, then `tool calls: <n> (<tool>: <count>, …)`. **The file is the contract**: the rules text tells the session to open `touched-<role>-<id>.md` when a coder or tester reports, and compare it with the report's `## DIFF` by eye in 1.8.0; a `check`-style comparison is 1.9.0's "Reports checked" gate. The hook answers no `additionalContext` (P6: it would land in the stopped agent's transcript, which nobody reads); the mod's `classic.SubagentStop` shows one line in the pane, `touched: <path> — <n> files`. The hook snippet gains a `SubagentStop` group (no matcher). Nothing is refused here; a transcript that cannot be read is one stderr line.
7. **The stamp carries facts** (p32). PreCompact's line becomes `## Compaction <ISO> (trigger: <manual|auto|unknown>) — branch <name> · HEAD <short> · <n> dirty files — re-read this ledger before continuing`, from `git rev-parse --abbrev-ref HEAD`, `git rev-parse --short HEAD` and `git status --porcelain` (line count), each 2 s, `--no-optional-locks`, absolute PATH entries only, `unknown` on any failure; each value is checked against `^[\w./-]{1,64}$` before it lands in a heading (the trigger rule already there). Facts, not a summary: within the binding "stamps, sweeps, prints".

Unchanged: the git refusal table, the names matched whole, exit 0 on everything that is not a refusal, the stdin bounds, the sweep and the print.

## Guard v2: the mod delivery

In `mods/omelette-fleet/hooks/register.tsx`, beside the pane's bookkeeping hooks, fail-open like every hook there (`.catch(($, e, next) => next(e))`):

- **`tool.call`, tool `Bash` | `Write` | `Edit` | `NotebookEdit`, in a loop whose agent is a guarded role** (the pane already maps `agentId` → role from `agent.spawn`): build the PreToolUse event the script reads (`hook_event_name`, `tool_name`, `tool_input`, `agent_type`, `cwd`) and run the rendered script with `$.process.run([node, script], { stdin, timeoutMs: 2000 })`. Exit 2 → `{ deny: stderr.trim() }`, no `next`. Any other exit, a timeout or a missing script → `next(e)`. The main thread's calls go to the script too, for rules 3 and 4 only (the role gate is the script's, not the mod's: the mod passes `agent_type` when it knows one and nothing otherwise, exactly as Claude Code does).
- **Who answers when both are wired:** the mod, because it runs first and a deny never reaches the settings hook; a call both would refuse is refused once, with the same text. The mod does not read the settings to decide whether to run: one code path, measured, and the settings hook is what a session without the mod (or under `claude -p`, probe P1) gets.
- **`node` is the engine's own** (`process.execPath` is not available to a module; the mod runs `node` from PATH, absolute entries only, as the CLI does) — probe P4 settles whether the engine exposes its executable; if not, `node` from PATH and a notice when it is not found.
- **Cost:** one child process per guarded tool call. Measured as the 1.7.0 pane was ([MEASUREMENTS, "The fleet pane's cost per tool call"](../../MEASUREMENTS.md#the-fleet-panes-cost-per-tool-call)): the program's stop line is 150 ms per call on average. Expected: 40–80 ms on this machine (node startup plus a 1 400-line parse); above the line, the task reduces the script's startup (lazy imports of `core/ledger.mjs` are already lazy) before anything else is cut.
- **The pane** shows a refusal as it shows a call: the row's subject gets `refused` for one tick; the daily count of refusals by delivery is kept in `$.state` for the measurement.
- `doctor` gains one line: `guard: settings hook wired (PreToolUse Bash|Write|Edit|NotebookEdit, SubagentStop) · mod omelette-fleet enabled, installed 1.8.0 — the mod answers first`, or the half that holds. What `doctor` can see (my call: it never says "loaded" — the CLI cannot see what a session loaded): `enabledPlugins` in the settings files for `omelette-fleet@…`, and `~/.claude/plugins/installed_plugins.json` for the install path and version. An installed version behind the package's is named as such: `mod omelette-fleet enabled, installed 1.7.3 (package 1.8.0): stale — reinstall, or the second delivery is absent` — the desktop app loads the cached copy by version, the CLI the folder in place (ledger 1.7.1), and a stale cache carries no guard. The pane itself says whether its guard hook found a rendered script, which is the live answer.

## Pins and the effort notice

- **Model pins.** `agent.spawn` for the four roles: the mod reads each role's definition file once per session (`.claude/agents/<name>.md` in the project, else `~/.claude/agents/`, the `model:` and `effort:` lines of the frontmatter) and, when `e.model` is set and does not name the definition's id, rewrites it: `next({ ...e, model: <id> })`, a toast `pinned <role> to <id>` and a pane note. An alias names the id when the mod's alias map says so — `opus → claude-opus-5-5`, `sonnet → claude-sonnet-5-5`, `haiku → claude-haiku-5-5`, `fable → claude-fable-5-1`, kept by hand beside the catalogs and bumped with them (my call: an alias of the same family is the definition's model, not a correction, so the count measures real overrides); an alias off the map, or any other id, is a pin. The `Agent` tool's `model` override is thereby refused for the four roles by construction; the operator changes a role's model with `omelette-fleet set … && rules --agents`, as today. `effort` is not in `agent.spawn`'s input; the rules text already says the definition decides it.
- **The effort flag.** `turn.step` carries `e.effort` and `e.agentId`; when a guarded role's step reports an effort other than its definition's, once per agent: a pane flag on the row and one toast `effort <x> on <role> (definition says <y>)`. Nothing is changed: the definition's `effort:` is honoured by the engine (CLAUDE_CODE_EFFORT_LEVEL beats it); the flag makes the exception visible.
- **`CLAUDE_CODE_EFFORT_LEVEL`.** Read at `session.start` (probe P5 settles how a module reads the environment; if it cannot, the settings hook's `SessionStart` prints the notice instead, which it can — `process.env`). Set → one notice naming the rule: `CLAUDE_CODE_EFFORT_LEVEL=<v> is set: it overrides every agent definition's effort (rules, "Spawning sub-agents")`.

## The handoff

- **Named fields.** A `## Handoff (<date> — <title>)` block holds, in order, each a bolded label on its own line: `State` (branch, HEAD, tree, what is done), `Open findings` (unruled findings, by pointer), `Agents in flight` (agent ids and what they hold), `Gotchas` (p31's critical context: what will bite the next reader — three lines at most), `Tried` (the `tried:` lines of this plan still worth knowing, see below), `Next action` (one sentence, then the step after it). The hook prints the block as it is; the fields are the rules text's, so a reader after a compaction finds each answer at its label. A block with fewer fields still prints: the print never validates.
- **`tried:` lines** (p13), the ledger's vocabulary for a dead end: `- <date> tried: <approach> — failed | succeeded — <why, one clause>`. Written when an approach is abandoned or confirmed, so a session after a compaction does not walk the same path; the handoff's `Tried` field repeats the ones still open. The sweep ignores them (they are plan-local).
- **The stamp** is 7 above.
- **Delivery by the mod.** `prompt.context`: the mod runs the rendered guard with a `SessionStart` event of `source: clear` (`$.process.run`, 5 s, the script's own bounds and reader) and appends one block `{ name: 'omeletteHandoff', text }` carrying the script's stdout — the open ledgers' last handoffs, the register's tail, the backlog's first table, under the 12 KB cap. `prompt.context` fires once per conversation — at startup and resume as well as after a compaction and a `/clear` (its declaration; probe P2 confirms the re-read live) — and the block is delivered **every time**, startup included (my call: a fresh session has no earlier context to lean on either, the cost is at most 12 KB once, and the settings hook stays silent on startup as 1.7.3 decided, so nothing is doubled there). No state, no hook on the compaction itself. Empty stdout → no block.
- **One copy, not two.** When both deliveries are wired the settings hook's `SessionStart` print would arrive as `additionalContext` beside the block on `compact` and `clear`. The mod hooks `classic.SessionStart` for those two sources, calls `next(e)`, and returns the result with the guard's `additionalContext` removed — keyed on the mod being loaded at all (its `prompt.context` hook is registered unconditionally), not on an order between the two events (my call: no state to get wrong). Probe P2 confirms that a module sees and may rewrite the settings hook's answer; if it cannot, both copies arrive in 1.8.0 and `doctor` says which group to drop. The stamp, the sweep and the refusals stay with the settings hook: the mod delivers, it does not replace.
- **The compaction skip, off by default.** `userConfig.handoffGate` (boolean, default `false`, title "Refuse a compaction without a fresh handoff"). On: `session.compact` with `trigger` `manual` or `auto`, no `agentId`, when the newest open ledger's last `## Handoff` heading is not fresh → `{ skip: 'no handoff in the last 30 minutes: write one, then compact again' }` once; the second attempt within 10 minutes passes (`$.state`). **Fresh** (my call, no vocabulary change for old ledgers): the heading's date is today and, when it carries a time, `## Handoff (2026-11-03 14:05 — title)`, that time is within 30 minutes; a heading with a date only counts as fresh for its whole day. The rules text says a block written under the gate carries the time; the print regex accepts both forms; the file's mtime is not used (the stamp and a `tried:` line would refresh it). Never on `precompute` or `plugin`, never for a sub-agent's own compaction. Measured, not recommended: the program's row counts compactions with and without a fresh handoff.

## The review brief

Text changes, in the templates (`agents/*.md`), the rules template and ORCHESTRATION "Reviews"; every line is one the harvest ruled on (backlog §2c, the row named):

- **`omelette-reviewer`** gets p1's stance in one paragraph: read to break confidence, not to confirm; list the attack surface of the change before the findings (inputs, states, callers, the files beside the ones changed); a finding earns its place when it answers four questions (what input or state, what happens, who is hurt, how to confirm) — one strong finding over three weak; mark an inference as an inference. Each finding carries, after its four parts: `confidence: 0–1`, `important | nit`, `introduced | pre-existing`, and `seen: <n>` when the same class recurs on the branch (the memory talk's "example plus prevalence": the pointer is the example, the count says whether it is a pattern) — the class named so the fix covers every instance. A new section before the verdict, `## DECLINED TO JUDGE` (p23): what the reviewer saw and chose not to rule on, one line each, `none` when none; the session rules on each. One rule line: the spec's silence is not permission (p24) — a finding is judged by its effect on the operator, not by whether the spec names the trigger. The verdict words stay (`ship`, `do not ship`, `needs-check`).
- **`omelette-coder`** gets p29: report every red test seen in the full run, its own or not, as a pointer line; and the FINDINGS section is bounded at about ten lines, details in the report file (backlog §3).
- **Rules template and ORCHESTRATION**: (p22) the dispatch's BASE is written in the ledger line before a coder starts, and a re-review's diff is `base..HEAD`, never `HEAD~1`; (p25) a review brief never pre-judges — no "do not flag X", no "nothing above minor"; (p26) a coder fixes `important` + `introduced` only; `nit` and `pre-existing` go to the ledger as one line each and to the release's whole-branch review; the final review of a release gets one fix dispatch for all its findings, not one per finding; the `review yield:` line splits rejected into `wrong / intentional / didn't matter`; (p27) a plan's header carries `Global constraints` (the spec's values, verbatim) and `Review focus` (the input classes no task's tests cover, each pointing at the task that should), and a task lists `Consumes` / `Produces` (the names it reads and the ones it defines) — one rules line, the full text in ORCHESTRATION "What each agent is handed".
- The rules file's size test rises once more (today 16 188 of 16 400): the plan's task measures and sets the new cap with the usual comment line.

## Probes before the first task

One task, first, by the session (a half day): live on the build of the day, each answer a ledger line and a line in the spec's plan header.

- **P1** (p10): do settings hooks fire under `claude -p`? Do a plugin's hooks? A `PreToolUse` that writes a marker file, run both ways. The answer goes to SECURITY "containment, not a boundary" either way. **Answered 2026-11-03 on 2.1.316:** all three fire headless — the project settings hook, a plugin's classic hook, a hooks module — in a cwd never trusted interactively; the sdlc claim does not hold here. SECURITY says so with the build, re-probed at each live gate.
- **P2**: `prompt.context` re-read after `/compact` and `/clear`, observed with a block carrying a timestamp; and whether a `classic.SessionStart` hook sees the settings hook's `additionalContext` in `next(e)`'s result and may return it changed.
- **P3**: the exact behaviour of Write and Edit on a file changed since it was read (the message, and whether a Write to a file never read in the session is refused), on this build — the premise of rule 3's "Bash only". **Answered 2026-11-03 on 2.1.316:** Edit on a file changed outside since its Read, and Write on a file the session had Read and that changed since, are both refused with `File has been modified since read, either by the user or by a linter. Read it again before attempting to write it.`; a Write to an existing file the session never Read overwrites it with no check. Rules 3 and 4 above are written to that.
- **P4**: how a module runs Node — `$.process.run(['node', …])` from PATH, or an engine-provided path. **Answered (2.1.312 declarations):** no engine path; `argv[0]` resolves from PATH, and `init.env` sets variables over the host's, so the mod runs `node` with a PATH of absolute entries.
- **P5**: how a module reads `CLAUDE_CODE_EFFORT_LEVEL` (`$.env`, `options`, or not at all). **Answered (2.1.312 declarations):** `$.env.get(name)` with a string-literal name; `plugin validate` lists the names read.
- **P6**: the `SubagentStop` payload on this build carries `agent_transcript_path` and `agent_id` (the declarations say so), and the transcript's JSONL shape for `Write`/`Edit`/`Bash` tool uses; and whose context a `SubagentStop` hook's `additionalContext` lands in, the session's or the stopped agent's. **Part 1 answered 2026-11-03:** the declarations carry `agent_transcript_path`, `agent_type`, `agent_id`; a transcript on disk is one JSON object per line with `message.content[]` holding `{ type: 'tool_use', name, input }` (`Write`/`Edit` → `input.file_path`, `Bash` → `input.command`) and top-level `agentId`, `isSidechain`, `toolUseResult`. **Part 2 answered 2026-11-03 on 2.1.316:** a `SubagentStop` hook's `additionalContext` lands only in the stopped agent's own transcript, as an attachment after its stop; the parent never sees it. So the touched record's route is the file alone (rule 6 answers no `additionalContext`), and the mod's `classic.SubagentStop` shows the one line in the pane.

A probe that fails its premise changes the spec before the plan, not the plan after.
