## Why

1.2.0 measured three things this release acts on (docs/MEASUREMENTS.md):

- **Reviews are where the tokens are worth it.** The three release reviews found 24 things, 17 accepted, two of them serious (an absolute path leaking through an uncaught throw; the release's own size claim). Each review was briefed by hand, and the Opus whole-branch review was a `general-purpose` agent with a prompt written on the spot. A review that good deserves a definition: clean context, a fixed shape, one `subagent_type`.
- **A coder at xhigh built the same behaviour as one at medium** on a plan-driven task, for 2.5× the cache reads and 3.6× the time — and N was 1, the task mechanical, and Codex ranked xhigh first on robustness and test depth. The trial *suggests* a medium bucket; it does not license a new default. This release ships the bucket and measures it on a judgement-heavy task; the default moves only on that row.
- **The lead cost 2.4–6× per task on Fable**, its bill the cache writes at Fable rates. It does not ship and is not re-run here: 1.2.0's row already says when it earns its place (a cheaper model, or a session whose context is the constraint), and backlog R keeps that pair for then.

And one thing the backlog ordered (R, 2026-09-22): security is the reviewer under a different brief, not a second agent — and the brief has to show it finds something before any definition carries it.

## P0 — the security brief over this package

Runs first, so the reviewer ships with a result, not a promise. Three runs over the **same revision**, `d7180b2`, then one row.

- **The brief.** Cloudflare `security-audit-skill` (MIT), the "MCP and sub-agent trust classes" section of `AI-AND-LLM.md`, quoted into `docs/SECURITY.md` under a new section "How this package is audited" **with Cloudflare's copyright line and the MIT permission notice kept beside the quoted text** (the package's own MIT notice does not stand in for theirs); the upstream commit hash named. Trail of Bits `skills` `differential-review` and `fp-check` (CC-BY-SA-4.0) as method, **linked, never copied**. The brief names the trust classes of this package's parts: three read-only MCP servers spawning vendor CLIs (`servers/*.mjs`, `core/`), a hook with git rights (`hooks/omelette-guard.mjs`), a CLI that writes managed files (`bin/omelette-fleet.mjs`), and the sub-agent definitions it renders.
- **The three runs.** (1) *Plain*: Codex `gpt-6-astra`, "review this package for security defects", no method, one call per category group (servers · guard · CLI/render) — the control. (2) *Brief*: the same calls with the brief. (3) *Plugin*: one run of the installed `claude-security` plugin over the same tree. Every finding from every run is **refuted by a fresh agent** before it is `verified` (the `fp-check` gate: a clean-context reviewer told to disprove it against the code). The row: findings by plain / brief / plugin, the overlap, verified vs refuted, and which verified findings only the brief found.
- **What lands.** Verified findings become tasks of this release (through the flow; a fix and its test each). The SECURITY section keeps the brief, the notice and the row. `omelette-auditor` (backlog S2) is **not** built unless the row shows verified findings the plain review and the plugin both missed; if it does not, the reviewer's security brief is the doc section, and that is the whole answer.
- **Never:** no finding is acted on because a tool said so; nothing an auditor read off the web is executed; the runs stay on the read-only units and read-only sub-agents.

## P1 — `omelette-reviewer`

- **The definition**, `agents/omelette-reviewer.md`, rendered by `rules --agents` beside the coder and the tester: `model` and `effort` from config (`agents.reviewer.model`, default `opus`; `agents.reviewer.effort`, default `xhigh` — review is judgement, the thing the release pays for); `tools: Read, Grep, Glob, Bash, Write`; `disallowedTools: Agent, Edit, NotebookEdit`.
- **What keeps it read-only — stated honestly.** Claude Code's tool filtering cannot scope `Write` to one path or make `Bash` read-only, and the guard refuses only the git commands it names. So the reviewer is read-only by *definition text and by check*, not by enforcement: its definition says the only file it writes is `.omelette/reports/<name>-review.md`; the guard refuses its `git commit`/`stash`/branch/`worktree` by name (containment, as for the coder — SECURITY says so); and **the session runs `git status --porcelain` after every review and rejects the review outright if anything but that report changed** (a test pins the definition's text; the rules line says the check).
- **What it does.** One review of one thing — a plan, a task's diff, a branch — with a clean context: the brief carries the base and head (or the file), the spec path, and, for a re-review only, the earlier findings and rulings. It reads what it reviews, runs the suite when told, and reports findings only, ranked, each `location · scenario · consequence · how to confirm`, then one line: ship / do not ship / needs-check. The reply is the line and the count. A finding without its four parts is a question, as the rules already say.
- **Where it slots in.** The rules' "Reviews" bullets gain one line (the definition, the report path, the `git status` check); the definitions bullet in "Spawning sub-agents" says three definitions instead of two (a factual line, pinned by test); the Routing table's "Strongest code review" row stays Codex — the reviewer is the *clean-context second reader on our own model*, the one 1.2.0 wrote by hand. ORCHESTRATION "Reviews" gains a paragraph; CONFIG "Agent settings" gains the two keys; `doctor` lists the third definition where it lists the other two.
- **The guard learns the names.** `GUARDED_AGENTS` gains `omelette-reviewer` and `omelette-coder-medium` (P2); the refusal names the role it caught, as now. SECURITY's PreToolUse row says four roles.
- **Security is a brief, not a role.** The reviewer run with P0's brief is the package's security audit; nothing else ships for it in 1.3.0.

## P2 — a medium coder beside the deep one

- **What ships.** A second coder definition, `omelette-coder-medium`: the coder template with the name and effort substituted (`agents.coderMedium.model` default `opus`, `agents.coderMedium.effort` default `medium`), guarded by name. **`omelette-coder` and its default (`xhigh`) do not change in this release** — the rules line "Opus-class, xhigh — the shipped `omelette-coder`" stays true, byte for byte. Four definitions render in all (coder, coder-medium, tester, reviewer).
- **The rule** (one clause appended to the existing coder line in "What each agent is handed"; the line's words untouched): the dispatcher briefs `omelette-coder-medium` when the plan section prints the exact text, diff, tests and expected numbers — the coder executes; `omelette-coder` otherwise — a new thing without a written shape, debugging without a known cause, a decision the brief *explicitly delegates* ("decide X between A and B, report the trade-off"). **A brief that leaves a required decision open gets `NEEDS_CONTEXT` at any effort** — the coder template already says so and nothing here changes it; effort buys depth on the decisions the brief hands over, not permission to guess. The bucket and its reason go into the brief and the ledger line.
- **The default moves on the row, not on the trial.** If P3's matched repeat holds (below), the **last task of this release** flips `agents.coder.effort` to `medium` and the rules' "xhigh" parenthetical to "medium, deep on request", with the migration stated in CONFIG and the CHANGELOG: a rendered definition changes only on `rules --agents`; an unset effort follows the new default at the next refresh; an explicit `set agents.coder.effort=xhigh` survives; `doctor` reports a rendered file that differs from config as it does today. If the row does not hold, nothing flips and the medium definition is opt-in — the rules say which bucket, the operator says whether.
- **The rules ceiling moves with the content:** 13 100 → the measured size of the two added lines plus headroom, set once the lines exist (the number follows the content; the test pins the exact lines, not a guess).
- **Docs.** ORCHESTRATION "What each agent is handed" — the coder item gains the two buckets in full; "Spawning sub-agents" lists the four definitions; CONFIG "Agent settings" the new keys, with the 1.2.0 trial row as the reason and the migration paragraph.

## P3 — this release is the experiment, again

Every row names the model, and every design names its confounds.

- **Bucket log — a ledger habit, not a row.** Every task of this release is dispatched with a bucket and a reason, and its ledger line records bucket · coder rounds · defects the tester found. Observational (medium gets the plan-driven tasks by construction), so it ranks nothing; it only shows a medium task that needed a round or produced a defect, which the rule must not produce. Summarised in one sentence in the matched repeat's row.
- **The matched repeat, judgement-heavy.** One task of this release that is *not* plan-driven — P0's largest verified security fix, or, if P0 verifies nothing, the reviewer definition's own design (P1's first task, briefed as a decision: "design the definition text from the spec section") — is run at **both** efforts in two worktrees from the same commit, same brief, judged by the clean-context tester's tests written once from the spec and by `omelette-reviewer` blind to which is which. The row: defects · tests failed · rounds · tokens · wall clock per arm. This is the row the default moves on. N = 1 again; it is the second data point, not the last.
- **The lead is not re-run here.** 1.2.0's row already says when it earns its place — when the session's context is the binding constraint, or on a cheaper model — and neither holds for this release. Backlog R keeps the Opus 5.5 pair with that condition; every package here is built directly by the session.
- **The reviewer measured.** This release's three release reviews are `omelette-reviewer` (Opus, clean context) + Codex + Grok, as in 1.2.0 but with the definition instead of a hand-written brief. Its findings and yield against 1.2.0's Opus review: same shape, no worse a catch.
- **Rent, one line.** The session's resident context per request at the end of this release against 1.2.0's (210–250k), from the session transcript, and the rules file's rendered size before and after — one command each, one line together.
