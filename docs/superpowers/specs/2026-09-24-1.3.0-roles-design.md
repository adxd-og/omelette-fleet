## Why

1.2.0 measured three things this release acts on (docs/MEASUREMENTS.md):

- **Reviews are where the tokens are worth it.** The three release reviews found 24 things, 17 accepted, two of them serious (an absolute path leaking through an uncaught throw; the release's own size claim). Each review was briefed by hand, three times, and the Opus whole-branch review was a `general-purpose` agent with a prompt written on the spot. A review that good deserves a definition: clean context, read-only tools, a fixed shape, one `subagent_type`.
- **A coder at xhigh built the same thing as one at medium** on a plan-driven task, for 2.5× the cache reads and 3.6× the time; the one design defect landed on high. The plan already decides most of what a coder does; the effort level should follow how much is left to decide.
- **The lead cost 2.4–6× per task on Fable** and its bill was cache writes at Fable rates. It does not ship; it is re-measured here on Opus 5.5, once, as an experiment.

And one thing the backlog ordered (R, 2026-09-22): security is the reviewer under a different brief, not a second agent — and the brief has to show it finds something before any definition carries it.

## P0 — the security brief over this package

Runs first, so the reviewer ships with a result, not a promise.

- **The brief.** Cloudflare `security-audit-skill` (MIT), the "MCP and sub-agent trust classes" section of `AI-AND-LLM.md`, quoted into `docs/SECURITY.md` under a new section "How this package is audited"; Trail of Bits `skills` `differential-review` and `fp-check` (CC-BY-SA-4.0) as method, **linked, never copied** into this MIT package. The brief names the trust classes of this package's parts: three read-only MCP servers spawning vendor CLIs (`servers/*.mjs`, `core/`), a hook with git rights (`hooks/omelette-guard.mjs`), a CLI that writes managed files (`bin/omelette-fleet.mjs`), and the sub-agent definitions it renders.
- **The run.** Codex `gpt-6-astra` with that brief over the package at `d7180b2`, one category group per call (servers · guard · CLI/render), four-part findings; **every finding is refuted by a fresh agent** (the `fp-check` gate: a clean-context reviewer told to disprove it against the code) before it is `verified`. Then one run of the installed `claude-security` plugin over the same tree. The comparison is one row: findings by the brief only, by the plugin only, by both; verified vs refuted.
- **What lands.** Verified findings become tasks of this release (through the flow; a fix and its test each). The SECURITY section keeps the brief and the row. `omelette-auditor` (backlog S2) is **not** built unless the row shows the brief finds what the plain review and the plugin miss; if it does not, the reviewer's security brief is the doc section, and that is the whole answer.
- **Never:** no finding is acted on because a tool said so; nothing the auditor read off the web is executed; the runs stay on the read-only units and a read-only sub-agent.

## P1 — `omelette-reviewer`

- **The definition**, `agents/omelette-reviewer.md`, rendered by `rules --agents` beside the coder and the tester: `model` and `effort` from config (`agents.reviewer.model`, default `opus`; `agents.reviewer.effort`, default `xhigh` — review is judgement, the thing the release pays for); `tools: Read, Grep, Glob, Bash, Write`; `disallowedTools: Agent, Edit, NotebookEdit`. Bash for `git diff`/`git log`/`npm test`, Write for its report file only — the guard refuses its commits by name.
- **What it does.** One review of one thing — a plan, a task's diff, a branch — with a clean context: the brief carries the base and head (or the file), the spec path, and what the earlier rounds ruled (a re-review only). It reads what it reviews, runs the suite when told, and reports findings only, ranked, each `location · scenario · consequence · how to confirm`, then one line: ship / do not ship / needs-check. Report to `.omelette/reports/<name>-review.md`; the reply is the line and the count. A finding without its four parts is a question, as the rules already say.
- **Where it slots in.** The rules' "Reviews" bullets do not change; the definitions bullet in "Spawning sub-agents" says three definitions instead of two (a factual line, pinned by test); the Routing table's "Strongest code review" row stays Codex — the reviewer is the *clean-context second reader on our own model*, the one 1.2.0 wrote by hand. ORCHESTRATION "Reviews" gains a paragraph; CONFIG "Agent settings" gains the two keys; `doctor` lists the third definition where it lists the other two.
- **The guard learns the names.** `GUARDED_AGENTS` gains `omelette-reviewer` and `omelette-coder-deep` (P2); the refusal names the role it caught, as now. SECURITY's PreToolUse row says four roles.
- **Security is a brief, not a role.** The reviewer run with P0's brief is the package's security audit; nothing else ships for it in 1.3.0.

## P2 — two coder buckets

- **The rule** (rules file, one clause added to the existing coder line, words of the line untouched): a coder is briefed at **medium** when the plan section prints the exact text, diff, tests and expected numbers — it executes; at **deep** (xhigh) when the coder must decide — a new thing without a written shape, debugging without a known cause, a spec with gaps, "you decide" wording. The dispatcher (the session, or a lead) writes the bucket and its reason into the brief and the ledger line.
- **The mechanism.** Effort lives in the definition, not in the `Agent` call, so there are two definitions: `omelette-coder` (config `agents.coder.effort`, **default changes from `xhigh` to `medium`**) and `omelette-coder-deep` (`agents.coderDeep.model` default `opus`, `agents.coderDeep.effort` default `xhigh`), same template with the name and effort substituted, both guarded. `rules --agents` installs four definitions in all. A `set agents.coder.effort=xhigh` puts an operator back where 1.2.0 was.
- **The rules ceiling moves with the content:** 13 100 → 13 400 rendered characters (`session`), the new clause and the definitions line's growth measured before the number is set, as 1.2.0 did (the number follows the content; the test pins the exact lines, not a guess).
- **Docs.** ORCHESTRATION "What each agent is handed" — the coder item gains the two buckets in full; "Spawning sub-agents" lists the four definitions; CONFIG "Agent settings" the new keys and the changed default, with the 1.2.0 trial row as the reason.

## P3 — this release is the experiment, again

Every row names the model.

- **Bucket validation.** Every task of this release is dispatched with a bucket and a reason. The row: per task, bucket · coder rounds · defects the tester found · tokens (transcripts, `context-by-source --agents`). The rule holds if the medium tasks show no more defects and rounds than the deep ones; if they show more, the boundary moves and the rules text says where.
- **The lead on Opus 5.5, once.** The private `omelette-lead` definition switched to `model: opus`, one package of this release through it (P1, three tasks or fewer) against another built directly (P2), same coder and tester definitions — the 1.2.0 pair re-run with the lead's bill at Opus rates. Ships in 1.4.0 only if the row says so: not more expensive in total, the session grew less, no more escaped defects.
- **The reviewer measured.** This release's three release reviews are `omelette-reviewer` (Opus, clean context) + Codex + Grok, as in 1.2.0 but with the definition instead of a hand-written brief. Its findings and yield against 1.2.0's Opus review: same shape, no worse a catch.
- **Rent, again.** The session's resident context per request at the end of this release against 1.2.0's (210–250k in the direct arm), from the session transcript; the rules file's rendered size before and after.
