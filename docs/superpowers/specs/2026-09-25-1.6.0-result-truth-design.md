## Why

One question runs through every item: **does the user know whether an answer is complete?** Today the answer is "sometimes":

- **The marker and the flag disagree.** All three adapters append `[<unit>: … — treat the answer as partial]` on a non-zero exit (gemini `adapter.mjs:294`, grok `:617`, codex `:359`), grok on an early stop (`:624`), codex on a missing `turn.completed` (`:356`) — and none of those paths sets `partial: true`. Only the output cap, the hard kill and the client cancel do. The spool header, the status feed's `end` event and `results --stats` therefore count those runs as clean. STATUS-FEED:65 lists five reasons and is right about the code, wrong about the intent.
- **Deep research folds a failed gather into a clean report.** `runDeepResearch` counts a thrown gather as `partial: false` by design (gemini `adapter.mjs:420-424`, `:476`); the synthesis sees `_(gather failed: …)_` in its input and writes a confident report over it. Reproduced 2026-09-25: no header, `partial` absent.
- **Two processes of one unit share one snapshot.** `status-<unit>.json` is written by every server process of that unit (`core/status.mjs:47`); process B's `boot()` re-reads A's `lastEvent` and writes its own empty `active`, so A's running call disappears from the feed and `lastEvent` can regress (`:86-93`). `fleet-log.ndjson` loses nothing; the snapshot lies.
- **`initialize` echoes whatever version the client asks for** (`core/jsonrpc.mjs:71`: `"banana"` → `"banana"`). Measured 2026-09-25: Claude Code 2.1.282 asks `2025-11-25` in every one of 299 logged sessions, and we answer `2025-11-25` without having checked what it requires. The current MCP revision is `2026-07-28`, which drops `initialize` altogether; Claude Code still opens with it (`protocolEra: "legacy"` in its own logs).
- **README:198** says a unit "spawns a vendor CLI that cannot write your repository"; SECURITY says the Gemini unit's read-only posture is a permission policy, not a kernel. README:311 already agrees with SECURITY; :198 does not.
- **A vendor process outlives the server that spawned it** when the server is killed from outside: `omelette-fleet call --timeout` below the unit's `timeoutS` SIGKILLs the server without cancelling the call (`core/client.mjs:81`), and Claude Code's own shutdown (`stdin` close → SIGTERM → SIGKILL) has no SIGTERM handler to meet it. SECURITY:277 has said so since 1.3.0 ("backlog U1").

## R1 — one rule for `partial`

**The rule.** `partial: true` is set if and only if the answer's text carries a marker of incompleteness. No adapter path may append a marker without the flag, and no path sets the flag without a marker — with one standing exception, the image tools, whose answer is a bare path by contract and whose flag is the only record (unchanged).

**The mechanism.** A new `core/partial.mjs` owns both halves:

- `partialMark(unit, kind, detail)` → the marker string, byte-identical to today's for every existing kind: `capped` (`output capped at <N> chars — the beginning of the stream was dropped; treat the answer as partial`), `killed` (`hard-killed after <N>s — treat the answer as partial; raise <unit>.timeoutS in the fleet config`), `cancelled` (`cancelled by the client — treat the answer as partial`, grok's `cancelTail` variant kept), `exited` (`CLI exited <N> — treat the answer as partial`), `early` (grok: `run ended early — stopReason=<s>`), `unfinished` (codex: `run ended before turn.completed — treat as partial`), `stages` (gemini: `<N> of <M> stages returned partial answers`), and the new `gathers` (R2). The text of every marker is a string constant in this one file; the adapters stop spelling them.
- `PARTIAL_MARK_RE` — matches exactly the markers above, anchored on `[<unit>: ` and the unit names.
- `withPartial(result, marker)` → `{ ...result, text: <text + "\n\n" + marker>, partial: true }`. The only way to append a marker is through this function, so the flag comes with it.

The adapters keep their control flow; each site that concatenates a marker today (gemini `:242, :266-267, :294, :534`; grok `:564, :589-590, :617, :624`; codex `:312, :324-325, :356, :359`) becomes a `withPartial` call. Where a path already sets `partial: true`, nothing changes but the spelling. `status` stays `"ok"` on a non-zero exit with text — the same reading a hard kill gets today: there is an answer, it is not a finished one.

**The contract.** STATUS-FEED:65 stops listing five reasons and states the rule, then lists the markers. ADAPTERS:273 ("A salvaged kill also returns `partial: true`") becomes "every marker comes with `partial: true`; build markers with `core/partial.mjs`, never by hand". `core/unit.mjs:41-48` (the adapter return shape) and `core/artifact.mjs:113` say the same. `results --stats`' `partial` column and the spool header need no change: they read the flag.

## R2 — deep research names its failed gathers

A gather that throws or is hard-killed is a stage that **ran and produced no findings**; today it is counted as neither partial nor failed. Now:

- `runDeepResearch` counts failed gathers separately from partial stages. The catch at gemini `adapter.mjs:476` records the sub-question and the error's first line.
- When N > 0 the report carries a header line above the synthesis, after the degraded banner and the stages line if present: `[gemini: N of M gathers failed: <sub-question 1>; <sub-question 2>]` (sub-questions truncated to 80 characters each), built through `partialMark('gemini', 'gathers', …)`, and `partial: true` travels out via `withPartial`.
- The synthesis prompt is unchanged: it still receives `_(gather failed: …)_` in place of the findings, which is the honest input. The design comment at `:416-424` is rewritten to the new rule.
- `degraded` (decomposition failed, one shallow pass) keeps its banner and gets no flag: that report is complete for what it did, and the banner says what it did. The three cancellation paths are unchanged (already `partial: true`).

## R3 — a snapshot per process

**Schema 2.** Each unit server process writes its own snapshot, `status-<unit>-<pid>.json`, atomically as today:

```json
{ "schema": 2, "unit": "codex", "pid": 48123,
  "active": [ … ], "lastEvent": { … } | null, "updatedAt": "…" }
```

- `boot()` no longer reads a predecessor's `lastEvent` (it starts `null`) and no longer clears anything but its own file. It **sweeps** its unit's stale files: every `status-<unit>-<pid>.json` whose `pid` is not alive (`process.kill(pid, 0)` throws `ESRCH`) is removed. A pid the OS has reused keeps a dead file alive until the next sweep finds it dead — a delay in cleanup, not wrong data, and the file's `updatedAt` shows its age.
- The file is removed on a clean exit (the `stdin` end path in `core/jsonrpc.mjs:224` after in-flight calls land; the SIGTERM path of U1). A SIGKILLed server leaves its file for the next sweep.
- The reader's two questions: **what is running now** = the union of `active` across `status-*.json` (the STATUS-FEED recipes already glob that pattern); **the last event of a unit** = the `lastEvent` with the newest `endedAt` across that unit's files. `fleet-log.ndjson` keeps its shape and writes `schema: 2` — one number per contract.
- No CLI command reads the snapshot today (`doctor` probes the servers, `results` reads the spool), so the CLI changes nothing here; the readers are the jq recipes and whatever an operator built on schema 1.

STATUS-FEED's snapshot section is rewritten for schema 2 with a "schema 1 → 2" paragraph (why, what a reader changes), and the recipes are updated: `jq -r '.active[] | …' ~/.omelette/status-*.json` stands; the "last event" recipe becomes a `jq -s` over the unit's files.

## R4 — an honest protocol version

`core/jsonrpc.mjs` gets `SUPPORTED_PROTOCOLS = ['2025-11-25', '2025-06-18', '2024-11-05']`, newest first. `initialize` answers the requested version when it is listed, otherwise the first entry — the spec's rule for the handshake era: "If the server supports the requested protocol version, it MUST respond with the same version. Otherwise, the server MUST respond with another protocol version it supports. This SHOULD be the latest version supported by the server." `DEFAULT_PROTOCOL` is `SUPPORTED_PROTOCOLS[0]`.

**Why those three.** Verified against the changelogs 2026-09-25 (ledger): for a tools-only stdio server every addition in `2025-06-18` (`structuredContent`, `outputSchema`, resource links, `_meta`, `title`) and `2025-11-25` (icons, `Implementation.description`, tool-name guidance, input-validation errors as tool errors — which the adapters already do with `isError: true`) is optional; the `MCP-Protocol-Version` header is HTTP-only. **`2025-03-26` is excluded**: it made receiving JSON-RPC batches mandatory ("MUST support receiving JSON-RPC batches") and the handler does not; `2025-06-18` removed batching again. `2026-07-28`, the current revision, is a different protocol (no `initialize`, per-request `_meta` version, mandatory `server/discover`, required `resultType`, no `ping`) — out of scope, see below. `core/client.mjs:142` (our own `call`) asks `2025-11-25`.

**Measured and recorded.** MEASUREMENTS gets a section "What Claude Code sends at initialize": 2.1.282, `protocolVersion: "2025-11-25"`, 299 of 299 sessions since 2026-09-05, `protocolEra: "legacy"`, no `server/discover` probe seen. `doctor`'s `initialize →` line says which version the server would answer **to Claude Code's request**, not to our client's (`bin/omelette-fleet.mjs:2617`).

**Backlog, not this release: the dual-era server.** When Claude Code stops opening with `initialize`, the server needs `server/discover`, `resultType: "complete"` on every result, `ttlMs`/`cacheScope` on `tools/list`, and `UnsupportedProtocolVersionError` (-32022). Until then our `-32601` on `server/discover` (`jsonrpc.mjs:154`) is what the spec's compatibility matrix calls "a non-modern error": a dual-era client falls back to `initialize` deterministically.

## U1 — unit timeouts

**Measure first, per CLI (agy, grok, codex), one MEASUREMENTS section.** (a) `omelette-fleet call --timeout 5` on a prompt that runs longer: is the vendor process alive after the server is gone, and for how long? (b) After a normal run ends, is anything left in the run's process group (`ps -o pid,pgid` on the group before `spawn.mjs` returns)? The section records the answer per CLI. **The measurement gates the code:** if (b) finds nothing for any CLI, the third path below is not written and the section says so.

**Then, the routine paths.**

1. **`call --timeout` cancels before it kills** (`core/client.mjs`): on timeout, send `notifications/cancelled` for the in-flight id, wait up to 2 s for the server to exit on its own, then SIGTERM, then SIGKILL after 1 s. The server's existing cancel path kills the process group.
2. **The server meets SIGTERM and SIGHUP** (`core/jsonrpc.mjs`, beside the `stdin` end handler): kill every active process group (`core/spawn.mjs` keeps a registry of live pgids; the kill is the same `process.kill(-pid, 'SIGKILL')` as `:190`), remove the R3 snapshot, exit. The `stdin` end path is **unchanged**: it still lets in-flight calls land so the answer is spooled (`<unit>_result` recovers it) — Claude Code's shutdown sends SIGTERM if that takes too long, and now SIGTERM is met.
3. **The run end reaps the group** (only if (b) found leftovers): when the main child has exited, SIGKILL whatever is left in its group before `spawn.mjs` resolves.

**What stays unbounded, and where it is written.** A SIGKILLed server. SECURITY:277 is rewritten: the outside-kill case is closed by 1 and 2, the leftover case by 3 or by the measurement, the SIGKILL case is named as the one that remains. No reaper by pgid read off a file: killing processes by a stored number needs its own threat section and is not this release.
