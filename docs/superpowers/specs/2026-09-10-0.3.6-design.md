# 0.3.6 — the small half of the road to 1.0: `cwd` for research, caps and contracts, the rules say when

**Status:** design approved in chat by the operator 2026-09-10 · **Base:** main `c0c2430` (v0.3.5 + the CI test fix) · **Branch:** `feat/0.3.6`

## Why

On 2026-09-10 the operator ruled that omelette-fleet takes no new feature until its backlog is empty, and that an empty backlog is 1.0. This release is the backlog's S column: five small code items the last two release reviews named, and four additions to the rules that Codex's review of the operating model asked for — the rules say *who* does what, not *when* a delegate is worth its cost, and the review discipline the last two releases actually practised is written nowhere.

Order of work: **S1 → S3 → S2 → S4 → S5** (code, probe first because S3 depends on S1), then **S6 → S9** (rules and docs).

## S1. `cwd` on the research tools; the probe stops changing directory

- `grok_research`, `gemini_research` and `codex_research` gain an optional `cwd` input, with the same schema text and validation the review tools use: absolute, must exist, must be a directory; otherwise the call fails before any spawn with the review tools' wording. Grok passes `--cwd`, Codex `-C` (and the spawn cwd), Gemini the spawn cwd. Omitted → today's behaviour (the server's process cwd). The spooled record's `cwd:` header shows it.
- `probeUnit` passes `cwd: dir` and drops `process.chdir` and its `finally`. With no directory change, a relative `OMELETTE_HOME` or bin override resolves against doctor's own cwd like for every other command, so `probeRuntimeEnv` keeps only the timeout cap: its absolutising and the tests that pinned it go, replaced by one test that a relative `OMELETTE_HOME` behaves under `--probe-sandbox` exactly as under plain `doctor`.
- ADAPTERS.md and the tool descriptions say research runs where `cwd` points.

## S2. Codex's built-in `outputCap`: 400 000 → 4 000 000

- `units/codex/adapter.mjs` gets a `CODEX_OUTPUT_CAP = 4000000` constant used by `builtin` and by `extractResult`'s default, the way Grok's `GROK_OUTPUT_CAP` is wired since 0.3.5; the fleet default 400 000 and Gemini stay. CONFIG's per-unit cap table and the `show` default follow. Test pins the constant and parameterises the existing Codex cap tests.

## S3. The probe's deadline ends the child, not just the report

- `probeUnit` creates an `AbortController`, passes `{ signal }` as the third argument of `rt.callTool(...)` and aborts it when the deadline fires. The runtime honours a signal only under `cancel: kill`; the probe therefore runs its unit with `cancel` forced to `kill` — the config key is overridden through the unit's env map when the unit has one, else through a runtime option `createUnitRuntime(unit, { env, cancel: 'kill' })` added for this purpose (the option wins over the config file, documented as internal to doctor). The abandoned call returns `cancelled` within the runtime's kill path; the probe's verdict logic is unchanged (directory first, then `skipped (timed out after N s)`).
- Result: `doctor --probe-sandbox` returns within `capS` + the kill latency, for every unit, including Gemini's `timeoutS + 60`. Test: the existing "late-cli" case asserts doctor exits within `capS + 5` s and the fake's process is gone.

## S4. `interpretGrok`: a cancel does not swallow an error Grok reported

- When `res.cancelled` and the stream also carried a Grok-reported error (`a.error` / the error event the adapter already parses), the cancelled marker names it: `[grok: cancelled by the client — Grok had reported: <error line>]` and the thrown `grok cancelled by the client` message carries the same tail. No change to which branch wins (cancel still decides `status: cancelled`). Test: a fake that emits an error event then is killed under `cancel: kill`.

## S5. Image tools return a bare path, or an error — never a path with a marker

- For `gemini_image`, `grok_image`, `grok_image_edit`, `codex_image`: when the run was capped, killed or cancelled and an artifact file EXISTS, the tool returns the bare path only; the cap/kill/cancel is recorded in the status feed (`partial: true`, the log line) and in the spooled record, never appended to the returned text. When no artifact exists, the tool fails with the unit's existing wording (`… output exceeded the N char cap …` / `… hard-killed …` / `… cancelled by the client`). The bare-path contract is stated once in ADAPTERS.md and in each image tool's description.
- Tests per unit with the fake binaries: capped + file → bare path, `partial: true` in the status feed; capped + no file → error naming `<unit>.outputCap`; killed + file → bare path.

## S6. Rules: when a delegate is justified; the small-change exception

Added to the rules template under "Operating model for the session" (and to ORCHESTRATION.md):

- A delegate (sub-agent or unit) is justified when **all four** hold: the subtask is independent (its own files or its own question), there is a **named uncertainty** it resolves ("does the migration run on 0.3.2 data?", not "look at the architecture"), the cost of a wrong answer is material, and the expected output fits one sentence. Otherwise the session does it.
- **Small-change exception**: the session edits directly when the change is at most **20 lines**, changes no behaviour beyond the fix, carries its test in the same commit (or touches only docs/comments), and is logged in the ledger. The tester still runs on every coder result; it is not required for a docs-only edit.

## S7. Rules: the finding format is mandatory

Added under "Tester flow" / a new "Reviews" bullet: every review brief asks for, and every finding is recorded as, **location · scenario · consequence · how to confirm**; the orchestrator's ruling on each is `verified`, `rejected (reason)` or `needs-check (what)`. A finding without a scenario is a question, not a finding. The three review briefs quoted in ORCHESTRATION.md use the format.

## S8. Rules: re-review continues, first review is clean

Added beside S7: the first review of a change always runs with a clean context (no coder summary, no prior findings); a **re-review** after a fix round is briefed with the previous findings and the rulings on them, so it verifies the fixes rather than rediscovering the file.

## S9. Ledger: the review-yield line

Added under "Ledger and handoff": at the close of a plan, one line `review yield: <findings> found / <accepted> accepted / <rejected> rejected — <the two or three that mattered>`. This repository's archived ledgers get theirs: 0.3.4 — 33 / 32 / 1 (FIFO hang, imprisoning Stop on a read-only `.omelette`, quoted `--exec`); 0.3.5 — 25 / 23 / 2 (held-vs-failed probe verdict, false BREACHED from our own spool, chdir).
