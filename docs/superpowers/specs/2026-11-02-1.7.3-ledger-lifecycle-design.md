# 1.7.3 — Ledger lifecycle and the decisions register

A ledger belongs to a branch and closes when the branch is gone; the rulings marked as binding move into a decisions register by script; after a compaction or a `/clear` the session is handed the same three things every time. Nothing in it asks anyone to remember.

## Why

Read 2026-11-02 in this checkout: `.omelette/` holds 11 ledgers of closed plans in its root (1.2.0 … cleanup, 500 KB) and 11 more in `archive/`; another operator project reports 15 closed ledgers in its root. Three consequences, all on the agent, none on the human:

- **PreCompact stamps every root ledger** (`appendToLedgers`), so after each compaction all 11 carry a fresh "re-read this ledger before continuing" line and look alive.
- **The compaction print is alphabetical with a 12 KB cap** (`sessionStart`, `HANDOFF_TOTAL_MAX`): `ledger-1.2.0.md` prints first; the open ledger, `ledger-cleanup.md`, sorts last and is the one dropped.
- **Rulings that outlive their plan live only in a gitignored ledger nobody re-reads** ("finding 5 is not fixed", "Flash is always High", "the guard is containment, not a security boundary"); the one place that calls itself an "archive of decisions" (`backlog-1.0.md`) is also gitignored. After a `/clear` nothing is printed at all: the rules file asks the session to re-read the ledger, and the rule about moving closed ledgers to `archive/` has existed since 1.7.0 and was followed for 11 of 22.

The agent after a `/clear` or a compaction has three questions: where did we stop, what is next, what is decided and still binds. The answer to the first is buried among 11 files; the third has no file.

## The model

- **A ledger belongs to a branch.** Its first lines carry a header, `branch: feat/<name>`. `omelette-fleet ledger open <plan>` creates `.omelette/ledger-<plan>.md` with that header from the current branch (refuses on a detached HEAD, refuses when the file exists). A header of `branch: main` is a standing ledger (lane lines, operator notes): it is never closed.
- **Open** = the header's branch exists as a local branch (`git show-ref --verify --quiet refs/heads/<branch>`). **Closed** = the header's branch is gone. **Untracked** = no header (every ledger written before 1.7.3). Only root ledgers are classified; `archive/` is never read by anything but a human's grep.
- **A binding ruling is marked when it is written**, not triaged later: `Ruling(binding): <what> — <why> — <cost if wrong>`, optionally ending in a pointer, `path:line` + a fragment in backticks, in `check`'s shape. The rules text gives the three criteria for the mark (outlives its plan; constrains future work; the cost of being wrong is named). Plain `Ruling:` stays local to the ledger. `Superseded by:` lines keep working as today.
- **The register** is `.omelette/decisions.md`, always — `fleet.config.json` is the operator's, global to every project, so no config key. A project that wants its register committed writes one line as the file's first line, `register: docs/DECISIONS.md` (a relative path inside the project, no `..`, not a symlink; anything else is refused with a line and the sweep writes nothing), and the sweep appends there instead. This checkout does that. The sweep appends; a human or the session edits the register to strike a line (`superseded by …` appended to the line, never deleted the same release). No cap enforced by code; `doctor` warns above 30 unstruck lines.
- **One register line per binding ruling**, in `check`'s pointer grammar when the ruling carries a pointer, so `check` sees it at the line start: `- <path>:<line> · \`<fragment>\` · <YYYY-MM-DD> · <plan> · <ruling>`; without a pointer, `- <YYYY-MM-DD> · <plan> · <ruling>` (prose to `check`). `<ruling>` is the ledger line from `Ruling(binding):` to its end, with a trailing pointer moved to the front; the date is the ledger line's leading `YYYY-MM-DD` when it has one, else the sweep's. The rules text asks a binding ruling to fit one line of about 200 characters.

## The sweep

`omelette-fleet ledger sweep [--dry-run]`, deterministic, idempotent, no judgement:

1. For every root ledger with a header whose branch is gone, in name order: collect every `Ruling(binding):` line (the whole line, `## Handoff` blocks included, fenced code excluded); append each to the register as one line with the sweep's date and the plan name; append to the ledger `closed <ISO> by sweep — <n> binding rulings → <register path>`; move the file to `.omelette/archive/` (`rename`, refusing to overwrite — a collision is reported and the file stays).
2. Untracked ledgers are listed, one line each, and left alone: `untracked: ledger-1.2.0.md (no branch: header — add one, or move it to archive/ by hand)`.
3. Prints one line per action, exits 0 even when there is nothing to do; without git on PATH or outside a repository it says so once and does nothing. `--dry-run` prints the same lines and writes nothing. Writes follow 1.7.2's rules: the register through tmp + rename, the ledger append O_APPEND | O_NOFOLLOW on a regular file, PATH entries absolute only.

**One home for the logic: `core/ledger.mjs`** (`sweepLedgers(projectDir, opts)`, `classifyLedger`, `readRegisterPath`), imported by the CLI. The guard template stays standalone for everything it refuses or prints; for the sweep alone it does `await import('<package root>/core/ledger.mjs')` through a path rendered at `rules --hooks` time (`{{package}}`, the absolute root of the package that rendered it), inside try/catch: an import that fails (the package moved, was removed, or the hook predates it) is one stderr line, the sweep is skipped, the print still happens. `doctor` already compares the hook's version marker with the package's; it adds the import path to that check (`hook imports <path> — not found: rules --hooks`). This is the first code the hook loads from outside itself; SECURITY says so, and that it is the package's own file at the path the operator installed, loaded with the session's privileges exactly as the CLI is.

Where it runs, so nobody has to call it: **the guard's SessionStart, every source** (startup, resume, clear, compact) runs the sweep when `.omelette/` holds a ledger, before any print, with a 2 s wall clock on each git call, fail-soft (an error is one stderr line, exit 0). `doctor` runs it too and prints its lines. The command exists for the operator and for the rules text; the hook is what makes the rule hold. The hook spawning git is new: SECURITY says what it runs (`git show-ref`, `--no-optional-locks`, read-only, the absolute-PATH rule of 1.7.2) and that it runs in the session's cwd.

## The print

`SessionStart` prints on `source` **`compact` or `clear`** (today: `compact` only; the plan's first task confirms live that Claude Code sends `clear` — the hooks reference lists `startup`, `resume`, `clear`, `compact`). After the sweep, in this order, under the existing 12 KB cap with the existing whole-block drop rule:

1. The last `## Handoff` block of every **open** ledger (root only, as today — the sweep has just emptied the root of closed ones), then of every untracked one.
2. The register (the redirect followed), whole, bounded 6 KB from the tail with the tail note — 30 lines of about 200 characters fit.
3. If `.omelette/backlog.md` exists: its first Markdown table (from the first line starting with `|` to the first blank line after it), bounded 2 KB. The backlog is a project convention, not a rule; a project without one gets no section.

Each section has a one-line heading naming the file. The order is the three questions in order.

## doctor and check

- `doctor`: `ledgers: 1 open (ledger-1.7.3.md → feat/1.7.3), 0 untracked, 23 archived` and `decisions: docs/DECISIONS.md (via .omelette/decisions.md) — 14 lines, 0 struck, 0 stale pointers`; a warning line for each untracked ledger, for more than one open ledger, for more than 30 unstruck lines, for a refused `register:` line, and for a hook whose rendered import path does not resolve.
- `check <register>` verifies the pointer lines as they are (the pointer opens the line); `doctor` runs it on the register for the `stale pointers` count.

## Rules and docs

- **Rules template** (`rules/omelette-fleet.md`, "Ledger and handoff"): start a ledger with `omelette-fleet ledger open <plan>` (or by hand, with the `branch:` line); write a decision that outlives its plan as `Ruling(binding):` by the three criteria; after a `/clear` or a compaction read, in order, the open ledger's last handoff, the register, the backlog's map — the hook prints the three; a plan closes when its branch is merged and deleted, the sweep does the rest; at a goal's boundary delete the merged branch, then `/clear`.
- ORCHESTRATION "Ledger and handoff" gets the same in its longer form; CONFIG gets the `ledger` commands, the `register:` redirect line, the hook's new behaviour on `clear` and `startup` and its import of `core/ledger.mjs`; SECURITY gets the hook's git call; CHANGELOG 1.7.3; the rules file version marker.
- `docs/DECISIONS.md` opens with a two-line map (what a line is, how a line dies) and the lines.

## Migration of this checkout

A task of this release, by hand, once: a cheap model harvests every `Ruling:` of the 22 ledgers (root and archive) into a candidate list; the session triages by the three criteria and writes `docs/DECISIONS.md` (expected 15–25 lines, each with a pointer where one exists); the 11 root ledgers move to `archive/` by `mv`; `ledger-1.7.3.md` is opened with the command. Other operator projects do the same by hand or leave their legacy ledgers untracked: `doctor` names them until they are moved.

## Non-goals

- No deletion of anything, ever: the archive stays, struck lines stay a release.
- No automatic triage: the `(binding)` mark is written by the session when the ruling is made; the sweep copies, it does not judge.
- No fleet-pane or mod changes (1.8.0), no `prompt.context` injection: the print stays a SessionStart hook.
- No edit of the operator's settings files; the hook snippet is unchanged (SessionStart is already wired, the matcher widens from `compact` to all sources in the printed snippet — an existing install keeps working on `compact` alone until the operator re-merges the snippet, and `doctor` says so).
- No cap enforced in code on the register; a warning only.
- No new key in `fleet.config.json`: it is the operator's file, not the project's.

## Tests and done-when

Tests, each where it earns its place: header parsing (first 20 lines, CRLF, missing, `main`); classification with a fake repo (branch present, deleted, detached HEAD on `open`); the sweep moves exactly the closed ones, copies binding lines verbatim with date and plan, excludes fenced code, is idempotent, refuses an archive collision, honours `--dry-run`, says one line without git; the `register:` redirect (relative, inside, refused shapes), the pointer moved to the front and `check` accepting the line; the print on `clear`, its three sections, their bounds and the cap; `doctor`'s lines and warnings; `check` on a register line with and without a pointer; the rendered rules file. Done when: `npm test` green on Linux three CI runs; three reviews per the release flow (Codex `codex_code_review`, Grok, an Opus whole-branch review; the reviewers are told that `feat/cleanup-gate` arrived on main without release reviews and cover it); this checkout's root holds one ledger and `docs/DECISIONS.md` is seeded; the live check on `source: clear` recorded in the ledger; tag `v1.7.3`.

Measured, before and after, with the same command — the rendered hook fed a `SessionStart`/`compact` event for this checkout — into MEASUREMENTS: bytes printed, which ledgers' handoffs are in it, whether the open ledger's is. Before (2026-11-02): 11,686 bytes, the handoffs of six closed plans (1.2.0 … 1.7.0), the two open ledgers absent; one compaction stamps 12 files. The behavioural question — does the session orient faster after a `/clear`? — gets one cheap series, not a verdict: at every `/clear` boundary the ledger records the tool calls and bytes read before the first working action; five or six boundaries decide `helped` / `no observed effect` / `confounded` in the evals vocabulary. One boundary is `confounded` by definition.
