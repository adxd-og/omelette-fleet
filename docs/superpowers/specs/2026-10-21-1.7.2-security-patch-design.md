No finding gives remote entry; each needs a precondition on the operator's machine (a relative PATH entry, write access to the fleet home, a widened passthrough). ## T1 — relative PATH entries

- `bin/omelette-fleet.mjs:367` `whichBin` walks every entry of `env.PATH`; `doctor` and `install` resolve the vendor binaries and `claude` through it. `core/check.mjs:196` copies the parent's `PATH` unfiltered into the env `git` runs with, in the checked repository's `cwd`. The units' runtime is already right: `core/spawn.mjs:148-151` keeps absolute directories only.
- Scenario: `PATH=bin:/usr/bin`, `doctor` run inside a foreign repository executes its `bin/codex --version`, outside any vendor sandbox.
- Fix: `whichBin` skips an entry that is not absolute (the same rule as `buildChildEnv`, one shared helper in `core/spawn.mjs`); `check`'s env takes the filtered PATH. `runClaude` keeps `inheritEnv: true` (the comment at `:1288` says why: the registration needs the parent's version-manager variables and runs no model); the `claude` binary it runs is the absolute path `whichBin` now returns.
- Test: a PATH with a relative directory holding an executable `codex` → `whichBin` returns null (and finds the absolute one when both exist); `changedSince` spawns `git` with a PATH holding no relative entry (the existing spawn stub in `test/check.test.mjs`).

## T2 — writes that follow symlinks

- `core/status.mjs:84` snapshot (tmp + rename, tmp named `${snapshot}.${pid}.tmp`), `:100` `appendFileSync` to `fleet-log.ndjson`, `:110` the log trim's tmp; `core/update.mjs:165` the update cache's tmp. All plain `writeFileSync` / `appendFileSync`: a symlink at the path is followed, and a tmp name an attacker can predict is a symlink they can plant.
- Scenario: `fleet-log.ndjson` → symlink to `~/.zshrc`; a prompt holding `$(cmd)` is appended there inside JSON and runs at the next shell start. Codex reproduced the mechanism in memory.
- Also: `mode: 0o600` applies at creation only; an existing wide-mode file keeps its mode.
- Fix, the precedent being `core/results.mjs:355` and `hooks/omelette-guard.mjs:945`: tmp files are opened `wx` (O_EXCL: a planted tmp fails the write, never follows) with an unpredictable suffix; the log is opened `O_WRONLY | O_APPEND | O_CREAT | O_NOFOLLOW`, `fstat` must say a regular file, and the mode is tightened to 0600 with `fchmod` when it is wider; everything stays fail-soft (the feed is a convenience, never a reason to fail a call). The same shape in `writeCache`.
- Test: log symlinked to a victim file → the victim is byte-identical after a logged event, the feed stays silent; a planted tmp at the predictable name → the snapshot still lands and the planted file is untouched; an existing 0644 log is 0600 after the first append.

## T3 — `@path` in Grok image prompts

- `units/grok/adapter.mjs:287-296` documents that the grok CLI attaches any existing file a prompt names as `@<path>` before the model runs, whatever the toolset; `:795` research neutralises `@` → `＠`. `grok_image` (`:862`) and the transformation text of `grok_image_edit` (`:349`, `:899`) pass the prompt untouched.
- Scenario: `@/Users/…/.ssh/id_ed25519` in an image prompt goes to the vendor although the image toolsets hold no `read_file`.
- Fix: `neutraliseAt` on the `grok_image` prompt and on the transformation text; an `imagePath` holding `@` is refused with an error naming the rename (review round: an existing crafted path such as `/tmp/x/ @/etc/passwd` reached the CLI's `-p` raw, and `@ /abs` attaches a file), and an `@`-free path passes as given — it is the tool's own input, and the CLI must see it. Residual as for research: `a＠b` for an e-mail in a prompt.
- Test: the fake grok records the prompt; `@/etc/passwd` arrives as `＠/etc/passwd` on both tools, and the edit's image path arrives intact (`test/grok.test.mjs` pattern).

## T4 — passthrough hands one vendor's key to another

- `core/spawn.mjs:138-153`: `OMELETTE_ENV_PASSTHROUGH` patterns apply to every unit; each adapter scrubs its own keys only (`units/codex/adapter.mjs:432`, `units/grok/adapter.mjs:266`, `units/gemini/adapter.mjs:156`). Codex reproduced: `CODEX_*` hands `CODEX_API_KEY` to Grok and Gemini; `GOOGLE_*` hands `GOOGLE_API_KEY` to Codex and Grok; `GROK_*` hands `GROK_CODE_XAI_API_KEY` to Codex and Gemini. With the default environment nothing leaks.
- Fix: one `BILLING_ENV` list in `core/spawn.mjs`, the union of the three `riskEnv` lists, scrubbed in every unit after the passthrough; each adapter's own list stays on top (a vendor adds a key, its adapter names it, the union follows). SECURITY's allowlist section says the scrub is fleet-wide.
- Test: with `OMELETTE_ENV_PASSTHROUGH=CODEX_*,GOOGLE_*,GROK_*` and the three keys set, no unit's child env holds any of them (`test/env-allowlist-1.5.0.test.mjs`).

## T6 — the Antigravity grey zone

- Sources, opened 2026-10-21: Antigravity Additional Terms §6 — "using third party software, tools, or services to access the Service" is a breach (example: OpenClaw with Antigravity OAuth), "including … using the Service in connection with products not provided by us"; the FAQ — "`agy -p` is intended for direct scripting and CI workflows. Wrapping `agy` inside third-party coding agents or applications, or automating account rotation, is not supported under consumer plans", and "to use a third-party coding agent with Gemini, we recommend using a Gemini Enterprise or Google AI Studio API key".
- The unit runs the official binary under the operator's own login, with no key handling and no account rotation: not the first clause; "wrapping agy inside a coding agent" on a consumer plan is the unit's case to the letter. Unsupported is not forbidden; the FAQ files it under the ToS question. No ban for calling the official CLI is known.
- Ruling (operator, 2026-10-21): a warning, not a rework. README's gemini row and SECURITY's "Gemini — the weakest posture" section get a paragraph: a grey zone on consumer Antigravity plans, the two quotes with the date, the account risk is the operator's, Google recommends an API key, which this unit does not take (it scrubs such keys on purpose). `doctor` prints one `notice` line under gemini when the gemini binary is found or the unit is registered, pointing at SECURITY. The AI Studio key path is a feature for after the clean-up (backlog).
- Test: `doctor` output holds the notice when the gemini binary is found or the unit is registered (the existing doctor tests with fake binaries).
