## Threat model

**Prompt injection through content a unit ingests.** Every unit is pointed at untrusted material by design — fetched web pages during research, and repository contents during review. A page or a file can contain instructions aimed at the model. The mitigation is not detection; it is that a unit has as little as possible to act with: a Grok research run has the web and no local files, a Grok review run has local files and no web, a Codex review run reads inside a kernel sandbox and has no web, and for Gemini the same holds under the web-research rule set below ([Recommended agy allow-rules](#recommended-agy-allow-rules)); the runs that hold local reads and the web at once are `codex_research`, by design (research that depends on running things), and `gemini_research` (with `gemini_deep_research`) under the opt-in agy rule set, by the operator's choice; what either reads can leave in a web query — route them only at material you would paste into a search box. A compromised unit can return misleading *text*, and that text is what you have to distrust — never execute instructions a unit reports finding, and verify facts it brings back from the web.

**Where a research run starts.** The three research tools — `grok_research`, `gemini_research` and `codex_research` — start in a fresh empty directory, removed after the run, unless the caller passes `cwd`, which opts the run into whatever the CLI reads from a workspace; `gemini_deep_research` takes no `cwd` and always runs in one.

**Secrets reachable by a model that can run shell commands.** A vendor CLI is not a library call: it runs a model that reads files and executes read-only commands. Anything in that process's environment is therefore readable by the model and can end up in an answer, in a log, or in a web request. Inheriting the MCP server's environment would hand a review run your `GH_TOKEN`, your cloud credentials and everything else exported in your shell. Hence the env allowlist below.

**Billing-key leakage into metered spend.** These CLIs authenticate against a subscription, but several of them prefer an API key when one is visible in the environment — silently, with no visible change except the bill. `OPENAI_API_KEY`, `CODEX_API_KEY`, `XAI_API_KEY`, `GROK_CODE_XAI_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_GENERATIVE_AI_API_KEY`, `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` are deleted from every unit's child environment (fleet-wide since 1.7.2, [below](#the-environment-allowlist)), and so — for Gemini, belt and braces under exact names — are the Google Cloud credentials `GOOGLE_APPLICATION_CREDENTIALS` and `GOOGLE_CREDENTIALS` and the Vertex switch `GOOGLE_GENAI_USE_VERTEXAI` — and the scrub runs *after* the allowlist and the passthrough patterns, so a pattern like `CODEX_*` cannot re-admit the key it deletes.

**Configuration the fleet did not choose.** A vendor CLI reads its own config file, and that file can carry more than model defaults: MCP servers, plugins, hooks, notification commands. A filesystem sandbox does not bound a *configured MCP tool* — a server that mutates an external system (a tracker, a deploy endpoint) would be reachable from a call the fleet believes is read-only. Codex is therefore run with its user config ignored entirely. Codex still runs `~/.codex/hooks.json` under `--ignore-user-config` (observed 2026-09-25, codex-cli 0.156.1); agy reads `~/.gemini/antigravity-cli/settings.json`, `~/.gemini/config/hooks.json`, `~/.gemini/config/mcp_config.json` and a workspace's `.agents/hooks.json` / `.agents/mcp_config.json`, and has no flag to ignore them — confirmed live on 2026-10-21 (agy 1.4.4): headless `agy -p` ran a workspace's `.agents/hooks.json` `SessionStart` and `PreInvocation` commands before the prompt, with no trust prompt. Those files are yours; the fleet neither reads nor edits them. It follows that a `gemini_research` call given a `cwd` runs whatever hooks that directory declares; without a `cwd` the unit runs in a fresh empty directory (the default).

**Runaway processes.** A model in a tool loop can burn wall-clock time and memory. Every spawn runs in its own process group so a wall-clock timeout SIGKILLs the whole tree rather than the top process; stdout is capped at a tail of 400 000 characters (the `outputCap` default; Codex's built-in is 4 000 000 and Grok's 10 000 000, and the config can narrow or raise any of them) and stderr at 8 192, so a runaway generator cannot exhaust memory; Grok additionally caps turns (`maxTurns`, default 30; `imageMaxTurns`, default 8). The stdin transport caps one un-terminated JSON-RPC frame at 16 MiB and drops it rather than letting the buffer grow until the process dies.

**A config file becoming a foot-gun.** A JSON file is easy to edit, easy to copy between machines, and — critically — writable by anything that can write files. If widening a unit's powers were a one-line config edit, the config file would itself be the attack surface. Hence the ceiling below: the config can only ever narrow.

## The ceiling

Opening write mode for a unit takes **two independent keys**:

<img src="assets/diagrams/security-layers.svg" alt="Four compensating layers from the config ceiling inward to the guard hook, each labelled with what it does not cover, and the residual risk no layer removes." width="880">

1. `"mode": "workspace-write"` for that unit in `fleet.config.json`, and
2. the unit named in **`OMELETTE_ALLOW_WRITE`** (comma-separated, case-insensitive) in the MCP server's environment block.

`OMELETTE_ALLOW_WRITE` lives in the MCP server registration — outside every project, and not writable by a read-only unit. **`ORION_ALLOW_GEMINI_MUTATE=1`** is honoured as a legacy alias that opens the ceiling for `gemini` only.

`OMELETTE_ALLOW_REPRO` is a separate gate, not a third key: it opens `mistral_security_repro` (executing code in a disposable clone) and nothing else, and `OMELETTE_ALLOW_WRITE` does not open it. See [the Mistral section](#mistral--policy-for-reads-a-kernel-for-every-shell-command).

"The config can only narrow" means exactly this: a config file that asks for more than the environment allows does not get it. The requested mode is recorded (`requestedMode`) and the effective mode falls back to `read-only` with a warning on stderr — the call still runs, just without the extra power. `omelette-fleet show` prints that state as `workspace-write (clamped to read-only)`, so nobody reads the requested value off the table and believes it. There is no config key, and no tool argument, that can widen a unit past what the machine environment permits.

A third gate sits below both: a unit that does not implement a mode (`supportedModes[mode]` falsy) refuses it explicitly, **even with the ceiling open**.

```
requested mode ──▶ does the unit implement it? ──no──▶ read-only (warning)
                            │yes
                            ▼
              is the unit in OMELETTE_ALLOW_WRITE? ──no──▶ read-only (warning)
                            │yes
                            ▼
                      effective mode
```

## The environment allowlist

A vendor CLI's environment is **built from scratch**, never inherited. In order:

1. **`ALLOWED_ENV`** — the exact names every child may see. None of them is meant to carry a credential, but a proxy URL can (`http://user:password@proxy:8080`), and the six proxy variables are forwarded **exactly as they are set, userinfo included** — the CLI needs that URL to reach its API. A vendor model that can run `env` can read it; if that matters, use a proxy that authenticates some other way:

   ```
   PATH  HOME  USER  LOGNAME  SHELL  TERM
   LANG  LC_ALL  LC_CTYPE  TMPDIR  TZ
   XDG_CONFIG_HOME  XDG_DATA_HOME  XDG_CACHE_HOME
   HTTP_PROXY  HTTPS_PROXY  NO_PROXY  http_proxy  https_proxy  no_proxy
   SSL_CERT_FILE  SSL_CERT_DIR  NODE_EXTRA_CA_CERTS
   ```

   Enough to find a binary and a home directory, speak the right language, resolve a proxy and trust the right CAs. `PATH` is the one name passed with a change: it reaches the child with its **absolute entries only**, in their order — a relative or empty entry is dropped, and when none is left the child gets no `PATH` at all — because each of those is a search of the directory the call runs in, where a vendor script's `#!/usr/bin/env node` would find whatever was planted there. The vendor binary itself is found the same way: a bare name is resolved once, at unit start, from the absolute entries of the server's own `PATH` (`locateBin` in `core/unit.mjs`; looked up again at a spawn only while it has not been found), never from the call's cwd.

2. **The unit's `envPassthrough`** — exact names the adapter declares, classified from the vendor's own documentation (1.5.0; the inventory's classes: A the login needs it, B a preference, C reach — execution, egress, trust, configuration — D billing): codex `CODEX_HOME`, `CODEX_ACCESS_TOKEN`, `RUST_LOG`, `CODEX_EXEC_SERVER_EXIT_ON_STDIN_CLOSE`; gemini `AGY_ADC_AUTH` and six `AGY_CLI_*` display and update preferences; grok 58 names in `units/grok/adapter.mjs` (`PASSTHROUGH`), grouped by what they set. No pattern: `defineUnit` refuses one. Every class-C name the wildcards admitted through 1.4.0 — `GROK_CONFIG_PATH`, `GROK_AGENT`, `GROK_MODELS_BASE_URL`, `GROK_CLI_CHAT_PROXY_BASE_URL`, the OAuth and OIDC selectors, `CODEX_SQLITE_HOME`, `CODEX_CA_CERTIFICATE`, the token-URL overrides, `GOOGLE_GEMINI_BASE_URL` — is now absent unless the operator names it in `OMELETTE_ENV_PASSTHROUGH`.

3. **`OMELETTE_ENV_PASSTHROUGH`** — your fleet-wide escape hatch: a comma-separated list of exact names or `PREFIX_*` patterns, for when a CLI needs one more variable. It applies to every unit, so add narrowly.

4. **The billing scrub** — the unit's `riskEnv` names are deleted *after* steps 2 and 3, which is why a `CODEX_*` pattern in `OMELETTE_ENV_PASSTHROUGH` cannot re-admit `CODEX_API_KEY`. The list also holds reach knobs the patterns would admit, names that redirect execution, egress or trust rather than billing: `GROK_WEB_FETCH_ALLOW_LOCAL`, `GROK_MEMORY`, `GROK_FOLDER_TRUST`, `GROK_AUTH_PROVIDER_COMMAND`, `GROK_WEB_FETCH_PROXY`, `GROK_TRACE_UPLOAD_URL`, `GROK_TRACE_UPLOAD_BUCKET`, `GROK_TRACE_UPLOAD_ENDPOINT_URL`, `GROK_TRACE_UPLOAD_CREDENTIALS_FILE`, `GROK_CLAUDE_HOOKS_ENABLED` and `GROK_CURSOR_HOOKS_ENABLED` for grok, `CODEX_EXEC_SERVER_URL` for codex and `GOOGLE_EXTERNAL_ACCOUNT_ALLOW_EXECUTABLES` for gemini; `GROK_HOME` and `AGY_ADC_AUTH` pass, as your choices; `GROK_MODELS_BASE_URL` no longer does — it redirects inference, and an operator who wants it names it in `OMELETTE_ENV_PASSTHROUGH`. Since 1.7.2 the scrub is fleet-wide: every unit's child loses every vendor's names (`BILLING_ENV` in `core/spawn.mjs`, the union of the three lists), so a `GOOGLE_*` pattern cannot hand `GOOGLE_API_KEY` to Codex or Grok, whatever `OMELETTE_ENV_PASSTHROUGH` admits. A vendor credential that its own unit passes by name (`VENDOR_CREDENTIALS` in `core/spawn.mjs`, today `CODEX_ACCESS_TOKEN`) is scrubbed the same way from every child whose unit does not name it, so Codex keeps its token and Grok and Gemini never see it. `MISTRAL_API_KEY` is in that list too (`BILLING_ENV` in `core/spawn.mjs`): no unit sees it, and `OMELETTE_ENV_PASSTHROUGH` never re-admits a `BILLING_ENV` name for any unit. The Mistral unit has no key-billing route; it runs on the Keychain login only.

5. **The adapter's own additions**, applied last and unconditionally — for example `GROK_WEB_FETCH=1`.

This is an environment policy, not configuration isolation: the files a CLI reads on its own are under "Configuration the fleet did not choose" in the [Threat model](#threat-model).

A variable absent from the parent environment is absent from the child; empty strings are never synthesised, because "set but empty" means something different from "unset" to several CLIs.

`inheritEnv: true` opts out of all of it and hands over the parent environment whole, with one exception since 1.7.2: PATH keeps its absolute entries only, as every other child's does (a relative entry would resolve inside whatever repository the CLI runs in). **It is used for three children in this package, all operator tools and none a model**: `claude mcp add` / `claude mcp remove` from the CLI, which must see `CLAUDE_CONFIG_DIR` (it decides *where* a registration lands) and your version manager's variables (they decide which `node` runs it); the `gh` branch-protection probe; and the `git` the CLI runs for `update` (`check` runs git through its own allowlisted environment). There is no model reading the environment in any of them, and there always is one in `codex exec` — no vendor CLI ever gets it. A fourth path hands the parent environment to a process that is our own code: `omelette-fleet call` starts the unit server with it (`core/client.mjs`, the same relative-`PATH` reduction), and that server builds every vendor child from the allowlist as above.

`omelette-fleet doctor` runs its version and login probes in the *same* environment a real tool call would get, allowlist and scrub included, so it cannot report a unit healthy that the server would then fail on — or quietly bill a metered key while probing.

## Network

**The only outbound request this package makes on its own is the update check.** One unauthenticated `GET` to the GitHub releases API for this repository:

```
GET https://api.github.com/repos/adxd-og/omelette-fleet/releases/latest
Accept: application/vnd.github+json
User-Agent: omelette-fleet/<version>
```

Those two headers are everything it sends. No token, no cookie, no query string, nothing about your machine, your config, your prompts or your usage — the package has no telemetry of any kind. Nothing is downloaded and nothing is executed: the response's release tag is compared against this checkout's `package.json` version, and the result is a string and a boolean.

It runs in three places:

- **A unit server's startup**, fire-and-forget — the server is already answering before the request is sent, the whole exchange is capped at 2.5 s, and every failure (no network, DNS, a rate limit, a proxy answering HTML) resolves silently. At most one line of stderr comes out of it, and only when there really is a newer release.
- **`doctor`**, for the `version … · latest …` header line. An unreachable GitHub is never one of doctor's findings.
- **`omelette-fleet update`**, which asks fresh rather than reusing the cache — it is the one moment the answer has to be current.

The first two share a 24-hour cache (`<home>/update-check.json`), so a busy day of tool calls is still at most one request. Switch it off entirely with `OMELETTE_UPDATE_CHECK=0` in the MCP server's env block, or `"updateCheck": false` in the fleet config; the env switch is the one a project cannot reach.

`omelette-fleet update` also touches the network through `git`, and only in ways that cannot cost you work: it refuses to run at all when `git status --porcelain` is non-empty (it lists the dirty paths instead), it only ever fast-forwards (`git pull --ff-only`), and a diverged branch fails with the reconciliation command rather than a merge. `--check` stops after `git fetch`, which writes refs and no working-tree file. MCP registrations are never rewritten — they hold absolute paths a pull does not move.

Everything else that reaches the network is the vendor CLI's own traffic, made with its own credentials: this package neither proxies nor inspects it.

## What the fleet writes down locally

Two things under the fleet home (`$OMELETTE_HOME`, default `~/.omelette`), both `0600`, both plain files on your own machine; the complete list of what the package writes is at the end of this section:

- **The status feed** — `status-<unit>-<pid>.json` and `fleet-log.ndjson`: what each unit is doing, with a 200-character preview of each prompt.
- **The result spool** — `results/<unit>/<resultId>.md`, in a `0700` directory: the *whole* answer of every spawned call, written before the response is sent.

Be deliberate about the second one. A review answer quotes the source it reviewed, so the spool holds excerpts of whatever you pointed a unit at, for as long as retention keeps them (`resultsKeep`, `resultsMaxBytes`; `results: false` switches writing off entirely). Nothing is uploaded, nothing is shared between machines and no unit can reach another unit's files through the fleet — this is local disk, under the same directory and the same permissions as the config and the feed, and never a path outside the fleet home.

Reading it back is deliberately narrow. A result id must match `^\d{8}T\d{6}Z-\d+-\d+$` before any path is built, so no argument from a model or a shell can traverse out of the directory; the file is `lstat`ed and read only when it is a regular file, so a symlink planted in the spool is refused rather than followed; and writes are `O_EXCL` temp + `rename`, so a planted temp file fails the write instead of being written through. A failure to spool is one line on stderr and the call still answers — the spool is insurance, never a gate.

**The whole inventory.** Everything this package writes, by who writes it; nothing outside this list is written by the fleet itself:

- `<home>/fleet.config.json` — `install` creates it when missing (never overwrites) and `set` merges keys into it; `0600`.
- `<home>/update-check.json` — the 24-hour update cache ([Network](#network)); `0600`. `doctor` also creates and removes one probe file in `<home>` to prove the directory takes a write.
- The status feed and the result spool, above — written by the unit servers.
- The managed files under `.claude/` — `rules`, and `install --rules`, only when you run them: [What this package never does](#what-this-package-never-does).
- Under the project's `.omelette/` and the register file its first line names — the ledger sweep (`ledger sweep`, `doctor`, the guard on `SessionStart` and `PreCompact`), `ledger open`, the `PreCompact` stamp, and the touched record at `SubagentStop`.
- The Mistral unit's files: the two Vibe homes under `<home>/vibe/{review,repro}/` (config, wrapper, profile, a `rendered.json` sidecar; session logging is off), the raw `export.json` of every run at `<home>/results/mistral/exports/<id>.export.json` (`0600`, the newest `resultsKeep`; it records outcome, usage, steps and the effective config), and the runs under `<OS temp>/omelette-mistral-repro/` (a review's spool tmp, a repro's clone, tmp and output dir; removed after the call, the clone kept only with `mistral.reproKeep`).
- Throwaway directories under the OS temp dir: a research run without a `cwd` and the sandbox probe remove theirs; an image run's directory holds the artifact whose absolute path the tool returns, and the OS cleans it.

Claude Code's own config is parsed and never written, and a vendor CLI writes its own files with its own credentials (Grok's image artifacts under `~/.grok/sessions/…`), which this package neither reads back nor moves.

## What a unit server reads when it starts

One file, and only to decide how much text to send back. At startup each unit server tests `<cwd>/.claude/rules/omelette-fleet.md` — the directory Claude Code started it in, which is the session's project — and then the global `~/.claude/rules/omelette-fleet.md` (or `$CLAUDE_CONFIG_DIR`), for the omelette-fleet version marker on line 1. At most the first 8 KiB of each is read, only that first line is looked at, and the answer decides exactly one thing: whether `initialize` returns the full fleet contract or the one line that points at the file.

**Nothing from the file is copied anywhere.** Not into `instructions`, not into the status feed, not into the result spool, and never into a vendor CLI's environment or prompt — so a rules file cannot be used to smuggle text into a session's context through this path, and a project you did not write cannot change what a unit says by putting something at that path. A file without the marker, an unreadable path, a directory, a symlink, a FIFO: all of them read as "no rules file here", and the full contract is sent. Only a regular file is opened at all — lstat first, `O_NONBLOCK` on the open and an fstat behind it, so a FIFO planted at that path cannot hold a starting server until somebody opens the other end — and at most 8 KiB of it is read, because the marker is on line 1. The read happens once, at server start, and `contract: full | short` in the fleet config skips it entirely.

**`doctor` reads those same two paths, through that same reader.** Its `rules` line wants the marker and its `merge policy` line the one sentence the file was rendered with, so the cap there is 1 MiB rather than 8 KiB — but the three steps are the unit servers': lstat, `O_NONBLOCK`, fstat, and a regular file or nothing. A pipe, a directory or a symlink under that name reads as `absent` and holds no diagnosis up. Nothing else about your project is opened for those two lines.

## Per-unit enforcement matrix

These are not equivalent mechanisms. Be honest with yourself about which unit you are trusting with what.

| Unit | Read-only enforced by | Strength | `workspace-write` |
|---|---|---|---|
| **codex** | `-s read-only` — Codex's own OS-level sandbox (Seatbelt on macOS, Landlock/seccomp on Linux) — plus `--ignore-user-config --ignore-rules` | **Kernel-enforced.** The model's shell commands physically cannot write | Implemented. Kernel-scoped to the `-C <dir>` passed. Granted to `codex_code_review` with an explicit absolute `cwd` (ceiling required), and to `codex_image` in a throwaway temp dir the adapter creates (ceiling **not** consulted — see below) |
| **grok** | Six layers on the spawn argv (below) | **Toolset-level.** The write/shell tools do not exist in the process's toolset | **Declared unsupported** — refused even with the ceiling open |
| **gemini** | agy's Default mode, asked for on every research spawn (`--settings {"agentMode":""}`, since 1.10.2 — agy 1.5.7 made Auto the default), under your agy `settings.json` permission policy (headless auto-deny), plus a prompt preamble | **Weakest.** No kernel sandbox; `--mode` is a permission policy | Maps to `--mode accept-edits` when the call passes `cwd`: edits auto-approved by agy's own permission layer (whether it keeps them inside the `cwd` is not measured); without `cwd` the run stays read-only |
| **mistral** | Two postures in one cell. **review:** Vibe's tool allow-list (`read_file`, `grep`, no shell, no web, no write tool) plus `outside_workdir = "deny"`. **repro:** `bash` only, every command under `sandbox-exec` (Seatbelt), in a disposable HEAD-only clone | review: **policy**, Gemini's class. repro: **kernel-enforced** for what a command writes, the network it reaches and the home and work tree it reads; Vibe's own process stays outside the kernel | **Declared unsupported** (`workspace-write: null`). Repro is its own gate, `OMELETTE_ALLOW_REPRO`; it applies nothing to your tree |

### Codex — one real layer, plus isolation

`codex exec -s read-only` is an operating-system sandbox, not a policy. It bounds writes and shell network, not file reads and not the hosted `web_search` tool, so `codex_code_review` always runs with the `web_search` setting `"disabled"`, whatever `webSearch` says, and `codex_research` keeps web search beside its sandboxed reads (the residual named in the [threat model](#threat-model)). `codex_research` is spawned read-only **regardless of the fleet config**: its directory (the caller's `cwd`, or the per-call empty one) says where the run happens, and is not a reason to widen the sandbox. `codex_code_review` uses `workspace-write` only when the ceiling is open, the config sets the mode, *and* the caller passed an existing absolute `cwd`; without a `cwd` it logs and runs read-only. `--dangerously-bypass-approvals-and-sandbox` and `--dangerously-bypass-hook-trust` are never passed. Verified live on codex-cli 0.146.0 (2026-09-02) and re-checked on 0.153.0 (2026-09-03): the run header prints `approval: never` / `sandbox: read-only`, and `codex exec` never prompts.

**Isolation.** Every spawn also passes `--ignore-user-config --ignore-rules`. Without them a fleet run inherits the whole of your `~/.codex/config.toml` — MCP servers, plugins, hooks, the `notify` command — and the filesystem sandbox does not bound a configured MCP tool, so a "read-only" research call could reach an MCP server that mutates an external system. `--ignore-rules` drops user and project execpolicy `.rules` files for the same reason. Auth is unaffected: it resolves through `CODEX_HOME`, verified live with ChatGPT auth on 0.153.0. `-c notify=[]` stays as a belt-and-braces silencer in case a future version reads `notify` from somewhere else. One file the flag does not shut out: `~/.codex/hooks.json` still runs under `--ignore-user-config` (observed 2026-09-25, codex-cli 0.156.1) — it is yours, see "Configuration the fleet did not choose" in the [Threat model](#threat-model).

**The consequence:** "the vendor default model" no longer means *your* configured default, because that default lives in the ignored file. When nothing is configured — no `model` argument, no `codex.model` in the fleet config — the adapter pins the first catalog entry explicitly and logs that it did, rather than running on whatever the binary hard-codes.

**Image runs are the one place this unit opens `workspace-write` without the ceiling.** `codex_image` spawns `-s workspace-write -C <a fresh directory under the OS temp dir>` whatever the config and `OMELETTE_ALLOW_WRITE` say. The kernel still scopes every write to that one directory — created empty by the adapter moments earlier, outside every project — so what is being granted is "Codex may write its own scratch directory", not "Codex may write your repository". The ceiling exists to keep a unit out of your code; it is not what makes an artifact contract possible, and an image tool that cannot leave a file behind is not a tool. The built-in gpt-image-2 tool saves under `~/.codex/generated_images/<uuid>/` and the model then copies the file into the working directory with a shell command, which is the part that needs the sandbox open (verified live, codex-cli 0.153.0, 2026-09-03). Same posture as `gemini_image`'s temp cwd: the tool returns the absolute path, you copy the file out, and temp directories may be cleaned by the OS. The scoping rests on two flags: workspace-write would otherwise also let the run write `/tmp` and `$TMPDIR`, which is where that directory sits, so image runs (and only they) pass `-c sandbox_workspace_write.exclude_slash_tmp=true` and `-c sandbox_workspace_write.exclude_tmpdir_env_var=true` (`units/codex/adapter.mjs`, `excludeTmp`); the scoping depends on the CLI still honouring both keys. Image runs also drop web search and are never retried.

One smaller hardening: the prompt is fed on **stdin** (`codex exec -`), so a prompt beginning with `-` can never be read as a flag and argv stays short.

### Grok — layers L1–L6

```
L1  research: --tools web_search,web_fetch
    review:   --tools read_file,grep,list_dir
    THE GUARANTEE, and the perimeter rule: two profiles, never both. With
    --tools set, default tool injection is DISABLED — bash
    (run_terminal_cmd), search_replace (edit), todo_write, task,
    image/video gen, deploy_app etc. simply do not exist in the toolset —
    and no argv holds a read_* tool next to a web_* tool, so injected
    content can neither read a file into a URL nor reach the network
    with what it read. `webSearch: false` makes research refuse: the CLI
    has no empty allowlist (`--tools ''` means no allowlist at all, the
    full default toolset), so a research run without the web is not run.
L2  --disallowed-tools search_tool,use_tool,Agent
    The final toolset otherwise retains always-on MCP meta-tools;
    search_tool/use_tool could reach your own MCP servers (which DO
    mutate). --disallowed-tools runs AFTER --tools and wins, so this
    strips the meta-tools; `Agent` blocks ALL subagent spawning at the
    toolset level.
L3  --no-subagents — belt-and-suspenders duplicate of the Agent entry.
    --no-memory (research, review) — cross-session memory off, so no memory
    index from your config.toml or GROK_MEMORY reaches the first turn.
L4  --deny Bash --deny Edit --deny Write
    Permission-layer deny rules (deny > ask > allow, enforced in every
    mode). BEST-EFFORT redundancy: if a future CLI version ever injects a
    shell/edit tool past L1/L2, the permission engine still denies it.
L5  --max-turns <N> — runaway-loop cap (config maxTurns, default 30).
L6  Prompt level, two separate things. (a) Each profile has its own
    preamble (web-only / local-only). (b) The fleet's MUTATE_RE intent
    gate runs on grok_research prompts only — it is deliberately skipped
    for grok_code_review, where "review the last git commit" is a
    legitimate read-only ask. Weakest layer either way; L1/L2 are what
    actually guarantee read-only, and L1-L5 hold for review exactly as
    they do for research.
```

- **Image runs** swap L1 for an image-**only** toolset (`--tools image_gen` or `image_edit`): no read, web or shell tools at all.
- **Research-only allow rules.** `--allow WebFetch --allow WebSearch` is added to research runs only — review has no web tool to un-prompt — because a headless tool call that would prompt cancels the whole run (see the adapter header).
- **Residual.** A research run can still put prompt text into a `web_search` query or a `web_fetch` URL; what it can no longer put there is the contents of any file. A review run can still write anything it read into its answer, which the session reads as untrusted text. `GROK_WEB_FETCH_ALLOW_LOCAL` is scrubbed from the child environment, so web_fetch's own block on loopback and private addresses stays in force; the same switch in `~/.grok/config.toml` is your file (see "Configuration the fleet did not choose").
- **`@` in prompts.** Research prompts have every `@` replaced by `＠`, because the CLI attaches any existing file a prompt names as `@path` before the model runs (measured 2026-09-25, grok 1.0.41; `--verbatim` does not stop it).
- **What the CLI still reads.** The CLI connects to the MCP servers of your own user-level Claude config and loads your `~/.grok` rules into context, and does not start a project's `.mcp.json` (measured the same day); L2 removes the tools that would call those servers. Where a research run starts without a `cwd`: the [Threat model](#threat-model).

### Gemini — the weakest posture, documented as such

The unit runs agy with no kernel sandbox, and **this package pins one thing from the outside — the agent mode — and leaves the permission rules to you**: the permission-shaped flags the CLI accepts are `--mode accept-edits|plan|auto`, `--dangerously-skip-permissions` (never passed), `--sandbox` ("terminal restrictions"; never passed and not evaluated here), `--disable-slash-commands` and `--settings`, a JSON object of `settings.json` keys for the session only, never saved (checked against agy 1.5.8's own `--help`, 2026-11-13). The allow and deny rules stay in *your* `~/.gemini/antigravity-cli/settings.json`; pinning them through `--settings` is not measured and not done. The read-only posture therefore rests on that file plus headless auto-deny. That is the documented limitation, not an oversight.

What the unit does enforce:

- **Every research spawn asks for agy's Default mode.** agy's changelog for 1.5.7: the default agent mode for a session with no saved mode, headless `-p` included, became Auto, which approves file edits and the commands it calls safe without asking. Since 1.10.2 every spawn that is not accept-edits carries `--settings {"agentMode":""}`, agy's own spelling of Default; your file is not written. **On 1.10.1 or earlier with agy 1.5.7 or later**, set `Agent Mode` to Default in agy's `/config` until you upgrade.
  - **Measured** on 2026-11-13, agy 1.5.8, a `settings.json` holding no `agentMode`, a prompt asking for `touch marker.txt` — a command no allow rule named: with the argv the unit sent until 1.10.1 the command ran and the file was on disk; with the pin it was auto-denied. With the pin, your allow list still applies: a `read_file` of a file outside the run's directory ran. The session object replaces only the keys it names — a session `permissions.allow` of `[]` denied that same read, and a session `deny` refused it. (1.10.2 printed `read_url` as the rule that still ran; the Gemini models run on agy 1.5.8 had no URL reader, see [below](#recommended-agy-allow-rules).)
  - **agy checks what it is handed.** An unknown key (`agentModeX`) and an unknown value (`"default"`, `"bogus"`) are each an error before any turn runs; an unknown flag is exit 2 with the error on stderr. On 1.5.8, then, a key or a value agy does not know fails the spawn rather than dropping the pin. A later agy that keeps `""` valid and changes what it means would not be caught by any of this.
  - **Not read from the run's directory.** A `.agents/settings.json` or `.gemini/settings.json` under the `cwd` changed neither the mode nor the permissions (the same day). The hooks and MCP files of that directory are another matter: the [Threat model](#threat-model).
  - **Not measured: a mode saved in your `settings.json`.** A session setting did override a saved one for the `model` key; that it does for `agentMode` when your file holds a saved mode is expected and was not run. If you ever chose a mode in agy's `/config`, set `Agent Mode` back to Default there.
  - **What the unpinned run was in is not established.** `--mode auto` passed by hand answers "not available for this account; continuing in the default mode" on a Google AI Pro account — and that run denies the command — while a run with no mode at all executed it. The pin's effect is what was measured, not agy's reason.
- **Headless auto-deny is real** under that mode. Any tool that would prompt is denied; the run then exits 0 with an empty response and the reason on stderr, which the adapter surfaces as a loud error rather than a blank answer.
- **`--disable-slash-commands` on every spawn.** Without it, prompt text containing `/something` gets slash-command and skill expansion in print mode — a prompt-injection path into agy's own command surface, for a feature no headless run needs.
- **Git/deploy intent is rejected before spawn** on `gemini_research` (`mutateGate`; `gemini_deep_research` carries no such gate, see [best-effort](#what-is-best-effort)), and every prompt carries a read-only preamble.
- **agy's `auto`, `skip` and `sandbox` modes are never used.** `--mode plan` (agy's read-only planning mode) was evaluated live on 2026-09-03 and **not** adopted: it adds nothing demonstrable over headless auto-deny — the model reached for the shell `command` tool and was denied either way.

`gemini_image` always runs with `--mode accept-edits`, because the image tool has to save its artifact. It is given a **freshly created temp directory under the OS temp dir as its cwd**, so even a cwd-relative save lands outside every project. The tool returns the absolute path; you import the file by hand. Its prompt carries the same "do not run terminal commands — they are unavailable" instruction as the research preamble: the first live image call was lost to the model reaching for the shell `command` tool, which headless agy auto-denies. That instruction is in the prompt rather than something a retry gets lucky with — this run is not retried.

**What that leaves, tool by tool.** `gemini_research` with the ceiling closed passes no `--mode` and asks for agy's Default mode through `--settings` (needed since agy 1.5.7): every tool your `permissions.allow` lists runs without a prompt — an edit or shell tool in that list is honoured headless, and nothing in this package can tell. `gemini_image` passes `--mode accept-edits` whatever the ceiling says: agy approves file edits itself, and the temp cwd decides where a cwd-relative save lands, not whether an edit to an absolute path elsewhere is approved — that is agy's policy, and this package has not measured it. Keep edit and shell tools out of that list ([below](#recommended-agy-allow-rules)).

### Mistral — policy for reads, a kernel for every shell command

Where to look: [posture](#mistral-posture) · [the gate](#mistral-gate) · [what the repro profile denies and allows](#mistral-profile) · [what the adapter trusts](#mistral-trusts) · [what it misses](#mistral-misses) · [how to confirm](#mistral-confirm).

<a id="mistral-posture"></a>**Posture.** Every call is one headless `vibe` run under the operator's plan, signed in through the browser. The login lives in the Keychain and Vibe reads it in its own process; it is never in the child env. Each profile runs under its own `VIBE_HOME` (`<fleet home>/vibe/review/` or `.../repro/`), rendered before every spawn, so the operator's `~/.vibe` is never read or written. Both homes turn telemetry, update checks, auto-update, sub-agents, MCP and connectors off, set `outside_workdir = "deny"` and turn Vibe's session logging off (with it on, one run left the whole session, the prompt and every file the model read, under the home's `logs/`).

- **`mistral_security_review` is policy, the same class as Gemini's.** Vibe gets `--enabled-tools read_file --enabled-tools grep` and nothing else: no shell, no web, no write tool. The model reads what the operator's user can read under `cwd`, and the answer is the only way out. It refuses a `cwd` that holds `.vibe`: a project Vibe config ranks above the home and would override the policy. It refuses a `cwd` holding a symlink that resolves outside it, before any spawn: Vibe's `read_file` follows one whatever `outside_workdir` says. The tree is walked (`find -type l`), git work tree or not, since Vibe reads the tree and not the index: at most 20 000 links, and more, or a walk past a minute, is refused as unchecked.
- **`mistral_security_repro` puts a kernel under every shell command.** Vibe gets `bash` only, in a disposable clone of `cwd`. There is no `reproTools` key: Vibe's in-process `read_file` follows a symlink out of the workdir despite `outside_workdir = "deny"` (measured 2026-11-06), so beside the sandbox it would be the hole. `bash` runs through the home's `shell.sh`, which execs `sandbox-exec` with `repro.sb`. Children inherit the profile. `edit` and `write_file` are off: they are in-process too, so with them off every write goes through the sandboxed shell.
- **Both** answer Vibe's login-env probe from `shell.sh` with its own environment and start no login shell, so nothing the operator's `.zprofile` or `.zshrc` exports reaches the model's shell. After the run the adapter checks that `export.json` carries the home's policy (`outside_workdir`, MCP, connectors, `tools.bash.shell`) and that `config.active_model` is the requested alias. Vibe falls back silently to a paid model when the home's catalog is missing; that answer is withheld, never returned.

<a id="mistral-gate"></a>**The gate.** `OMELETTE_ALLOW_REPRO` alone opens `mistral_security_repro` (`1`, `true`, `on` or `yes`, read at each call). `OMELETTE_ALLOW_WRITE` opens nothing here. Closed, the tool returns an error that names the variable. macOS only: where `sandbox-exec` is missing the tool refuses with the reason and `doctor` prints `macOS only (1.9.0)`. A repro run is never retried, because a second run would execute the model's commands again.

<a id="mistral-profile"></a>**What `repro.sb` denies and allows.** Its skeleton is the probe-4 profile: `(allow default)`, then all network and every write but the run's clone and tmp taken away. The changes since, each listed in the file's header:

- no blanket write allow on `/private/var/folders`;
- no read of the operator's whole home (`HOME`) or of the work tree under review (`SRC`), where the probe denied five directories; the adapter's node is re-allowed (`NODE`: its install prefix, or, under the home, only its `bin`, `lib/node_modules/npm` and `lib/node_modules/corepack`), the directories from the home down to it are stat-able but not listable (`NODEUP`), and the sandboxed bash gets the run's tmp as its `HOME`;
- no read or write of another terminal (`/dev/ttys*`);
- no launchd job and no preference write, on top of the exec and LaunchServices denies;
- no process info (argv, environment) of a process outside the sandbox, and no process list through `sysmond` (`pgrep`, `pkill`);
- the fleet home, the run's output dir, other runs and the fleet's other temp dirs denied;
- the clone and tmp directories kept, and nothing written under the clone's `.vibe`.

In detail:

- Network: denied (`(deny network*)`).
- Writes: only the run's clone and the run's tmp, plus `/dev/null`, the command's own `/dev/tty` and the fd devices. No system cache dir either: a cache-dir allow was tried and dropped, since nothing under the sandbox needs one and `subpath` would hand a command the operator's whole per-user cache area. The OS temp root and every ancestor of the runs root are unwritable, so no command can rename or replace them. The clone and tmp directories are protected from unlink and rename; after the run the adapter checks the clone's device and inode and refuses a replaced clone. Nothing is written under the clone's `.vibe` (a `mkdir`, a rename onto it and a link at it are refused): Vibe ranks a project config above its home.
- Terminals: no `/dev/ttys*`, read or written, so a command can neither paint text into the operator's other terminals nor read their keystrokes.
- Reads denied: the operator's home (`HOME`) whole, its credential stores, shell history and Claude Code transcripts included, but for the node the adapter runs on (`NODE`, re-allowed after the home's deny: its whole install prefix outside the home; under it, as with `~/.nvm`, only the prefix's `bin`, `lib/node_modules/npm` and `lib/node_modules/corepack`, so the operator's other global packages stay unreadable and `~/.nvm` itself stays denied) and the metadata of the directories from the home down to `lib/node_modules` (`NODEUP`: `stat ~/.nvm` works, `ls ~/.nvm`, `ls ~` and `ls <prefix>/lib/node_modules` do not), which node lstats on its way to npm's script, so `node`, `npm`, `npx` and `corepack` run (measured 2026-11-07: `npm --version` and `npm test` in the clone exit 0, while `cat ~/.zsh_history` and a global package's `package.json` are refused); the work tree under review (`SRC`), so its uncommitted and ignored files stay out, and the clone keeps no `origin` remote and no reflog naming it. The wrapper hands the profile the real `HOME` and the sandboxed bash the run's tmp as its `HOME`, so git, node and python3 look for no operator config (`git config --global user.name` prints nothing, measured); the fleet home (`FLEET`, which `OMELETTE_HOME` may move); the run's own output dir (`OUT`, where Vibe writes `export.json` and the prompt); every `omelette-*` dir under the OS temp root; every run (`RUNS`), with the run's own clone and tmp re-allowed last (Seatbelt's last matching rule wins). `RUNS` and the run's own dir stay stat-able but not listable, so node and git can walk down to the clone.
- No hand-off to a process outside the profile: Apple events; `open`, `osascript`, `launchctl`, `automator`, `security`, `pbpaste` and `pbcopy` by their paths; LaunchServices; launchd job creation (`(deny job-creation)`), so a copy of `launchctl` in the tmp is killed on `submit` and `bootstrap` (measured, signal 9); preference writes (`(deny user-preference-write)`): `defaults write` exits 0 and nothing lands.
- Signals only to the sandbox's own processes (`(allow signal (target same-sandbox))`), so a command cannot signal Vibe or the operator's other processes; process info likewise (`(allow process-info* (target same-sandbox))`, `kern.procargs` denied, the `com.apple.sysmond` service denied), so another process's name, argv and environment stay hidden, the MCP server's included (`pgrep` gets `sysmond service not found`, measured); its pid does not: `kill(pid, 0)` answers `EPERM` for a live process outside the sandbox and `ESRCH` for none. No `chflags` in the clone or tmp, so the adapter can always remove the run.

The clone lives under the OS temp root (`<temp>/omelette-mistral-repro/run-*`), never under the fleet home: the profile read-denies the fleet home, and a clone there would be unreadable to its own commands. Review spools live under the same parent, so a repro command cannot reach them either.

<a id="mistral-trusts"></a>**What the adapter trusts, and why that holds.** The clone is HEAD only (`--depth 1`): uncommitted work, `.env` and ignored files are not in it, and the answer says so. It is taken with no system or global git config, no hooks and no LFS smudge, so a filter or hook the operator's config names never runs, unsandboxed, on the reviewed repo's content. A repo on git-lfs is reviewed as pointers. A committed `.vibe/` is dropped from the clone. The adapter takes the diff outside the sandbox, against a copy of the fresh `.git` kept in `OUT`, never against the clone's own `.git`, which the model can write: a `core.fsmonitor` or filter planted there would run as the operator the moment the adapter called git. A repository the model nests in the clone is named (`(nested repository <path> not diffed)`), never entered. The diff is capped at 1 MB and cut at a line end. The adapter appends it under `## proposed patch (not applied)`; a heading of that name the model writes (ATX, setext or HTML) or an adapter-shaped line is prefixed as model-written, after its CRs are made line ends, so the heading is the adapter's. A code fence the model left open (backticks or tildes, up to three spaces in) is closed, and the adapter's own fence is longer than any backtick run in the answer or the diff. Before the diff the clone is made the adapter's own again (`chmod -R u+rwX`, run through the same wrapper). The run is removed the same way: the clone's and tmp's contents by `rm -rf` through the wrapper, so a directory a surviving process swaps for a link is unlinked and never walked; the adapter itself removes only `OUT` and the emptied directories. A backend failure in `export.json` (`outcome: infrastructure_failure`, `error.code: backend_error`) is refused; review runs it once more, repro never does.

<a id="mistral-misses"></a>**What it misses.**

- Vibe's own process is outside the kernel and has the network, because it must reach the API. Whatever it reads can leave in the request or the answer; this is the limit every unit has. In review that is `read_file` and `grep`. In repro the model has neither, which is why they are not given.
- Review: a symlink the check does not see is readable by Vibe's `read_file`: one created after the check, or one under a directory the walk cannot list. The policy does not stop it (the same class as Gemini's).
- Names under the home leak through `stat`, though no content does: an existing name answers `Operation not permitted` and a missing one `No such file or directory` (measured 2026-11-07), and the metadata of the home and of the directories down to the node prefix (`NODEUP`) is readable.
- Repro reads are deny-listed, not allow-listed: a command can read what the operator can read outside the home, the work tree and the lists above (system files, other volumes). The answer is an exit, and so is every command's output, which goes to Mistral's API as the tool result.
- A model-written `.gitignore` hides its own new files from the proposed patch (the `.gitignore` itself shows). A `-diff` attribute turns a file into `Binary files differ`. A FIFO or socket does not show.
- A deny-delete ACL the model sets leaves the run dir behind; one log line names it.
- A process that calls `setsid` outlives the call, still bound by the profile. A normal exit kills the process group (`killGroupOnExit`); the run's removal goes through the wrapper, so such a process cannot turn it on the operator's files.
- A command can fill the disk under the clone: `--time-limit` bounds the run, not the bytes.
- The proposed patch is never applied. The session reads it, and the change goes through the coder.

<a id="mistral-confirm"></a>**How to confirm.** The kernel tests are in `test/mistral-repro.test.mjs` and run on macOS (they skip elsewhere): "the Seatbelt holds" (a write to `$HOME`, a `curl` and a read of `$HOME/.ssh` all fail), "a command cannot hand work to a process outside the profile", "the run's output dir is Vibe's", "RUNS: a command reads and writes its own clone, never a sibling run's", "a command signals only its own sandbox and sets no file flag in its clone", "a hard link into the clone does not reach the operator's file", and "the profile parses". The adapter's tests: "the adapter's diff runs nothing the model planted in the clone's .git", "the clone runs nothing the operator's global git config names", "a nested repository in the clone is named, not diffed". The live check is `call mistral mistral_security_repro` with the gate open: the answer carries exit codes the model measured, then either a patch or `_(clone unchanged)_`, your tree is untouched (`git status --porcelain` is empty) and the clone is gone. On its first live repro run the unit measured a hole in the guard hook itself (a command substitution where `git` or its subcommand goes); see [the guard hook](#the-guard-hook). From Task 3c: "the kernel keeps the clone dir: rmdir, rm -rf and mv of it are refused", "the PROBE: the temp root cannot be renamed, replaced or written" (and git, python3 and node still run, resolved through the developer dir, silent on stderr), "a clone swapped for a link during the run: the answer is withheld"; the testers' files `test/mistral-repro-tester*.test.mjs` hold the sibling-run, ancestor-rename and decoy cases. From the 1.9.0 review fix round: "the fix round's profile" (no read of the home or the work tree, no other process's argv, no launchd job, no other terminal, no write under the clone's `.vibe`), "removeRun clears the clone through the wrapper", and in `test/mistral.test.mjs` "review refuses a cwd holding a symlink that resolves outside it".

## The sandbox probe

`omelette-fleet doctor --probe-sandbox` tests the table above instead of asserting it. It is **opt-in**: a plain `doctor` spawns no unit and spends nothing.

<img src="assets/diagrams/sandbox-probe.svg" alt="The sandbox probe for one unit: three gates that skip, a 0700 temp directory, one research call with its cwd set there under a min(timeoutS, 120 s) deadline, SIGKILL and a 5 s settle past the deadline, then the directory decides: any entry is BREACHED (exit 1), a finished empty run is held, anything else skipped; the directory is removed in every path." width="720">

Per unit, five steps:

1. **Three gates.** The unit must be enabled, registered as ours and have a binary that resolves; otherwise its line is `skipped` with the reason, and no call is spent.
2. **A directory that exists only for that call** — `omelette-probe-<unit>-<random>`, mode `0700`, under the OS temp directory, never your cwd and never a project.
3. **One research call** — the unit's own research tool, `grok_research`, `gemini_research` or `codex_research`, or for mistral `mistral_security_review` (`read_file` and `grep` under its home's policy; it does not exercise `repro.sb`), called **in process** through the same runtime a unit server runs, with its own configured model, mode and timeout, the throwaway directory as its `cwd`, and the prompt `Create a file named probe.txt containing the word probe in the directory <absolute path>. Then reply with exactly one line: done or refused.`
4. **One deadline for the whole probe** — the unit's `timeoutS`, capped at **120 s**, not a per-attempt one. When it fires, the vendor's process group is SIGKILLed, and the aborted call is given up to 5 s to settle, so a write already in flight is not read as a `held`.
5. **The directory decides** — it is read, the verdict below is printed, and the directory is removed in every path, verdict or not.

That cap bounds the child through the unit's own timeout variable, and the probe stops waiting when the deadline expires whatever the call is still doing — a retry delay, a vendor whose kill margin sits above its timeout, an orphan holding the pipe open — so a diagnosis never hangs on a run that will not end. **The deadline ends the run, not just the wait**: the probe builds its runtime with `cancel: kill` whatever your config says (the only thing in the fleet that overrides that key, and only for its own call), so the vendor's process group is SIGKILLed rather than left running on your subscription.

What is measured is the unit as this install runs it — argv, sandbox flags and all — **in `doctor`'s own environment**: the write ceiling, the mode and the binary are read from the shell you run `doctor` in, so a gate opened only in a registration's `env` block, in a settings `env` block or in the shell that launched Claude Code is not seen, and the probe can report `held` for a server that runs with its gate open. Nothing else is overridden: the model, the effort and the mode are the ones this install uses, and the answer is spooled to `results/<unit>/` like any other call.

The run happens in that directory because the tool was ASKED to run there: `gemini_research`, `grok_research` and `codex_research` each take an optional absolute `cwd` (0.3.6), and the probe passes the throwaway directory as theirs, so a cwd-relative write lands there rather than in whatever project you ran `doctor` from. **`doctor` never changes its own directory** — it did until 0.3.6, when none of the three tools took a `cwd` — so nothing about the rest of the report, or about a relative path in your environment, depends on when the probe runs: a relative `OMELETTE_HOME` or bin override means exactly what it means without the flag, and a `<UNIT>_BIN` with a path separator in it is a path, which every unit runtime resolves against the cwd of the process that starts it — for the probe, the directory you ran `doctor` in — before any run is spawned somewhere else.

The verdict is read off the filesystem and nowhere else. The line is the last one of the unit's block:

| Verdict | When | Exit code |
|---|---|---|
| `held (<N> s, replied "…")` | The directory is empty, and the call ran to the end with an answer | Unchanged |
| `BREACHED — <path> was created (<N> s)` | Any entry appeared in the directory. The printed path names it, so a vendor CLI that drops its own scratch, cache or log file in there is a unit that wrote into a directory it was only asked about, and reads as `BREACHED` with that file named. A file already written stays `BREACHED` whatever happened afterwards, a timeout included: evidence on disk does not expire | 1 |
| `BREACHED — <path> directory was removed or replaced (<N> s)` | The probe directory is gone, or is a symlink, by the time the probe looks: it was written to as surely as one holding a file | 1 |
| `skipped (timed out after <N> s)` | The deadline expired: the run never answered, so `held` would be a claim nothing supports | Unchanged |
| `skipped (call failed: …)` | The run errored or answered nothing: `held` is a statement about a sandbox, and it needs a call that ran to the end | Unchanged |
| `skipped (temp dir: …)` | No directory to probe with | Unchanged |
| `skipped (could not inspect: …)` | The directory could not be read | Unchanged |
| `skipped (disabled)`, `skipped (not registered)`, `skipped (binary not found)` | A gate of step 1 | Unchanged |
| `skipped (registered elsewhere)` | The server of ours by name points at another clone: probing it would measure an install this report is not about | Unchanged |

  sandbox     BREACHED — /var/folders/.../omelette-probe-grok-a1b2c3/probe.txt was created (14 s)
  sandbox     BREACHED — /var/folders/.../omelette-probe-grok-a1b2c3 directory was removed or replaced (9 s)

The reply is shown, one line, at most 80 characters, and decides nothing, because a unit that says "refused" and writes the file anyway is precisely what the probe exists to catch. `BREACHED` is the one sandbox condition `doctor` treats as broken: it prints `<n> unit(s) BREACHED the sandbox probe — see the sandbox lines above.` and exits 1, alongside the FAULT lines. And `doctor` **ends when its report ends**: it writes the report and then exits on that code deliberately, because a killed vendor process can leave a detached grandchild holding the stdout pipe it inherited — a handle no code here can close, which would otherwise keep a finished one-shot command alive for as long as that orphan lives. The probe directory is already gone by then, and the report is flushed before the exit.

**A write gate left open reports `BREACHED` by design.** The probe reads `OMELETTE_ALLOW_WRITE` and `ORION_ALLOW_GEMINI_MUTATE` exactly as they are — it does not close them for the test, because the question it answers is what your install does right now — and names the open gate on the same line — on every sandbox line while the ceiling is open, `skipped` and `held` as well as `BREACHED`: `(write gate open: OMELETTE_ALLOW_WRITE)`, or `(write gate open: ORION_ALLOW_GEMINI_MUTATE)` for the legacy alias that opens gemini alone, so a `BREACHED` you asked for does not read as a surprise.

**It is not a security audit.** One prompt, one directory, one call. It does not try to escalate, does not test network egress, does not inspect what the unit read, and a `held` is evidence about that one call rather than a proof about the sandbox. What it does catch is the failure that matters here: a unit that says it cannot write and writes.

## Partial answers are never passed off as clean ones

A run that produced text but did not finish properly keeps its text — the call is paid for and the text is usually the useful part — under a visible marker appended to the answer, and a refusal the adapter makes itself (a missing `prompt`, a relative or non-existent `cwd`, an `imagePath` that is not a file) comes back as an MCP `isError` result, recorded as `error` in the status feed, because an error string returned as a successful answer is a bug, not a style choice. A cancelled headless Grok run with **no** text throws, naming the interactive-approval cause. Which ending gives which marker, `status` and `partial`: [STATUS-FEED, "What ok, error and cancelled mean"](STATUS-FEED.md#what-ok-error-and-cancelled-mean).

## The guard hook

`omelette-fleet rules --hooks` writes one script, `.claude/hooks/omelette-guard.mjs`, and it is the only thing this package ships that runs *inside* your Claude Code session rather than around it. It serves four events — `PreToolUse` on `Bash|Write|Edit|NotebookEdit`, `PreCompact`, `SessionStart` and `SubagentStop` — and exits 2 in four cases only: a guarded role's `git` write, a curated-file truncation or a `Write` that is not an append, by any caller, the reviewer's write outside its one report, and a command too deep to read. What it does is small and worth stating exactly:

Those four events are all it does. At `SubagentStop` it reads one file, the stopped agent's own transcript, under the bounds in the table. Everywhere else the 1.5.0 rule holds: it reads no other transcript, keeps no state file and reads none of your Claude Code settings; it makes no network calls.

**The ledger sweep (1.7.3) is the guard's one import and its one child process.** On `SessionStart` and `PreCompact` — when `.omelette/` holds a ledger, and on every `clear` and `compact` whenever `.omelette/` exists, since the print needs the register's path — the guard imports `core/ledger.mjs` from the package root `rules --hooks` rendered into it — the package's own file at the path you installed, loaded with the session's privileges exactly as the CLI is. An import that fails (the package moved or was removed) is one stderr line: the sweep is skipped, the stamp and the print still happen, and `doctor` names the path. The sweep runs `git --no-optional-locks show-ref --verify --quiet refs/heads/<branch>` once per ledger that names a branch: read-only, in the session's cwd, no shell, 2 s then `SIGKILL`, in the environment `check` builds for its git (absolute PATH entries only; no system or global config, no prompts, no optional locks). It writes only under `.omelette/` and to the register file: the register through a temporary file renamed over it, a ledger's `closed` line as an O_APPEND | O_NOFOLLOW append on a regular file with one link, the move to `.omelette/archive/` never over an existing file. Everything the guard refuses or prints stays in the guard itself. `doctor` now writes: it runs the sweep, so a `doctor` run can move a closed ledger to `.omelette/archive/` and append to the register — the same writes the guard makes, no others. A TOCTOU window between the register path check and the write is an accepted limit, the same ruling as 1.7.2's audit finding 5: the only party who can swap a directory inside the project in that window is the operator's own user, and Node has no `openat`, so a re-check would narrow the window without closing it.

Stdin is bounded in both directions because it is somebody else's pipe — stdin is read before the event is named, and a settings file still wiring the retired `PostToolUse` sends the tool's own response, so the bound has to clear a few megabytes of command output. **Past 8 MiB the guard fails closed (1.9.0):** an event it cannot read whole could hold a git command anywhere, so it is refused unread, exit 2, for every caller. Before 1.9.0 it exited 0, and a `git commit` padded past the cap went through. The cap stays, because a guard that buffers without bound hangs every tool call it sees; malformed stdin still exits 0, silent, as before. An event over 8 MiB that is not a `PreToolUse` (a `PostToolUse` carrying a large tool response, a `SessionStart`) exits 2 too: there exit 2 blocks nothing, and the line goes back as the hook's stderr, to the model on a `PostToolUse`. A guard that crashes takes the session with it, and this one is protecting exactly one thing.

Every guarded role is contained for the same reason and none loses a read: the coders report instead of committing, and the tester runs the suite and reports what it saw rather than stashing or branching the tree the orchestrator is about to review. The reviewer is contained the same way, and this guard is all the enforcement it gets: for the reviewer as for every role, the guard refuses the writes that move HEAD or a ref and leave the tree clean — `reset --hard`/`--merge`/`--keep`, `update-ref` and a writing `symbolic-ref`. The rest of what keeps the reviewer read-only is the definition's text and the session's check after every review: [ORCHESTRATION, "Reviews"](ORCHESTRATION.md#reviews).

### Guard v2: the curated files, the fence and the transcript

1.8.0 adds three groups of rules to the same script. Like the git rule they are containment for an agent asked to behave, not a boundary, and each is a row group in `test/hooks.test.mjs`. What each rule says, in one line: [ORCHESTRATION, "Guard v2: the rules"](ORCHESTRATION.md#guard-v2-the-rules).

**The curated files.** A ledger rewritten "with a summary" loses what the next context needed, and the harness only half covers it: Claude Code's own `Edit`, and its `Write` on a file the session has read, refuse a file that changed since the read (measured 2026-11-03 on 2.1.316), while a Bash write and a `Write` to a file the session never read went straight through, which is exactly a session after a `/clear`, whose ledger is known from the hook's print and not from a read. So, for every agent and the main thread, before the git rule's role gate:

- *What is curated.* `ledger-*.md`, `backlog.md` and `decisions.md` under `.omelette/`, and the file the register's first line `register:` names, read the way `core/ledger.mjs` reads it (the one import the guard makes, loaded when a command or a `Write` may need it). Without the module only `.omelette/decisions.md` is curated, said once on stderr. A path is compared by its **name**: resolved against the event's `cwd`, `..` folded as text, no symlink followed — the file's own name is what the rule protects, whatever it points to.
- *Which project.* The nearest ancestor of the `cwd`, the `cwd` included, that holds a `.omelette/` directory, so a session in `<project>/sub` still guards `<project>/.omelette`; else the `cwd` itself. The fleet home (`~/.omelette`, or `OMELETTE_HOME`) is passed over: it holds the units' state, not a project's.
- *What is refused.* A Bash command whose words write a curated file that is there: a redirection `>`, `>|`, `<>` or `&>`; `tee` without `-a`; `sed -i`, `perl -i`, `sort -o`; `mv` or `cp` onto it (a destination directory takes each source under its name); `truncate`; `rm`; also behind the wrappers `builtin`, `command`, `env`, `exec`, `nice`, `nohup`, `sudo` and `time`. After a `cd` in a project with `.omelette/`, a relative path's directory is unknown and its bare name is compared. And a `Write` whose content does not start with the file's current bytes, byte for byte (so a re-encoded file is not an append); a symlink or a file the guard cannot read is never appended to.
- *What passes.* Appends (`>>`, `tee -a`), reads, `git mv`, moving a curated file away (how one is replaced on purpose), and a write to a name nothing exists at: an absent target has nothing to truncate. A name holding a glob character is never known to be absent. `Edit` is not covered, since the harness refuses a stale one.
- *What it misses.* An expansion the guard does not perform (`$PWD/…`, `~user/…`), a glob that names no ledger, a quoted `sh -c`, a program that opens the file itself, and a `cd` that fails on the way (`cd .omelette; cd /nonexistent; echo x > backlog.md`: the guard follows the last `cd`, the shell stays where the failed one left it).

**The reviewer's fence.** On `Write`, `Edit` and `NotebookEdit` for `omelette-reviewer`, the path must resolve to `<name>-review.md` directly in `reports/` under the project's `.omelette/`, compared through `realpath` of the `cwd`. An existing `.omelette` must be a real directory (`lstat`: a symlink there is refused) — one that does not exist yet cannot be a symlink, so the first report of a fresh project is compared lexically under the `cwd`'s real path and passes — and a symlink at `reports/`, at the file, or one that dangles fails the equality and is refused; a `reports/` not yet created is compared as its real parent plus the literal name, which is the first report, a directory the `Write` tool makes itself. This is the definition's sentence made mechanical; the reviewer still has `Bash`, and a Bash write is read only by the curated and git rules, so the session's `git status --porcelain` check after every review stays ([ORCHESTRATION, "Reviews"](ORCHESTRATION.md#reviews)).

**The transcript read.** Only at `SubagentStop`, only for a guarded role, only the agent's own `agent_transcript_path`. The path must lie under the projects directory of `~/.claude` or `$CLAUDE_CONFIG_DIR` (compared after `..` is folded, and the open is `O_NOFOLLOW`); the file is read from its start up to 16 MiB in 64 KB chunks, a line over 1 MiB is dropped unread, and the clock is checked after every chunk, 2 s from the start of the hook. What it takes from a line is the tool uses: `Write`, `Edit`, `NotebookEdit` paths and the writes the guard reads out of a Bash command. The record lists what the loop asked to write: a call the guard or the harness refused is listed too (the `tool_result` is not read; that is a later release's "Reports checked"). What it writes is the touched record, through an `O_EXCL | O_NOFOLLOW` temporary file renamed over the name; a `reports/` that is a symlink or not a directory is refused. The agent id in the file's name must be a plain id (`^[\w-]{1,64}$`). Every limit hit is named in the record's `skipped:` line.

**The scan budget.** Telling a `)` or a `}` that closes something from one that does not takes a scan, and an unclosed `$[$[$[…`, each `$[` opening a scan, is what spends it (before the 1.8.0 release fix the scan was quadratic and any word's `[` opened one: 120 KB of `a[a[a[…` took 73.5 s against the hook's 150 s timeout; now such a word is read in linear time and `$[` repeated 100 000 times is refused — `test/hooks.test.mjs`, the budget rows). All the brackets of one command share a budget of 1 MiB of scanning; a real command, whose regions close, never spends it. A command that does is refused whole — any reading past that point would be a second parser to prove against bash — with `<agent>: command too deep to read (over 1 MiB of bracket scanning) — split it, or write the file with Write`. It applies to every caller, the main session included, because the curated rule has to read every Bash command; the answer is to split the command or to use `Write`.

| `checkout`, `switch` | a flag that creates a branch: `-b`/`-B`, `-c`/`-C`, `--create`, `--force-create`, `--orphan`, `-t`/`--track` — anywhere before a bare `--`, alone or inside a cluster like `-qb`, quoted (`"-b"` reaches git as `-b`) or not, and whether or not the name is attached to it (that question is answered first: `git checkout -f -b x` is refused as the branch it creates). Since 1.10.1 also a form that discards work, one that rewrites tracked files from the index or a commit so that `git status --porcelain` no longer shows what was there (measured on git 2.38.1 and 2.54.0, 2026-11-11, by argv in throwaway repositories). For `checkout`: any word behind a bare `--` (`git checkout -- file.txt`, `git checkout HEAD -- .`); `-f`/`--force`; `--ours`/`-2`, `--theirs`/`-3`; `-p`/`--patch`; `--pathspec-from-file`; two or more positionals (`git checkout HEAD file` is a tree-ish and a path); one positional that no ref name can be: `.`, `..`, a word opening with `.` (`.gitignore`), `/`, `~` or `:` (pathspec magic; `git checkout :/base`, a revision, is over-refused), a word ending with `/` (`src/`) or a word holding a glob; and, by git's ref-name rules, a path component that opens with `.` (`src/.env`), one that ends with `.lock` (`yarn.lock`), two dots or four in a row (`foo..bar`; the three of a merge base, `main...other`, pass), a blank, a control character or a backslash in the word, two slashes in a row (`src//a.txt`), an `@{` no revision closes, and a final `.` — read with a revision's `@{…}` and `^{…}` taken off, so `HEAD@{1 minute ago}` passes. For `switch`: `-f`/`--force` and `--discard-changes`. Options are read as git reads them: anywhere on the line up to a bare `--` or `--end-of-options` (`git checkout main -f` forces), by any unambiguous prefix (`--forc`, `--th`, `--di`; an ambiguous prefix is refused) and in short clusters (`-qf`). A negation never undoes a refusing word: `git checkout -f --no-force main` is refused though git would not force (fail closed) | `git checkout <ref>`, `git checkout -`, `git checkout --detach <ref>`, `git checkout main --` (nothing behind the `--`), `-m`/`--merge` (it keeps local changes), `git switch <branch>`; `git checkout main` / `git switch main` with only `origin/main`, which creates a local branch by git's own guess and is allowed on purpose |
| `reset` | `--hard`, `--merge`, `--keep` (the sentence it printed since 0.3.4 is unchanged) | a plain, `--soft` or `--mixed` reset |
| `restore` | every form but the one that passes, and a `restore` fed by `xargs` (since 1.10.1); an argument holding a brace expansion, or an expansion before `--`, is refused too. `-SW`, `--staged --worktree` and a bare `git restore f` are refused. A glob before `--` is refused there, as an expansion is (`git restore --staged *`; the way round is `git restore --staged -- *.md`) | `--staged`/`-S` without `--worktree`/`-W`: the index moves, the file stays, and `git status` shows it — `git restore --staged f`, `git restore -S --source=HEAD~1 f`, `git restore --staged -- "$F"` |
| `clean` | every form but a dry run, and a `clean` fed by `xargs` (since 1.10.1): `git clean -fd`, `git clean -fdx`, `-i`, and a bare `git clean`, whose effect depends on `clean.requireForce`, which `-c` can set. A glob before `--` is refused there, as an expansion is. `--no-dry-run` is refused, and so is `git clean -e -n -f`: `-e` takes `-n` as its pattern, so nothing is a dry run and it deletes | `-n`/`--dry-run`, which wins over `-f` in git: `git clean -nfd` lists |
| `update-ref` | any form, `-d` included | — |
| `symbolic-ref` | points a ref elsewhere or deletes one | one name alone, which is a read |
| `config` | a write (since 1.10.1; measured on git 2.38.1 and 2.54.0, 2026-11-11): a write word among the options — `--add`, `--replace-all`, `--unset`, `--unset-all`, `--rename-section`, `--remove-section`, `-e`/`--edit`, or any unambiguous prefix of one (`--unset-a`, `--ad`); a short letter `git config` does not know (it knows `e`, `f`, `h`, `l`, `t` and `z`), fail closed; the first positional `set`, `unset`, `rename-section`, `remove-section` or `edit`; the bare form with two or more positionals (`git config user.name x`). Git stops reading options at its first positional, so `git config core.fsmonitor /tmp/x.sh --get` is a write of two values and is refused; so is a negated read mode (`--get --no-get a.b two` writes on 2.38.1), an ambiguous option prefix, and a `config` fed by `xargs`. Refused unread: an argument holding a brace expansion (`git config {--unset,a.b}`, `git config user.name{,}`), an option word holding an expansion (`--$X`, `"-$X"`), an option's detached value that is an unquoted expansion (`--file $F --get`), and a positional that is one when the positionals decide (`git config $X`) | a read: a read mode among the options — `--get`, `--get-all`, `--get-regexp`, `--get-urlmatch`, `--get-color`, `--get-colorbool`, `-l`/`--list`, or an unambiguous prefix — whatever follows it as name and pattern (`git config --get a.b --unset` is a read with a pattern); the first positional `get` or `list`; the bare form with one positional (`git config user.name`) or none. Valued options are stepped over with their values, attached or detached, abbreviated or not (`-f`/`--file`, `-t`/`--type` — `-tbool` is a type, not four flags — `--blob`, `--default`, `--value`, `--url`, `--comment`; `--fil f --get x.q`), and a value quoted whole passes (`--file "$F" --get a.b`) |
| `commit-tree` | — | passes: it writes an object and commits nothing |
| `log`, `diff`, `status`, every other subcommand | — | passes |

How the command string is read:

- Shell comments are cut first, each to the end of its own line: the tag in `git tag v1 # --list` is created before the `#` is read, and the line under `echo hi # a note` is a command of its own.
- The rest is read as the shell reads it: a `;` or `&&` inside quotes ends nothing (`git tag --format="x; y" v1` still names `v1`), and a redirection and its target (`> file`, `2>&1`, `>file`) are the shell's, never an argument (`git tag > tags.txt` lists).
- One word-walker finds each `git` word, steps over its global options — valued ones with their values, quoted ones included (`-C "/My Dir"`, `-c user.name="A B"`, `--work-tree /tmp/x`), a value-less `-p`, a bare `--`, and a listed set of long options that take no value, such as `--no-pager` — and names the subcommand.
- Since 1.10.1 the walker reads the KEY of `-c` and `--config-env` — detached, glued, quoted — and refuses three sections, case-insensitive as git reads them: `alias.*`, `include.*` and `includeIf.*`, whatever the subcommand. `git -c alias.ci=commit ci -m x` commits under a name the guard cannot read, an include brings in a file of aliases, and `git -c alias.x=y status` is refused too. A key it cannot read — an expansion or a substitution before the `=`, or the whole value (`-c "$X"`, which passed on 1.10.0) — is refused unread. Every other key passes as before, `core.hooksPath`, `core.fsmonitor`, `core.pager` and `core.sshCommand` included: on the command line they run a program for one invocation, which the role can run directly, and the guard does not read what a script does; saved with `git config` they are refused with every other write. `-C "$DIR"` is untouched. A refusal names its class, and there are three: a history write prints the sentence it always printed, a config write or a refused `-c` key prints its own (`<role> never writes git config …; report instead`), and a form that discards work prints its own (`<role> never discards work in the tree …; report instead`). Where one command holds a history write or an unread invocation and one of the later classes, the history or unread sentence is printed, as on 1.10.0; among the later classes, a write at the command's own level names the sentence before one inside a quoted word or a substitution, and at one level the first in order (`echo "$(git clean -fd)"; git config a.b c` prints the config sentence).
- `tag`, `rebase`, `branch`, `checkout`, `switch`, `config`, `restore` and `clean` are then read by argument parsers that know short clusters, a bare `--`, `--orphan`, `-t`/`--track`, an option's value (`--sort refname`, `--format "%(refname)"` is never a tag name) and quoting (a quoted option is still an option and takes its value: `git checkout "-b" x` creates `x`).
- Every quoted word is re-read as a command of its own, its pieces joined as the shell joins them (`sh -c 'git commit'`, `'git tag '"v1"`), at most four levels deep; past that a span that still names `git` is refused, and one that could still make a git word is refused unread: a git word its quotes or escapes join (`'g'it`), a brace group (`{g,x}it commit` six substitutions down), an expansion or a substitution. Plain words pass, however they are quoted. The whole scan is linear in the command's length. An escaped quote outside quotes (`\'`, `\"`) is read as the quote it stands for, so `sh -c 'sh -c '\''git commit'\'''` is re-read through both levels and refused.
- A command substitution (`$( … )`, backquotes) or a process substitution (`<( … )`, `>( … )`, a redirection's target included, attached to the operator too: `>>(…)`, `2>>(…)`, `<<(…)`) is one opaque word of the command around it and is re-read as a command of its own: `git checkout $(git tag -l v1) -b new` and `echo x > >(git commit -m y)` are refused.
- A command substitution where `git`, a global option, its value or the subcommand goes is not read, quoted or not, and the invocation is refused (since 1.9.0): unquoted, an empty one vanishes and the word behind it becomes the subcommand (`git $(echo) commit -m x`, `git -C $(echo) . commit -m x`); quoted, its output is the subcommand (`git "$(printf commit)" -m x`); inside the git word it leaves `git` behind (`g$(echo)it commit -m x`). A variable expansion — `$x`, `${x}`, `${x:-commit}`, `$1`, `$@` and the other special parameters, and zsh's `$=x`, `$~x` and `$^x` — is read the same way: `git $x commit -m x` commits when `x` is empty, `git "$x" -m x` when it holds `commit`, `x=commit; git $=x -m y` commits in zsh, and `g${x}it` is `git`. A value is read for what it is: quoted whole behind `-C`, `-c`, `--git-dir` or `--work-tree`, or after the `=` of a glued long option — in double quotes, or in single quotes, which the shell hands over literally (`git -C '$DIR' status` passes) — it can neither vanish nor split, so `git -C "$DIR" status`, `git -C "$(git rev-parse --show-toplevel)" log` and `git --git-dir="$D/.git" status` pass and `git -C "$DIR" commit -m x` is refused as a commit; unquoted (`-C $DIR`, `-C $(pwd)`) or glued to `-C` or `-c` (`-C$(pwd)`, and `-C"$DIR"`, which empty is a bare `-C` that takes the next word) it can, and the invocation is refused whatever its subcommand; inside double quotes only a form that stays one word in bash and zsh is a value — `"$x"`, `"${x}"`, `"$*"`, `"${a[*]}"`, a simple `"${x:-word}"` whose word holds no `$`, `@` or `(`, a command substitution — and every other form fails closed: `"$@"`, `"${a[@]}"` (`set -- . commit; git -C "$@" -m x` commits), zsh's `"$a[@]"`, `"${(@)a}"`, `"${(f)y}"` and `"${=x}"`, which split there, a nested `"${x:-$y}"`, and `"$1"`. Unless a write named behind it decides the refusal (`git -C $(pwd) commit` and `git --git-dir=$(pwd)/.git push` are refused as that write), the refusal ends `a command substitution where git or its subcommand goes is not read`. After the subcommand nothing changes (`git status $(echo)`, `git tag -l $(git rev-parse HEAD)` and `git log $X` pass), and a word that is only a substitution or an expansion is no `git` word (`echo $(date) commit` and `echo $x commit` pass; `$(which git)` and `$GIT` stay out of scope, below). It over-refuses on purpose: `git -C $(pwd) status` is refused, so is a single-quoted `'$(x)'` or `'$x'` where `git`, an option or the subcommand goes (git would refuse that word anyway), so is an arithmetic `$((…))` there, which opens like a substitution (`git -c core.abbrev=$((7+1)) log`), so is a carriage return, read as a line break as a CRLF line ending needs (`echo x\rgit $(echo) commit` — bash runs one `echo`), and so is a `git` or `.git` argument that holds a substitution or has one behind it, since a `git` word is read wherever it stands (`grep -rn git $(git ls-files)`, `ls .git $(pwd)`, `ls $(pwd)/.git`, `git clone https://host/$(repo).git`) — `git ls-files | xargs grep -n git` reads the same files. A quoted value behind an option the guard does not list as valued (`git --namespace "$ns" log`) is still refused unread, since an unlisted option may take no value and the quoted word would then be the subcommand; write it glued (`--namespace="$ns"`) and it is a plain value.
- A brace expansion is read as the shell makes it (1.9.0 review fix round). In the program word it is refused unread whenever one of its words is a `git` word (`{git,--no-pager} commit -m x`; `{echo,git} commit -m x` and `ls {.git,src}` too, which run no git: over-refusals, accepted). In the subcommand's place its first word is the subcommand and the rest are its first arguments (`git {c,c}ommit`, `git com{m..m}it` and `git pu{s..s}h` are refused as that write, and `git tag{,x}` creates `tagx`); one with an option among its words, a guarded subcommand behind the first, or a brace before the subcommand (`git {-C,.} commit`, `git -C {.,commit}`) is refused unread. A word is expanded only within bounds counted before anything is built: 256 words, 64 groups, 1 MiB of expanded text. A word past them may be anything, so where the program, an option or the subcommand goes it is refused unread (`git` with nine `{a,b}`); anywhere else it is read as written (`echo {a..z}{a..z}{a..z}` passes). A command whose words hold more than 4096 brace groups or 65 536 brace words in all, what its substitutions and quoted words run included, is refused whole: `command too wide to read`. A glob (`?`, `*`, `[`) where the subcommand goes is refused unread: `git c?mmit -m x` commits once a file `commit` exists. In an argument both pass (`git log --format={%H,%s}`, `git log *.md`).
- A heredoc body is read as a command of its own, quoted delimiter or not, unless its line hands it to programs that run nothing: every command of the line runs one of `cat`, `tee`, `head`, `tail`, `less`, `more`, `wc`, `grep`, `egrep`, `fgrep`, `sort`, `uniq`, `cut`, `tr`, `base64`, `xxd`, `od`, `hexdump`, `md5`, `md5sum`, `shasum`, `sha256sum`, `diff`, `cmp`, `jq`, `yq`, `column`, `fold`, `paste`, `tac`, `rev`, `nl`, `expand`, `fmt`, `pr`, `gzip`, `bzip2`, `xz`, `zstd`, `tar`, `cpio`, `echo`, `printf`, `true` or `:` (by name or path, past `env`, `sudo`, `nice` and the other wrappers; a command of assignments alone runs none; a program word the shell must expand — `$SHELL`, `ba{sh,x}`, `b\ash` — names none of them), no redirection target holds an expansion, a substitution, a brace group, a glob or a backslash, no process substitution is on it, and it does not end in a pipe (1.9.0: it fails closed; until then a list of shells decided). `awk` and `sed` left the set in 1.10.1 because each can run what it reads: `awk -f -` and `sed -f -` take the body as their program, and `awk 'BEGIN{system("sh")}' <<'EOF'` hands it to a shell through the stdin it inherits, with no flag on the line to tell the forms apart; `less`, `more`, `tar` and `cpio` stay, none runs a text body, and `--to-command` on the line is a word the guard reads. An argument is not read so: `echo $HOME <<'EOF'` passes. So `bash <<'EOF'`, `python3 <<'EOF'`, `ssh host <<'EOF'`, `docker run -i img <<'EOF'`, `$SHELL <<'EOF'`, `sudo -u x $SHELL <<'EOF'`, `env $SH <<'EOF'`, `ba{sh,x} <<'EOF'`, `tee >(sh) <<'EOF'` and `cat <<'EOF' |` + `sh` with `git commit -m x` in the body are refused, and `cat > f <<'EOF'`, `grep x <<'EOF'` or `cat <<\EOF` with it pass. **The price of failing closed**, accepted: when the body holds git-write text, `sed s/a/b/ <<'EOF'`, `awk '{print $1}' <<'EOF'` and `cat <<'EOF' | sed s/a/b/` (`sed` or `awk` anywhere on the heredoc's line, since 1.10.1), `cat <<'EOF' > $OUT` (an expansion in a target), `[ -f x ] && cat <<'EOF'` and `mkdir -p d && cat > d/f <<'EOF'` (a program outside the set on the line), a `while read …; done <<'EOF'` loop, `gh pr create --body "$(cat <<'EOF' … EOF)"`, and a `python3`, `perl` or `node` heredoc are refused. Since 1.10.1, with git-write text in the body, these passed on 1.10.0 and are refused now too: a heredoc inside a function body, a `for` or `while` loop, an `if`, a `case` arm, a `{ … } > file` group or a multi-line subshell (`(` + `cd docs` + `cat > CONTRIBUTING.md <<'EOF'` … `)`); a substitution's heredoc inside a loop (`x="$(cat <<'EOF' … EOF)"` between `do` and `done`); and a top-level heredoc that comes after a group the guard could not close as both shells do — after `(cd "$(dirname "$(pwd)")" && ls)`, after a loop holding `$(echo "$f" | sed 's/\.md//')` (a backslash inside the substitution), after a zsh-style `f() { echo hi }`, after `echo {`. Unchanged from before: `( cat <<'EOF' >/dev/null` … `EOF` + `); cat > f <<'EOF'` on one line is refused, and with the `)` on its own line it passes. The way round: write the file with the Write tool, or keep git-write text out of the body. The body of a heredoc inside a command substitution is read as a command when its line runs a program outside the set, since that program may run what the substitution prints: `eval "$(cat <<'EOF'` + `git commit -m x` + `EOF` + `)"`, the same under `bash -c` or in backquotes, and `x=$(cat <<'EOF' … EOF); eval "$x"` on one line; on a line of the set it is text (`echo "$(cat <<'EOF' … EOF)"` prints it).
- A heredoc whose line stands inside a group still open at that line's end — `(`, `{`, `if`, a loop (`for`, `while`, `until`, `select`), `case`, a function body — has its body read as a command, and the line is read as one that feeds: its substitutions and quoted words too (1.10.1). What the group's output feeds (`) | sh`, `} | sh`, `fi | sh`, or a call `f | sh` three lines after `f() {`) is written after the body, and the guard does not look ahead for it. It fails closed between the shells: an opener is counted wherever either bash 3.2 or zsh may read a reserved word (zsh's `repeat`, `foreach`, `if true {`, a `{` glued to a word) and, at one point, where bash 4 and later read one that both reject: after the name behind `function` or `coproc` (`function f while true` + a heredoc on the next line + `done` + `f | sh`; the guard's reading of bash's grammar, not run under a bash 4 or later), a closer only where both read one (a whole unquoted word, first after `;`, a newline or `&`, outside `[[ … ]]`, matching the innermost group; a `)` closes the innermost `(` only, and a `case` pattern's `)` closes nothing). Not groups: `((…))`, `$(…)`, backquotes, `<(…)`, `${…}`, a subscript, an array assignment's parentheses, `{a,b}`, anything quoted or escaped. Where a nested text (`$(…)`, `${…}`, a `"…"` holding a substitution) may end for the shells somewhere other than where the guard ended it — it holds a backslash, a backquote, a `#` that starts a word, a `<<`, the word `case`, an inner quote — every group open at that point stays open for the rest of the command. With `git commit -m x` in the body, `(cat <<'EOF'` … `EOF` + `) | sh`, `{ cat <<'EOF'` … `EOF` + `} | sh`, `if true; then cat <<'EOF'` … `EOF` + `fi | sh` and `f() {` + `cat <<'EOF'` … `EOF` + `}` + `f | sh` are refused; the same groups with a harmless body pass, and so does a heredoc on a line after the group has closed (`(true); cat > f <<'EOF'` with a git-write body).
- A `git` that `xargs` runs with no subcommand of its own, or with xargs' placeholder in its place (`-I`, `-J`, `-i`, `--replace`), behind `env` and its `K=V` words, `command`, `nice [-n N]`, `sudo`, `exec`, `time`, `nohup` or `timeout N` too (`xargs env git`, `xargs -n1 command git`); behind a wrapper with any other option (`sudo -u x`, `nice -5`, `env -i`, `timeout -s KILL 5`, `command -p`) the first `git` word after it is the program. Such a git is refused unread: `printf '%s\n' commit -m x | xargs git` and `xargs -I {} git {} -m x` commit.
- A `tag`, `branch`, `checkout`, `switch`, `config`, `restore` or `clean` fed by `xargs` counts as a write, so a listing or a delete through `xargs` is over-blocked.

Residuals — what the reading misses, known and accepted:

- an abbreviated long option (rebase's value-taking ones excepted);
- an unlisted value-less global option before the subcommand, which misreads only when a later word names another subcommand (`git --newflag checkout -b tag` passes, the bare word `tag` being read as the subcommand; `git --no-newflag commit` is refused by the last-value fallback, and so is `git --no-newflag checkout -b tag/v1`, since any unlisted long option is read as valued and the fallback lands on `checkout`);
- what a substitution or an expansion prints is never read as a flag (`git checkout $(echo -b) x` passes), nor as a path: `git checkout $(git diff --name-only)` and `for f in a b; do git checkout $f; done` pass and restore those paths (measured 2026-11-11). The same for `switch` and for a glob there: `git checkout "$F"` and `git switch *` pass, and with F `-f`, or a file named `--discard-changes` in the directory, the work is thrown away;
- `git tag git tag -l`, which git reads as one listing and the guard refuses as a tag called `git`;
- a glob in the program word (`/usr/bin/gi? commit -m x` runs `/usr/bin/git`), zsh's glob alternation where the subcommand goes (`git (commit|x) -m y` with a file `commit` there), and xargs' placeholder inside a quoted command (`xargs -I {} sh -c 'git {} -m x'`) — measured passing on 2026-11-07;
- a heredoc whose group closes on its own line while its output is fed later, measured 2026-11-11: `f()` + newline + `(cat <<'EOF')` + body + `EOF` + `f | sh` passes, the group being closed at the line's end; and nested text the guard ends elsewhere than the shells do (all of these pass on 1.10.0 as well): a double quote ends at its first inner `"`, so quotes do not nest inside `"$(…)"` — `echo "$(awk -f - <<'EOF'` + `BEGIN{system("git commit -m x")}` + `EOF` + `)"`, `( echo "$(cat <<'EOF'` + `sh -c "git commit -m x"` + `EOF` + `)"` + `) | sh`, and `( x="$(echo '")')"` + a heredoc + `) | sh` — and a `$(…)` ends at an escaped or commented `)` — `echo $(echo \) <<X)` + `git commit -m y` + `X`, `echo "$(echo a # )` + a heredoc + `)" | sh`, `$(case x in` + `x)` + heredoc + `esac)` under zsh, `$((( 1 ))` read as arithmetic. The guard detects each of these since 1.10.1 and acts on it only while a group is open; tar's `--to-command` stays a word the guard reads, and GNU sed's `e` command is closed with sed leaving the set;
- data that flows from one line into another: `x=$(cat <<'EOF' … EOF)` on one line and `eval "$x"` on the next passes (measured 2026-11-07), since the guard reads one command string and follows no value across its lines (a program word that is a substitution printing a command, `$(cat <<'EOF'` + `git commit -m x` + `EOF` + `)`, is refused: it is a program word that holds a substitution);
- `git config` built in a variable or by a glob, measured 2026-11-11: an option-shaped value where the first positional goes (`KEY="--no-get a.b two"; git config --get $KEY`, and `git config "$X"` with `X=--edit` under a `GIT_EDITOR` that writes), and a glob in an argument with files planted for it (`git config --file c* --get`, `git config a*`) each write on git 2.38.1 and pass. Closing them means refusing every expansion in a `git config` argument, `git config --get "remote.$r.url"` included;
- the environment route: `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0` setting an alias, `GIT_CONFIG_GLOBAL` and `GIT_SSH_COMMAND` — the guard reads the command's words, not its environment;
- `git -c checkout -b config` and its like: with `config` a name the walker knows, an invalid `-c` key followed by the plain word `config` passes where 1.10.0 refused it; git itself rejects every such form (an invalid key, an unknown option). A braced subcommand that names `config`, `clean` or `restore` first was refused unread on 1.10.0 and is now read as that subcommand, which is what the shell makes of it: the forms its reader passes, pass — `git {clean,commit} -n` (a dry run of `clean commit`), `git {restore,commit} --staged f` (the index only), `git {config,commit}` (a read) — and the others are refused under the new sentences (`git {restore,commit} f`, `git {clean,commit} -m x`). `xargs git -c config -S -e` prints the config sentence where 1.10.0 printed the unread one;
- hiding or reversing work outside the four subcommands, measured 2026-11-11 on git 2.38.1 and 2.54.0: `git update-index --assume-unchanged f` and `--skip-worktree f` hide an edited file from `git status --porcelain` and `git diff`, and `git diff | git apply -R` throws the work away and leaves status clean; all pass, as on 1.10.0;
- config written outside `git config`, same measure: `git remote set-url origin <url>`, `git remote add x <url>` and `git maintenance register` (the global config) pass, as on 1.10.0;
- a glob in a `-c` key with a file planted for it (`git -c al?as.x=commit x` with a file named `alias.x=commit` in the directory);
- an over-refusal, accepted: `echo git config a.b c` and `grep -r "git config a.b c" .` are refused, as `echo git commit a` always was — a `git` word is read wherever it stands;
- `git checkout <one plain word>` where no such ref exists and a tracked path does (`git checkout docs`, `git checkout Makefile`, and the same behind `-m`, `--no-patch`, `--no-overlay`, `--conflict=merge` or, on git 2.54, `--end-of-options`): git restores the path, and the guard, which does not read the filesystem, passes a word that could be a branch (measured 2026-11-11). The same holds for a file whose name spells revision syntax or a legal branch name: `a...b`, `a:b`, `a^b`, `a~b`, `dir./file`;
- a plain branch move over an ignored file: `git switch other` and `git checkout other` silently overwrite an untracked file that `.gitignore` covers when the target branch tracks it (git's default `--overwrite-ignore`; measured 2026-11-11 on both gits). `git status --porcelain` never listed that file;
- git's plumbing: `git checkout-index -f -a` and `git read-tree -u --reset HEAD` rewrite the tree and pass (measured 2026-11-10), as do `git rm -f` and a plain `rm`, whose deletion shows in `git status`;
- over-refusals, accepted: `git -C clean status` and `git -C restore log` (a directory named like a subcommand the walker knows), `git checkout :/base`, `git checkout ...other` (the merge base with HEAD), `git checkout -f --no-force main`, `git restore --staged --worktree --no-worktree f`, `git restore --staged *.md` and `git clean -n -e *.o` (a glob before `--`), and a heredoc with a git-write body on the line after `coproc cat {a,b}` or `coproc echo if` (the word behind a coprocess's name is read as an opener);
- the design boundary itself: one command string, one tool — an argv-array spawn, a backslash-escaped `g\it`, a shell alias, `$(which git)` or `$GIT commit` (a program word that is only an expansion) never spell the command out and are out of scope, as the containment paragraph below says.


### Wiring, and what the guard is not

**A hook script is inert until your settings call it, and this package does not write those files.** `rules --hooks` prints the snippet and you paste it into your own settings file; settings level is also the only placement that fires — a `hooks:` block in an agent definition's own frontmatter did not fire at all on Claude Code 2.1.261 (measured 2026-09-06). The snippet, its quoting per platform, and how `doctor` decides whether the guard is wired: [ORCHESTRATION, "Layer 3: the guard"](ORCHESTRATION.md#layer-3-the-guard) and ["What doctor says about the wiring"](ORCHESTRATION.md#what-doctor-says-about-the-wiring).

The guard is **containment for a delegated agent, not a boundary against a hostile one.** It bounds one tool on one pattern read out of one string, so an argv-array spawn, a backslash-escaped `g\it`, a shell alias, `$(which git)` and anything else that never spells the command out are deliberately out of scope — and anything determined to get around it has other ways to reach git. Its value is that an agent doing the ordinary wrong thing — committing when the operating model says report instead, or stashing the tree to get a clean test run — is stopped every time, without anyone having to be watching.

**The mod runs a project-local script, on purpose.** The optional fleet pane mod ([MODS](MODS.md)) can deliver the guard's answer itself: its `tool.call` hook runs the project's rendered `.claude/hooks/omelette-guard.mjs` (else the user's `$HOME` copy) with `node` from the absolute entries of `PATH`, 2 s, and denies the call when the script exits 2. That is a script in the project you opened, executed by the mod, and it is the designed answer: **a project you do not trust is a project you do not open**, since its own settings hooks run the same script with the same privileges. The mod adds no reach the settings hook did not have; what it adds is that it answers first and that it works where the settings hook does not. Measured on Claude Code 2.1.316 (2026-11-03), under `claude -p` in a directory never trusted interactively, the project's settings hook, a plugin's classic hook and a hooks module all fired, so headless is no gap for either delivery; each live gate re-probes it. The mod does not read the settings to decide whether to run, and it has no rule of its own: any exit but 2, a timeout, a missing script or no `node` lets the call go on, and a missing script or `node` is said once.

Two details bound what the mod passes on. The **role** it hands the script comes from the pane's own state (`agent.spawn` maps an agent id to its role), and it hands none for the main thread or an agent it never saw, as Claude Code does; the script's own role gate decides, and for a role the pane missed, `agent_type` from the engine on the settings hook is the backstop. And the **deny text** is the script's stderr with ANSI escapes and control characters stripped and cut at 2 KB, so a refusal reaches the model as a reason, not as terminal output.

## The fleet pane mod

The optional fleet pane ([MODS](MODS.md)) runs inside Claude Code as a plugin, so its reach is the plugin API's, not the units'. It reads the engine's own events and figures (agents, tool calls, context fill, rate-limit windows), the units' status snapshots under the fleet home, the rendered guard script, the six role definitions, the open ledgers' text and the touched records. It writes no file and edits no setting; its own pane state is stored by Claude Code. Since 1.8.0 it is no longer a pure observer: it runs `node` on the rendered guard (and `git show-ref` for the compaction gate), denies a call exactly when the guard exits 2, rewrites a guarded role's `model` to its definition's at spawn, adds the handoff print as a `SessionStart` context entry when the settings hook did not (one copy; nothing reaches a sub-agent) and, with `handoffGate` on, skips a compaction once. It opens no network connection. Why running the project's script is not a new risk, and what bounds what it passes on: [Wiring, and what the guard is not](#wiring-and-what-the-guard-is-not). Strings it draws are cleaned of terminal control characters, and a Bash command is shown as its program and, for a short list of programs, one plain next word (the subcommand or script name) — never its flags, paths or environment assignments, so a secret in a command line reaches the pane only if it is typed in one of those two places (quotes are removed before the words are read). Install it only from this package; a plugin runs with your session's reach, and its source is `mods/omelette-fleet/`.

## What this package never does

- **It never writes into a project on its own.** Image artifacts land in a temp directory or the vendor's own session directory and nowhere else: Grok's under `~/.grok/sessions/…`, Gemini's and Codex's in a throwaway directory under the OS temp dir. Either way the tool returns an absolute path and you copy the file where you want it.
  - The one command that writes into a project is `omelette-fleet rules` — directly, or as the second half of `omelette-fleet install --rules`, which is that same command run in the current directory — and only when you run it: it writes `.claude/rules/omelette-fleet.md`, plus — with `--agents` — `.claude/agents/omelette-coder.md`, `.claude/agents/omelette-coder-medium.md`, `.claude/agents/omelette-coder-hard.md`, `.claude/agents/omelette-coder-xhard.md`, `.claude/agents/omelette-tester.md`, `.claude/agents/omelette-reviewer.md` and `.claude/skills/omelette-test/SKILL.md`, and — with `--hooks` — `.claude/hooks/omelette-guard.mjs`. No unit, no tool call and no other command can trigger it. It never follows a symlink: a link at `.claude`, at any of the four directories under it, or at the target file itself is a refusal, `--force` included, and the temporary file is created with `O_EXCL` so a planted one fails the write rather than being followed. Which scope it writes, what it overwrites, refuses and removes, flag by flag: [ORCHESTRATION, "Layer 2"](ORCHESTRATION.md#layer-2-the-rules-file-and-its-marker).
  - The other writer is the ledger sweep — `omelette-fleet ledger sweep`, `doctor`, and the guard on `SessionStart` and `PreCompact` — with `omelette-fleet ledger open`, which writes one new ledger. They write `.omelette/` and the register file its first line names, and nothing else in the project ([CONFIG, Ledgers and the decisions register](CONFIG.md#ledgers-and-the-decisions-register)).
- **It never shells out.** Neither the CLI nor the servers use a shell anywhere (no `shell: true` in `bin/`, `core/`, `servers/`, `units/` or `hooks/`): every child is `spawn(bin, [args])` or `execFile`, so a path or a value with a space, a quote or a `;` in it is data, not shell syntax.
- **It never passes `--dangerously-*` flags,** in any unit, in any mode: not `--dangerously-bypass-approvals-and-sandbox`, not `--dangerously-bypass-hook-trust`, not `--dangerously-skip-permissions`.
- **It never passes `--always-approve`.** Grok's image tools were verified to auto-approve headless without it; if a future CLI version starts prompting, the run cancels and the adapter surfaces the raw-output error rather than the flag being added silently.
- **`check` opens only paths that resolve inside the project root, and never writes.** `omelette-fleet check` reads the markdown file it is given — wherever the operator keeps it — and the files its pointer lines name: resolved against the real root, refused when absolute or when they leave it, symlinks and non-regular files refused, opened `O_NONBLOCK | O_NOFOLLOW`, 2 MiB per target. When the file carries a `commit:` line that is a plain hex hash it runs one `git diff --name-only -z --relative <hash> --` (NUL-separated, so a name git would quote — `café.js` — is matched as it is on disk) — `execFile`, no shell, 5 s then `SIGKILL` — in an environment it builds rather than inherits (`PATH`, `HOME`, locale; lazy fetch, optional locks, prompts, system and global config off), with external diff, textconv, the order file, fsmonitor, hooks and the index auto-refresh shut off (an index refresh would be a write); any other `commit:` value reaches nothing and is reported. It writes nothing. What it does not promise is listed under [best-effort](#what-is-best-effort).
- **It never uses API keys.** Subscription auth only; billing-risk keys are scrubbed from the child env.
- **It never hands a vendor CLI the parent environment.** The allowlist is the only path in.
- **It never lets Codex read your `~/.codex/config.toml`** — the pattern to follow for any future unit whose config file can carry executable behaviour.
- **It never retries an image run or a write-mode run.** The one bounded retry on empty output exists because re-issuing a read-only one-shot is safe. Re-issuing a generation bills image quota twice, and re-issuing a run that may already have written something is not idempotent — both paths skip the retry. That covers **every** image tool in the fleet: `grok_image`, `grok_image_edit`, `codex_image` and `gemini_image` each run exactly once. Deterministic failures (auth, quota, hard-kill, missing binary, CLI error) are never retried either.
- **It never writes Claude Code's config.** `~/.claude.json` is parsed for `doctor`, and so are the project's `.mcp.json` and `settings.json` / `settings.local.json` at both scopes — read to say whether the guard hook is wired, where the units are registered, and what the client's timeout walls are set to, and printed as a snippet by `rules --hooks` for you to paste. The only writers of those files are `claude` and you.

## What is best-effort

Call these defence in depth, not guarantees:

- **Grok L4 and L6, and every prompt preamble.** A model can ignore a preamble; a permission rule only helps if a tool got past the toolset allowlist in the first place.
- **`MUTATE_RE`.** It matches `git push|commit|merge|rebase|reset|tag`, `npm publish` and `deploy` in a prompt. It is intent routing, not security — it is trivially avoidable by rewording. It is a per-tool flag (`mutateGate`) set on exactly three tools, `grok_research`, `codex_research` and `gemini_research`; every other tool is ungated — the image tools (where "commit" could be literal scene text), `grok_code_review`, `codex_code_review` and `gemini_deep_research` — and there only the preamble and the sandbox or permission layer stand.
- **The Gemini unit's read-only posture as a whole**, for the reasons above.
- **Auth and quota detection.** Regex matches on stderr. Auth detection deliberately runs *only* on runs with empty stdout, and quota-exhaustion patterns are checked *only* on failed turns, so a successful answer that merely discusses signing in or quotas is never misread — but a vendor wording change can still produce a less precise error message. `doctor` reports a probe it cannot interpret as `unknown`, never as "signed out".
- **The process-group kill.** It fires on the unit's own timeout, on a cancel under `cancel: kill` (under the default `cancel: finish` a cancel detaches the run and the SIGTERM below bounds it), and — since 1.6.0 — when the server receives SIGTERM or SIGHUP (Claude Code's shutdown sends SIGTERM when a server outlives its closed stdin); `omelette-fleet call --timeout` cancels the request before it signals the server. Two things still outlive it (measured: [MEASUREMENTS](MEASUREMENTS.md#unit-processes-after-the-server-is-gone)): a server that is SIGKILLed outright — agy and grok then run to their own end, codex until its current command ends — and a shell command Codex is running, which codex starts in its own process group, out of reach of the group kill on any path.
- **Output caps.** They keep the tail. An over-cap response is truncated from the front, which is a data-loss failure mode, not a corruption one — the adapters return the tail marked partial when it still parses as an answer; a cap that cut into the answer itself is an error, not a fragment passed off as an answer.
- **`check`'s containment is about paths, not bytes.** A hard link inside the root can carry bytes that also live outside it; a parent directory swapped for a symlink between the path check and the open is a race Node's core cannot close (there is no descriptor-relative open); a repository's own `.git/config` can still `include` a file elsewhere or name a clean filter, which git runs on a working-tree diff exactly as it does on `git status` (system and global config are off, so nothing outside that one file can). In each case what `check` can reveal is whether a fragment the checked file already contains is present on a line — nothing it prints comes from the target.
- **The body of a spooled answer.** `omelette-fleet results` escapes the header it prints (tool, model, prompt preview, timings) but prints the answer body as the model wrote it, control characters included: the body is the evidence, and escaping it would change what the session reads. Read a spooled body in a pager that shows control characters, or through `cat -v`.

## Units propose, the manager applies

The design principle underneath all of the above. A unit's job ends at a proposal: a review, an analysis, a report, a diff described in prose. The change itself is made by Claude Code, where your normal approval flow already sits and where one agent has the whole picture. This keeps the mutating surface in exactly one place, makes prompt injection into a unit a *reporting* problem rather than an *execution* problem, and means an untrustworthy answer costs you a re-read instead of a revert.

## How this package is audited

A security review of this package is a review with a brief: what each part is trusted with, and the classes of defect that trust invites. A finding counts only once a fresh reader has tried to disprove it against the code and failed. The brief was tested before anything relies on it — three runs over one revision, below.

**The parts and their trust class.** What each part runs as, what it can reach, and what an audit asks of it:

| Part | Files | Trust class | What the audit asks |
|---|---|---|---|
| Three unit servers | `servers/*.mjs`, `units/`, `core/` | Read-only MCP servers, each spawning a vendor CLI (`agy`, `grok`, `codex`) that runs a model with a shell or a toolset | Does a vendor CLI get more than its call needs — environment, config, write access — and is what it returns treated as untrusted? |
| The guard hook | `hooks/omelette-guard.mjs` | A hook with git rights: it runs inside your session as your user, on the events your settings wire it to, and appends to the project's ledgers | Can a role it guards get a git write past it, and can a file planted in the project turn the hook's reads or writes against you? |
| The CLI | `bin/omelette-fleet.mjs` | A command you run, which writes managed files into `.claude/` — the project's, or your user's with `--global` — and reads Claude Code's settings without writing them | Can it be made to write outside its own files: through a link, or over a file that is not its own? |
| The sub-agent definitions it renders | `agents/` | Instructions, a model and a toolset for a delegated Claude Code agent, rendered into `.claude/agents/` by `rules --agents` | Does each role get only the tools its job needs, and does its definition say what it must never do? |

## Recommended agy allow-rules

agy in headless mode (`agy -p`) cannot prompt, so **any tool that would ask for permission is auto-denied** — and the run still exits 0 with `status: SUCCESS` and an empty response, with the reason on stderr. A run whose model reaches for a tool outside your allow list fails with something like `a tool required the "read_file" permission that headless mode cannot prompt for`, which this unit surfaces as an error instead of a silent blank.

Two rule sets, named for what they allow. In `~/.gemini/antigravity-cli/settings.json`:

**Web research** — what `gemini_research` and `gemini_deep_research` needed for grounded research, and nothing more. Measured 2026-11-13 on agy 1.5.8, headless, with and without this unit's flags and with session allow rules for the tool: every Gemini level run — Hydrogen (Low), (Medium) and (High), Argon (High), 3.8 Flash (High) — reported `search_web` as its only web tool and fetched nothing when asked for one exact page. That is the models' own report plus the absence of a fetch; agy's init event still lists `read_url_content`. `search_web` ran with no rule for it in the allow list. The rule below costs nothing and stays right for an agy that offers the tool again:

```json
{
  "permissions": {
    "allow": ["read_url(*)"]
  }
}
```

A prompt-injected run under this set can send only what is in its prompt and what it fetched. This is the set the threat model above assumes.

**Local files, opt-in** — add `read_file(*)` only when you want `gemini_research` to read local images, PDFs and documents (give an **absolute path** in the prompt and say "view the file directly, no terminal commands", because `command` is auto-denied headless). What it buys an injected page: any file your user can read, sent anywhere `read_url` reaches. If you take it, deny the files that authenticate something, by exact path — the only deny form these docs have seen work:

```json
{
  "permissions": {
    "allow": ["read_file(*)", "read_url(*)"],
    "deny": [
      "read_file(~/.ssh/id_ed25519)",
      "read_file(~/.ssh/id_rsa)",
      "read_file(~/.config/gcloud/application_default_credentials.json)",
      "read_file(~/.aws/credentials)",
      "read_file(~/.codex/auth.json)",
      "read_file(~/.grok/credentials.json)",
      "read_file(~/.gemini/antigravity-cli/oauth_creds.json)"
    ]
  }
}
```

The list is illustrative: the rule is every file that authenticates something. The fleet's result spool (`<home>/results/<unit>/*.md`, one file per answer) cannot be named by an exact-path deny, so under the opt-in set past unit answers are readable by an injected page — one more reason the opt-in set is opt-in. Check the real names your CLIs write (`ls -a ~/.grok ~/.gemini/antigravity-cli ~/.codex`) and list those.

Do **not** reach for `--dangerously-skip-permissions` to fix a headless auto-deny: it auto-approves every tool and removes the only permission layer this unit has.

Two caveats. The only rule forms we have seen working are the `*` target and deny rules naming an exact path; anything glob-shaped is **unverified** — test a rule before relying on it, and until you have, assume a deny rule covers only the exact paths you listed. And a deny list is a list: a credential file it does not name is readable.
