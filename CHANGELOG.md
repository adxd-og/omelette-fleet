# Changelog

## 0.3.3 — unreleased

- **Units report progress while a run is in flight.** A `tools/call` now reaches the runtime with the request's own context — its id, the client's `progressToken`, an abort signal and a way to send notifications — and while a child runs the unit sends `notifications/progress` every 30 s with the elapsed seconds and one short line. Nothing is sent to a client that supplied no token, and nothing after the response. The reason is a wall nobody had noticed: since Claude Code 2.1.203 a stdio tool call that sends neither a response nor a progress notification for 30 minutes is aborted for idleness, whatever `MCP_TOOL_TIMEOUT` says, and no unit sent either. `OMELETTE_DEBUG_META=1` logs the `_meta` of every `tools/call` to stderr — the one-line spike that settled whether a given client sends a token at all, kept as a debugging aid.
- **Cancellation has a policy: `cancel: "finish" | "kill"`, default `finish`.** `notifications/cancelled` used to be ignored, so a request the client abandoned kept running and its answer went nowhere. The transport now keeps an in-flight table keyed by request id (a number id and a string id are different requests), aborts the one it names, and drops that request's response — the MCP spec says a receiver ignores it, and sending it confuses a client that already moved on. `finish` leaves the vendor CLI alone, records the result, and marks the feed entry `detached: true`; `kill` SIGKILLs every process group the request owns, aborts a pending retry delay and stops a deep-research pipeline between stages, ending the call as `cancelled`. `finish` is the default because the units run on subscriptions with the billing keys scrubbed: a run that finishes after a cancel costs window quota, not money, and the incident behind this release was a lost answer.
- **Goodbye no longer kills a paid run.** A server used to exit the instant its stdin closed. It now stops reading, waits for the calls still in flight — each already bounded by that unit's `timeoutS` — and only then exits, so `finish` survives a client timeout and a client restart.
- **Every spawn-tool call carries a result id.** `<YYYYMMDDTHHMMSSZ>-<pid>-<seq>`, generated by the runtime and independent of the status feed (which plenty of installs switch off). It rides the feed's `start` line, `active` entry, `end` line and `lastEvent`, all still schema 1, alongside the new `detached` flag and the new `cancelled` status.
- **A `local` tool kind.** A tool answered in-process, with no spawn, no status-feed entry and a reduced context — what `<unit>_models` always was internally, now a first-class kind other tools can use.
- **The handoff block comes back after a compaction.** `PreCompact` stamped the re-read line into every `.omelette/ledger-*.md` and printed one `HANDOFF:` reminder — and that reminder went nowhere a contract promises: Claude Code's hooks reference documents `SessionStart` stdout as added to the session's context, and says nothing of the kind about `PreCompact`. So the guard gains a third event. On `SessionStart` with `source: "compact"` — and only that source; `startup`, `resume`, `clear` and `fork` lost no context — it prints each ledger's **last handoff block** to stdout, preceded by `--- <ledger> · last handoff ---`. A block is the last `## Handoff` heading to the next `## ` heading or the end of the file, with headings inside fenced code read as the text they are, so a ledger quoting its own vocabulary is not cut in half by its own example. It is bounded twice over — 40 lines and 4 KB per ledger, 12 KB across all of them, with a `[… truncated]` line where something was dropped and a ledger past the total cap dropped whole rather than half-printed — and each file is read at most 1 MiB and only when `lstat` says it is a regular file, so a symlink planted under that name is skipped rather than followed and a FIFO never blocks the read. Nothing to print is printed as nothing: no header, no blank line, exit 0. The guard still never fails a hook.
- **`rules --hooks` prints three groups, and `doctor` reads them.** `HOOK_EVENTS` is `PreToolUse`, `PreCompact`, `SessionStart`; the snippet's third group carries `"matcher": "compact"`. `doctor` reports `hooks project: v0.3.3 (wired: PreToolUse, PreCompact, SessionStart)`, and an installation still wired the 0.3.2 way is `NOT wired (missing SessionStart) — paste the snippet from rules --hooks` — the missing event by name, because that is what has to be pasted; an unreadable settings file or a matcher aimed elsewhere is the more specific reason and still wins the line. A `SessionStart` matcher is read exactly the way a `PreToolUse` one is, against the session's SOURCE instead of a tool name: `compact` and `startup|compact` are wired, an unanchored regex is tested as one, `startup` gets `NOT wired (SessionStart matcher is not compact)`, and an absent matcher counts as wired because the guard's own `source` check is what keeps a startup quiet.
- **The ledger has to live under the session's cwd.** Both halves of the mechanism read `<session cwd>/.omelette/ledger-*.md`, so a plan whose ledger sits in another repository gets neither the stamp nor the print. Said in the rules template, in `docs/ORCHESTRATION.md` and in the README.
- **`doctor` names the client's two timeout walls.** A `mcp timeout` block, informational and never a fault: the wall-clock `MCP_TOOL_TIMEOUT` compared with the longest call the enabled units can make (the largest `timeoutS`, plus 60 s for gemini, whose hard kill sits that far above the timeout it hands agy), and the 30-minute stdio idle abort a call hits when it sends neither a response nor progress. Unset is the client's documented ~28 h default and reads as `ok`; below what the fleet needs the line ends `· TOO LOW`, the snippet to merge follows (`{"env":{"MCP_TOOL_TIMEOUT":"<needed>"}}`), and a `next` line appears once every first-run step is done. Both variables are resolved the way Claude Code resolves them — process environment, then the `env` block of `.claude/settings.local.json`, `.claude/settings.json` and the user scope's files under `$CLAUDE_CONFIG_DIR` or `~/.claude` — and the line names the file the value came from. A per-server `"timeout"` on the registration overrides the variable for that server and gets a line of its own; one the client would refuse is reported as ignored rather than counted. While gemini is enabled, one more line bounds `gemini_deep_research` at `3 stages × 2 attempts × (timeoutS + 60 s)`. This is the wall the 2026-09-06 incident hit: a `codex_code_review` that ran 1081 s against a client that had abandoned the request at 900 s.
- **`doctor` finds this checkout's servers under any prefix, and in two more files.** A registration is ours by where it points — command node, args path exactly this clone's `servers/<unit>.mjs` — rather than by the name it wears, and the scan now covers the user scope, **this** project's scope inside `.claude.json` (another project's entries are not this project's) and the project's checked-in **`.mcp.json`**, which doctor did not read at all before. Without `--prefix`, when nothing of ours is registered as `omelette-*` and our servers are found under exactly one other prefix, doctor adopts it — `prefix        orion (found on the registrations)` — and the unit lines and the `next` line use it, so an operator running under their own prefix stops being told to install what is already installed. Two prefixes are ambiguous: doctor names both, keeps `omelette`, and leaves the choice to `--prefix`. An explicit `--prefix` is unchanged, and so are `install`, `uninstall` and `update`, which still work by name.
- **The guard's wiring is the union of a scope's settings files.** `settings.json` and `settings.local.json` are read as one: a guard wired for one event in the shared file and the rest in the machine-local one is wired, and doctor said `NOT wired` about it because it kept whichever single file listed the most events. A matcher that covers no `Bash` call is still reported — unless another file wires that event properly, in which case there is nothing to fix and nothing is claimed.
- **Codex and Gemini read `capped`, so a front-truncated run can no longer pass for a whole answer.** `core/spawn.mjs` has reported since 0.3.2 that its tail cap dropped characters — and a tail cap drops the *beginning*, so a parser reading from the top sees a fragment. Grok acted on it; the other two did not. Now they do, in the shape their CLIs need. **Codex**: a capped run whose last `agent_message` survived comes back with `[codex: output capped at <N> chars — the beginning of the stream was dropped; treat the answer as partial]` and `partial: true`, and a capped run whose answer rode a line longer than the cap throws `codex output exceeded the <N> char cap and the final message was lost — raise codex.outputCap or narrow the task` — where it used to report "produced no answer", naming a cause that was not the cause. **Gemini**: agy prints one JSON envelope, so a capped run that still parses (its dropped front was a preamble) is marked the same way, and one whose envelope no longer parses throws `agy output exceeded the <N> char cap and the answer envelope was lost — raise gemini.outputCap or narrow the task` instead of failing open with the middle of that envelope as the answer. In both units a hard kill is answered first — the salvaged text under both markers — and only a killed run with nothing to salvage names the cap, in an error naming both bounds; and both cap errors join the deterministic failures the bounded retry skips, because a second full run would be paid for and would hit the same cap. Neither unit raises its `outputCap`: both stay at the fleet default of 400 000.
- **A run the client cancelled says so instead of blaming `timeoutS`.** `cancel: kill` ends a run with the same SIGKILL a hard kill uses, and all three adapters read it as one: the salvaged answer carried `[<unit>: hard-killed after <N>s — … raise <unit>.timeoutS …]` and a run with nothing to salvage threw the matching error, sending the operator after a bound that had held. `core/spawn.mjs` tells the two apart (`cancelled: true`), so a cancelled run is now marked `[<unit>: cancelled by the client — treat the answer as partial]`, or refused with `<bin> cancelled by the client` when there was nothing to keep — deterministic either way, because nobody is waiting for the retry. All three spawning units read the flag: `agy cancelled by the client`, `grok cancelled by the client`, `codex cancelled by the client`.
- **`gemini_deep_research` says when its report stands on partial stages.** Every stage is one agy one-shot, so every stage can come back partial; the report used to present the synthesis of a salvaged kill as a finished document. It now carries `[gemini: N of M stages returned partial answers]` under the title — under the degraded-run banner when there is one — and `partial: true` beside `status: "ok"` in the status feed. M counts every stage that ran (decompose, one per sub-question, synthesis); a gather that *threw* is counted there and never in N, because its `_(gather failed: …)_` line already stands where its finding would be. A cancelled run, which never reaches synthesis, is partial by definition.
- **Docs.** `docs/CONFIG.md`'s "What `outputCap` does" now describes all three units instead of Grok plus a line saying the other two keep the default; `docs/STATUS-FEED.md` lists the third reason a run is `partial`; `docs/ADAPTERS.md` replaces the "Gemini and Codex do not read `capped` — it is a gap" paragraph with the three CLI shapes worth copying, and states the bare-path contract an image tool keeps (`codex_image` returns a verified path, never a path with a marker attached).

- **No paid answer is lost: every result is spooled before the response is sent.** `core/results.mjs` writes each spawned call's answer to `<home>/results/<unit>/<resultId>.md` — a `0700` directory, a `0600` file, a fenced header (unit, tool, result id, model, effort, `startedAt`/`endedAt`, `durationMs`, `status`, `partial`, `detached`, `cwd`, a 200-character JSON-quoted prompt preview) and then the answer verbatim — inside `finish()`, before anything reaches the client. It is fail-soft the way the status feed is: synchronous, every fs call wrapped, a failure is one stderr line and the call still answers. Errors and refusals are spooled too, a disabled unit's included: a call refused before the spawn is still an answer the caller may have lost. Local tools (`<unit>_models`, `<unit>_result`) never are. The write is an `O_EXCL` temp file in the same directory plus a `rename`, so a reader sees the whole file or none of it, and a temp file this process did not create is never removed — it belongs to another server's live write. Retention is per unit, after every write and at server start: `resultsKeep` (default 50) results inside `resultsMaxBytes` (default 50 MB), oldest by `endedAt` first with the filename as the tie-breaker, abandoned `*.tmp` older than an hour swept, every unlink guarded because two servers of the same unit share the directory. One answer bigger than the whole budget is kept anyway — it is the one that was just paid for. `results: false` switches writing off per unit or in `defaults`, and `doctor` says so on the unit's new `results` line.
- **`<unit>_result` — the answer the client dropped, handed back.** A new `local` tool on every unit (answered in-process: no spawn, no status feed entry, no spool of its own). With no `id`: the newest result in full, then `Recent results:` and up to ten lines of `<resultId>  <tool>  <status>[ partial][ detached]  <durationMs>ms  <startedAt>` — which is what a caller who timed out actually needs, since it never received the id. With an `id`: that result. An id must match `^\d{8}T\d{6}Z-\d+-\d+$` and is checked before any path is built, the file is `lstat`ed and read only when it is a regular file (a symlink in the spool is refused, never followed), and an unknown id or an empty spool is one line with `isError`. Reading is unaffected by `results: false`: the switch stops new writes, it does not hide what is already there.
- **`omelette-fleet results [<unit>] [<id>] [--path]`.** The same files from a shell, with no server and no vendor CLI: no arguments lists the last ten across the fleet newest first (`<resultId>  <unit>  <tool>  <status>[ partial][ detached]  <durationMs>ms  <startedAt>`), a unit lists its own, a unit and an id prints that file, and `--path` prints paths instead of content. An empty spool is exit 0 — nothing is broken; an unknown unit, a malformed id and an id that is not there are exit 1 with one line each. Reading never creates a directory.

## 0.3.2 — 2026-09-06

- **Ledger vocabulary.** The rules file and ORCHESTRATION's "Ledger and handoff" now ask for two things a plan ledger did not have: provenance apart from trust (a claim from a unit, coder or tester is `candidate` until the orchestrator verified it, then `verified` / `rejected`) and demote-not-delete (a wrong `Ruling:` is never edited — a `Superseded by:` line follows it). Prose only; no code, no tokens per turn.
- **Grok no longer answers from a front-truncated stream.** `core/spawn.mjs` keeps the LAST `outputCap` characters of a run's stdout, and it now reports `capped: true` when that cap actually dropped something — a tail cap drops the *beginning*, so a parser reading a stream from the top is looking at a fragment and could not tell. Grok is the unit where that bites: its streaming NDJSON carries thinking deltas, tool calls and one JSON envelope per text delta alongside the answer, and the authoritative `result` line comes last. `interpretGrok` now splits the two cases instead of failing open on both. Whole lines still parse: the answer is real but missing its start, so it comes back with `[grok: output capped at <N> chars — the beginning of the stream was dropped; treat the answer as partial]` appended and `partial: true` beside `status: "ok"` in the status feed, alongside the hard-kill marker when a run managed both. Nothing parses — the answer rode one `result` line longer than the cap — and the streaming runs throw `grok output exceeded the <N> char cap and the final result line was lost — raise grok.outputCap or narrow the task`, where 0.3.1 would have handed back the JSON fragment that survived as if it were the answer; the plain-stdout image runs have no lines to parse and keep their front-truncated text under the marker. A hard kill still answers first — salvaged text with both markers — and only a killed run with nothing captured names the cap, in an error that names both bounds. That failure joins the deterministic ones the bounded retry skips — a second full run would be paid for and would hit the same cap. A run that was killed AND left only a fragment is the same loss and now says so too, instead of salvaging the fragment under the partial marker; and a kill on a run the CLI had already reported an error for names the error (`grok hard-killed after 300s; the CLI had reported: auth expired`, and the same clause inside the capped-kill message), because an expired login reads nothing like a slow review and no bound explains one. **`outputCap` is a config key** (positive int, default 400 000, per unit or in `defaults`, threaded through `spawnFor` and overridable per call); Grok's built-in raises it to 2 000 000 for the reason above. Documented in `docs/CONFIG.md` (a section of its own), `docs/STATUS-FEED.md` (the second reason a run is `partial`) and `docs/ORCHESTRATION.md`.
- **`omelette-fleet install --rules` is the whole first run in one command.** It registers the units exactly as before, then does `rules --agents --hooks` in the current directory — the operating rules, both sub-agent definitions, the `/omelette-test` skill, the guard script and the settings snippet, printed last, where the eye already is. It runs on every exit path, `claude` missing included, because the project files have nothing to do with the registrations; `--dry-run` covers both halves and still writes nothing. A fleet home the CLI may not write is reported as the failure it is — `config  FAILED to write …` and exit 1 — and the rules phase still runs, since an operator who asked for both halves should not lose the one that had nothing to do with it. Both halves write into the CURRENT directory, so the README's Quickstart now says it in two steps: `install` from the clone, then the project files from inside the project.
- **`doctor` says what to do next.** One `next` line while something is missing, in the order a first run needs it: `omelette-fleet install` (nothing registered), `omelette-fleet rules --agents --hooks` (registered here, but any of the four managed kinds is missing from the project), `merge the hooks snippet into .claude/settings.json (rules --hooks prints it)` (the script is there and nothing calls it) — and nothing at all once those are done. A registration is "ours" only when it points at this clone's server, so a name pointing at another checkout still gets `install`; the whole check reads the project scope, which is what the commands it suggests write. The install line carries the prefix the run was asked about (`omelette-fleet install --prefix review`), because plain `install` would register `omelette-*` and leave the names doctor went looking for exactly as missing as it found them. A managed file that is at the right path without our marker gets a line of its own instead of the plain suggestion — `rules --agents --hooks` would refuse that file, and sending an operator into a refusal is not a next step: doctor names the situation and the `--force` that ends it. A managed path that is a SYMLINK gets a third line, and deliberately no `--force`: `rules` refuses to write through a link whatever flags it is given, so the step is to remove the link. It is informational and **never a fault**: the exit code still answers one question only, whether a unit that is enabled AND registered is broken.
- **A `PreToolUse` matcher is read the way Claude Code reads one: an exact list, or an unanchored regex.** Comparing the string literally reported a guard wired under `"Bash|Edit"` — which fires on every Bash call — as `NOT wired`; anchoring every pattern instead got the other half wrong, since the harness tests a pattern unanchored. Now: absent, `""` and `"*"` mean everything; a string of nothing but tool names, `|`, `,` and spaces is an exact LIST, compared item by item, so `"Bash|Edit"` and `"Bash, Write"` are wired while `"Bashful"` and `"ash"` name no tool at all; anything else is a regex tested against `Bash` unanchored, which wires `".*"`, `"Ba."`, `"^Ba"` and `"ash$"`. One that does not compile covers nothing rather than being guessed at, and gets a line of its own — `NOT wired (PreToolUse matcher "(" is not a valid regex)` — because a typo in the settings file and a guard aimed at another tool are fixed differently, and a matcher that is not a string at all gets a third — `NOT wired (PreToolUse matcher is not a string)`, an explicit `null` included, since a key that is there holding a non-pattern is not the same state as a key that was never written.
- **The guard tells reads from writes for tags and rebases, by the MODE of the invocation rather than the position of a word.** Listing tags is how an agent finds the last release and `git rebase --abort` is the recovery an agent stuck mid-rebase needs — both were blocked and both now pass, and so does every other spelling of the same intent, because both subcommands are now classified by reading their arguments: a `tag` invocation is a write when a write flag appears anywhere in it (`-a`/`--annotate`, `-m`/`--message`, `-F`/`--file`, `--cleanup`, `-s`/`-u`/`--sign`, `-f`/`--force`, `-d`/`--delete`), or when a tag NAME is present with no listing or verify flag beside it — so `-l`, `--list`, `-n`/`-n5`, `--contains`/`--no-contains`, `--with`/`--without`, `--points-at`, `--merged`/`--no-merged` and `-v`/`--verify` read whatever else is in the command, and `git tag v1 --list` lists where `git tag v1`, `git tag -- v1`, `git tag --create-reflog v1`, `git tag --no-sign v1` and `git tag v1 --format=x` all create — `--sort` and `--format` decorate a listing without selecting one, which is exactly why they are not in that set. `rebase` is the mirror image: `--abort`, `--quit` and `--help`/`-h` pass wherever among the arguments they sit (`git rebase -q --abort` included), and every other form is blocked, `--continue` and `--skip` among them, since each creates a commit. Both scans read the command the way a shell would. Comments come off first, each to the end of its OWN line (`git tag v1 # --list` creates a tag; the `git commit` in `echo x # git commit` is text; the line below `echo hi # a note` is a command of its own). The command is then tokenized once with quoted spans opaque, so a flag inside quotes is text (`git rebase --exec 'echo --abort now' HEAD~1` rebases), a separator inside quotes ends nothing (`git tag --format="x; y" v1` is one command that names `v1`), and an option's value is a value rather than a name whether it arrives attached or as the next word (`git tag --sort refname` and `git tag --format "%(refname)"` list; `git tag -m msg v1` still creates). Every step is a single linear pass — comments, tokens, flags — so the guard's hot path, every Bash call in the session, stays free of the option-run tiling the regexes were built to avoid: a listing narrowed 60 times over, or a 10 KB command, is answered in milliseconds.
- **`--remove --agents` takes the empty skill directory with it.** A skill IS a directory, so removing `SKILL.md` alone left `.claude/skills/omelette-test/` behind, still reading as an installed skill. `syncManagedFile` removes files and nothing else, as before; the skills kind gets one timid post-remove step — only that directory, only after a run that actually removed our `SKILL.md`, only when it is empty, never through a symlink, and a failure is silent rather than a refusal on top of a removal that worked.
- **The hook snippet is quoted for the platform the CLI runs on.** POSIX single quotes as before; where `process.platform` is `win32`, double quotes instead (`"node \"C:\\Users\\me\\.claude\\hooks\\omelette-guard.mjs\""`), because `cmd.exe` reads a single quote as part of the path. That is a correctness fix in the quoting, **not** Windows support — see the platform note below, and note that a double-quoted command is still shell-quoted: under PowerShell or Git Bash a `$` in the path would expand. The builder moved into `core/rules.mjs` beside the hooks kind it belongs to and takes the platform as a parameter, so both forms are tested from either kind of machine; `doctor` still recognises the wiring by the script's name, whichever quoting it finds.
- **`/omelette-test <spec path> [repo path]`.** The skill takes an optional second argument for an orchestrator whose session sits in another repository: `$0` is the spec, `$1` the repo, and the injected commands are `` !`git -C "$1" diff HEAD` `` and `` !`git -C "$1" ls-files --others --exclude-standard` ``. Leave it off and the shell expands `"$1"` to an empty string, where `git -C ""` is a no-op — the diff is the current directory's, exactly as in 0.3.1 (verified on Claude Code 2.1.261, 2026-09-06).
- **`maxTurns` in a definition is honoured — measured, not assumed.** An agent given `maxTurns: 3` and six tool calls to make stopped after three, and the harness told the orchestrator it had stopped at its turn limit and could be continued (2026-09-06). So the tester template now says to report what it had left to do, and the rules file and `docs/ORCHESTRATION.md` say to raise `agents.tester.maxTurns`, re-render, and **continue the same tester** rather than dispatching a new one, which throws its context away.
- **"Picked up within seconds" is now "usually within seconds, sometimes minutes".** A new global definition once took about ten minutes to appear (2026-09-06). The CLI's post-write line, the README and `docs/ORCHESTRATION.md` all say so; the watcher is real, its latency is not a guarantee.
- **A positive-int config key is a WHOLE number.** `coerce` floored what it was given, so `omelette-fleet set grok.outputCap=0.5` became the `0` the key exists to forbid and `maxTurns=1.9` became a `1` nobody wrote. A fraction is refused outright now — in the file, in an environment variable and through `set`, which says what it wanted (`expected a positive integer (a whole number — 0.5 and 1.9 are refused, not rounded)`). `docs/CONFIG.md` says the same for every posint key.
- **The `/omelette-test` skill's `argument-hint` is quoted.** `argument-hint: [spec path] [repo path]` is not the hint it looks like: YAML reads `[spec path]` as a flow sequence and then finds a second one stapled to it, which is a parse error — and a skill file a YAML reader rejects is a skill Claude Code never loads. It ships as `"[spec path] [repo path]"`, and the frontmatter test now refuses an unquoted value that opens a flow collection, the same way it already refused an unquoted `": "`.
- **Platforms: macOS and Linux are supported; Windows through WSL.** Native Windows is not supported yet. CI runs the suite on `windows-latest` as a **non-gating signal** — 43 tests fail there today (POSIX path assertions, fake vendor binaries with no `.cmd` shim, file-mode checks), which is harness and platform work rather than a fault in the units, and it is tracked for 0.3.3. The README's Requirements section says the same.

## 0.3.1 — 2026-09-06

0.3.0 shipped the operating model as text. 0.3.1 turns three of its rules into mechanisms, and fixes one thing 0.3.0 promised but could not deliver for Grok.

- **Grok's hard-kill salvage now has something to salvage.** `grok_research` and `grok_code_review` ask the CLI for `--output-format streaming-messages-json --include-partial-messages` instead of `--output-format json`. The reason is measured, not theoretical: the `json` format writes **nothing** to stdout until the run ends — 0 bytes at 20 s on a probe whose plain-mode twin had text by 16 s — so 0.3.0's "keep what the run produced" path found an empty buffer on exactly the runs it exists for. The streaming format emits NDJSON as the answer is produced; a 30 s kill on the 2026-09-06 probe left 441 text deltas / 1513 characters recoverable. One parser serves both paths: `text_delta` events assemble the running answer (thinking deltas and tool-argument fragments never join it) and the final whole message wins when the run got that far, being the authoritative full text; a line truncated by the kill is skipped. The partial markers are unchanged, and `[grok: hard-killed after Ns — …]` now carries real text. Image runs keep plain mode.
- **Grok reports token usage.** Taken off the same stream and merged across the events that carry it, so a final message reporting only output tokens cannot erase the input count an earlier one gave — and a reported **0** survives the merge as the count it is, rather than reading as "none given". It reaches the status feed as `usage: { input, output }`, next to Gemini's. Grok reported none before.
- **Ledger and handoff, as a rule and as a hook.** The rules file and `docs/ORCHESTRATION.md` gain a "Ledger and handoff" section: keep a ledger for every plan from the first step, one line per event, every decision as `Ruling: <what> — <why> — <cost if wrong>`, tasks marked complete with their commits; append a handoff block before a compaction and at every natural pause; re-read the ledger after a compaction before doing anything else. Location is `<project>/.omelette/ledger-<plan>.md` by convention — the rule is the file, not the path. The `PreCompact` half of the new guard hook stamps `## Compaction <ts> (trigger: <manual|auto>) — re-read this ledger before continuing` into every `.omelette/ledger-*.md`, so the marker lands even on a compaction nobody announced.
- **`omelette-fleet rules --hooks`** writes `.claude/hooks/omelette-guard.mjs` — one managed script serving both hook events — and **prints** the `hooks.PreToolUse` / `hooks.PreCompact` snippet to paste into `.claude/settings.json` or `.claude/settings.local.json`. It prints it on every run, not only the one that created the script, because a script nobody calls is the failure mode where everything looks installed; under `--dry-run` it announces the snippet instead of printing it, since a snippet naming a script that was never written is a snippet somebody pastes. The path in it is absolute and shell-quoted — a hook `command` is a command line, not an argv, so a checkout under `~/My Projects` would otherwise paste a hook that runs `node /Users/you/My`. The CLI never edits either settings file: 0.3.0's rule that Claude Code's config is read and never written now covers them too. `doctor` parses **both** of a scope's settings files read-only and reports `hooks  project: v0.3.1 (wired: PreToolUse, PreCompact)` or `NOT wired — paste the snippet from rules --hooks`, matching on the script's name inside the command string rather than on an exact path (so the quoted form still reads as wired), and naming a settings file it could not parse rather than counting it as unwired.
- **The coder's "never commits" is enforced.** The guard's `PreToolUse` handler (matcher `Bash`) exits 2 when the calling `agent_type` is `omelette-coder` and the command is a `git` invocation that creates commits, moves branches or touches stashes, worktrees or tags: `commit`, `merge`, `rebase`, `cherry-pick`, `revert`, `am`, `pull`, `push`, `stash`, `tag`, `worktree`, `branch <name>`, a `branch` flag that moves a ref (`-m`/`-M`, `-c`/`-C`, `-f`/`--force`, `-u`/`--set-upstream-to`), and any `checkout`/`switch` that creates a branch (`-b`/`-B`, `-c`/`-C`, `--create`, `--force-create`, `--orphan`, `--track` — wherever the flag sits in the command, name attached or not). Options ahead of the subcommand are stepped over with their values, quoted ones included (`-C "/My Dir"`, `-c user.name="A B"`, `--work-tree /tmp/x`, a value-less `-p`, a bare `--`), so prefixing them does not slip past. `git log`, `git diff`, `git status`, `git commit-tree` and `git branch` as a listing (`-l`, `--list`, `-a`, `-r`, `-v`, `-d`/`-D`) are deliberately untouched. It is containment for a delegated agent, not a boundary: it reads one command string, so an argv-array spawn, a backslash-escaped `g\it` or `$(which git)` is out of scope by design. It is a **settings-level** hook keyed on `agent_type` rather than a `hooks:` block in the agent's own frontmatter, because the frontmatter form did not fire at all on Claude Code 2.1.261 — no log line, `git commit` went straight through — while the settings-level form fired for the same sub-agent, blocked it, and carried `agent_type` on its stdin (spiked 2026-09-06). The script never throws: malformed stdin, an unknown event or an unwritable ledger all exit 0 — and so do stdin past 1 MiB and stdin that never closes (abandoned after 5 s), since the pipe belongs to somebody else. A `.omelette/ledger-*.md` that is not a regular file is `lstat`ed and skipped, so a symlink planted under that name is not followed and a FIFO does not hold the append open.
- **`/omelette-test <spec path>` — the tester handoff as a mechanism.** `rules --agents` now also writes `.claude/skills/omelette-test/SKILL.md`: `context: fork`, `agent: omelette-tester`, `argument-hint: [spec path]` (model-invocable on purpose: the orchestrating session calls it through the Skill tool — a `disable-model-invocation: true` key would leave only a human able to run it, which the live check on 2.1.261 confirmed), and a body carrying `` !`git diff HEAD` `` and `` !`git ls-files --others --exclude-standard` ``. Those run at invocation, before the fork, so the forked tester opens with the working tree's real diff — there is no step at which the coder's summary could be substituted for it. `$ARGUMENTS` is the spec path. The rules file's tester flow points at the skill and keeps the manual `subagent_type: omelette-tester` dispatch as the fallback.
- **Agent settings live in the fleet config.** A new top-level `agents` block — `agents.coder.model` (`opus`), `agents.coder.effort` (`xhigh`), `agents.tester.model` (`sonnet`), `agents.tester.effort` (`xhigh`), `agents.tester.maxTurns` (`80`) — is what the shipped definitions render from: the templates carry `{{model}}`, `{{effort}}` and `{{maxTurns}}`. `omelette-fleet set agents.tester.maxTurns=120` takes the dotted three-part path, `omelette-fleet show agents` prints the block with each value's source, and `rules --agents` re-renders from the config as it is at that moment (the marker stays the proof of ownership; a changed value just makes the content differ). Retuning a role is now a config change the orchestrator can make mid-plan — the rules file spells out the turn-limit case: raise it, re-render, re-dispatch. An invalid value in the file is a warning and the built-in default, never a refusal to write the definition; through `set` the same mistake is refused outright.
- **`omelette-tester` gained `maxTurns` and a line about it**: a truncated run is not a failing suite, and it must say so in its report. The template also states outright that it never modifies the implementation or the implementer's tests.
- **Managed files generalise to four kinds.** Rules, agents, skills and hooks share one registry and one `syncManagedFile`, so each kind gets the same marker-is-ownership rules, the same refresh / foreign / remove behaviour, the same `--print` and `--dry-run`, its own `doctor` line and its own `update` refresh hint. Only the comment syntax of the marker differs (`<!-- -->`, a YAML comment on line 2, `//` on line 1). A flag selects which kinds a run touches — `--remove --hooks` takes away the rules file and the marked guard script, and nothing else — and an unmarked file is never removed whichever flag named it. `--remove` never removes a directory either: `--remove --agents` takes the skill's `SKILL.md` and leaves the empty `.claude/skills/omelette-test/` for you to delete.
- **Docs.** `docs/ORCHESTRATION.md` gains "Ledger and handoff", the clean-context rationale for the tester (a second, uncorrelated context catches what the author's cannot — Boris Cherny's test-time-compute tip), a monorepo placement note, "narrow the run when the full suite is Docker-bound", the hook layer in "How the rules reach a session", and the Grok streaming note in "Supervising". `docs/CONFIG.md` documents the `agents` block and the dotted `set` form; `docs/SECURITY.md` gains a section on exactly what the guard does and restates that your settings files are never written; `docs/ADAPTERS.md` recommends a streaming output format over a whole-document one, with the measurement behind it; `docs/STATUS-FEED.md` records Grok's usage. The README gains the `rules --hooks` step and a "Fewer permission prompts" snippet, and its inline copy of `examples/fleet.config.json` — which was missing the `agents` block — now matches the file byte for byte.
